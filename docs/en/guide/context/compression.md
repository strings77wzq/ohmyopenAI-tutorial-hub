# Context Compression

## Concept

The essence of context compression isn't "deleting information" — it's **preserving equivalent decision-making value with fewer tokens**. Good compression lets the Agent make the same decisions in a compressed window as it would in the full window.

## Why Is Compression Needed?

The context window has two hard constraints:

1. **Capacity ceiling**: Even a 200K window fills up during long-running tasks.
2. **Attention decay**: The larger the window, the less attention the Agent pays to the middle portion ("lost in the middle" effect).

Compression keeps the window small and efficient.

## Three Compression Strategies

### Extractive Compression

Keep the most critical sentences or paragraphs from the original text; discard the rest.

```
Original (200 lines of test output):
  Test 1: PASS
  Test 2: PASS
  ...
  Test 47: FAIL - expected 200 got 404
  Test 48: PASS
  ...

Extractive compression:
  Tests: 46/47 passed, 1 failed
  FAIL: Test 47 - expected 200 got 404 (line 128)
```

**Best for**: Test output, build logs, lint reports, search result lists.

**Not for**: Code (extractive compression breaks syntax), safety rules (every rule is non-negotiable).

### Abstractive Compression

Use a model to generate a semantic summary of the original text, expressing the same information in fewer tokens.

```
Original (500 lines of API documentation):
  POST /api/users - Create user. Params: name (string, required),
  email (string, required)...
  GET /api/users/:id - Get user...
  ...

Abstractive summary (generated by another Agent or the same Agent in summary mode):
  API provides user CRUD: POST /api/users creates (name+email required),
  GET /api/users/:id queries, PATCH /api/users/:id updates,
  DELETE /api/users/:id deletes.
  All endpoints require Bearer token. Pagination via page+limit params.
```

**Best for**: API documentation, long conversation histories, project architecture docs, log summaries.

**Risk**: Summaries may lose critical details (like a parameter's default value or an edge-case behavior). After compression, the Agent might make wrong decisions based on inaccurate summaries.

### Structural Compression

Replace raw content with structured metadata; the Agent expands details when needed.

```
Original (a 2000-line src/ directory):
  src/
  ├── auth/
  │   ├── login.ts (340 lines)
  │   ├── middleware.ts (120 lines)
  │   └── types.ts (85 lines)
  ├── api/
  │   ├── routes.ts (560 lines)
  │   └── handlers.ts (420 lines)
  └── utils/
      └── format.ts (95 lines)

Structural compression:
  src/ (7 files, ~2120 lines)
  Modules: auth (login + middleware + types), api (routes + handlers), utils (format)
  Entry: api/routes.ts → registers all routes
  Auth: auth/middleware.ts → Bearer token verification
```

**Best for**: Project structure, large module indexes, dependency graphs.

**Advantage**: The Agent knows "where the information is" and can read precisely when needed. Extremely high compression ratio with zero information loss.

## When Compression Is Not Applicable

Some information loses its decision-making value once compressed — these must be kept in full:

| Information Type | Why It Cannot Be Compressed |
|-----------------|---------------------------|
| Safety rules (permission boundaries, key policies) | Missing even one rule could lead to a security incident |
| Code currently being modified | Agent needs line-by-line understanding to write correct changes |
| Acceptance criteria | Each item is an independent pass/fail condition |
| Error messages (first failure) | The exact wording of an error message is a critical debugging clue |
| User's latest instructions | What the user said cannot be "summarized" by the model — intent would be lost |

## When to Compress

```
At task start:
  Pre-inject L1+L2 summaries → No compression (nothing to compress yet)

After each iteration:
  Check window utilization
  ├── < 60% → No compression
  ├── 60–80% → Compress L5 (operational evidence), keep only the latest round
  └── > 80% → Compress L4+L5 + old iterations in L3
               → If still not enough, trigger human decision

Key principle: Compress lower-priority layers first (L4→L5→L3); never compress L1
```

## Example: Compression Plan for a Long Conversation History

An Agent conversation that has run for 20 iterations. Each iteration includes the Agent's reasoning and tool call results.

```
Before compression (~80K tokens):
  [Iteration 1] Read file → analyze → modify → test fails
  [Iteration 2] Read file → analyze → modify → test fails
  ...
  [Iteration 19] Read file → analyze → modify → test passes
  [Iteration 20] Current round

After compression (~30K tokens):
  [Summary: Iterations 1–18]
  Goal: Fix 3 type errors in the auth module
  Approaches tried:
    Approach A (add type assertions) → failed (introduced new errors)
    Approach B (refactor interface definitions) → failed (broke other modules)
    Approach C (introduce generics) → partial success (2/3 errors fixed)
  Current state: 1 error remaining, file src/auth/middleware.ts:47

  [Iteration 19 - Full text] → Most recent context
  [Iteration 20 - Full text] → Current round
```

Key insight: The compression preserved "what was tried" and "current state," so the Agent doesn't repeat failed attempts.

## Troubleshooting

| Symptom | Likely Cause | Fix |
|---------|--------------|-----|
| Agent repeats previous errors after compression | Summary didn't preserve the "tried approaches" list | Maintain a "Tried & Failed" list in L3 |
| Compression causes critical context loss | A layer that shouldn't be compressed was (e.g., L1 acceptance criteria) | Ensure compression only happens on L4+L5+old L3 iterations |
| Agent frequently re-reads compressed content | Summary not detailed enough for the Agent to decide whether to expand | Add an index of "expandable information sources" |
