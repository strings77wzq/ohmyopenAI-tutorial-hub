# 评测层级

## 概念

评测的目标不是"给 AI 输出打一个抽象分数"，而是**判断它是否满足可发布的验收标准**。不同层级的评测回答不同的问题，对应不同的工具和证据类型。

## 为什么需要分层？

单层评测有两个致命缺陷：

1. **粒度不匹配**：一个"代码质量分数"无法告诉你问题是"API 签名错了"还是"变量命名不规范"
2. **反馈延迟**：如果只在最后才跑全量评测，Agent 可能在错误方向上浪费了很多轮迭代

四层评测模型让 Agent 在每一次操作后都能收到合适粒度的反馈。

## 四层模型

```
┌─────────────────────────────────────────────────────────┐
│ L1 单例检查 (Unit Check)                                │
│ 问题: 这一个输入是否得到了正确的输出？                     │
│ 工具: fixture, 快照, assertion                          │
│ 频率: 每次工具调用后                                     │
│ 反馈延迟: 秒级                                           │
│ 示例: "这个 API 调用返回了 200 还是 404？"               │
├─────────────────────────────────────────────────────────┤
│ L2 场景检查 (Scenario Check)                            │
│ 问题: 一个完整的工作流是否从头到尾正确？                    │
│ 工具: Harness scenario, trace, e2e test                 │
│ 频率: 每个子任务完成后                                   │
│ 反馈延迟: 分钟级                                         │
│ 示例: "创建 PR → 跑 CI → 部署预览 → 链接检查 全流程正确？" │
├─────────────────────────────────────────────────────────┤
│ L3 回归检查 (Regression Check)                          │
│ 问题: 旧的行为是否被这次变更破坏了？                        │
│ 工具: 测试套件, 链接审计, 快照对比                        │
│ 频率: 每个 PR 提交前                                     │
│ 反馈延迟: 分钟到小时级                                    │
│ 示例: "新增的页面是否破坏了已有页面的链接？"               │
├─────────────────────────────────────────────────────────┤
│ L4 发布检查 (Release Gate)                              │
│ 问题: 这个变更是否适合公开发布？                           │
│ 工具: 构建验证, 可访问性审计, 性能测试, 内容审查           │
│ 频率: 每次发布前                                         │
│ 反馈延迟: 分钟到小时级                                    │
│ 示例: "Lighthouse a11y ≥ 95? 移动端无溢出？暗色模式正常？" │
└─────────────────────────────────────────────────────────┘
```

## 每层的详细设计

### L1 单例检查

这是最快、最便宜的评测层。Agent 在每次工具调用后应回答两个问题：

```
1. 返回值是否符合预期格式？（结构检查）
2. 返回值是否在合理范围内？（语义检查）
```

示例：

```
Agent 调用: write_file("src/auth.ts", content)
  L1 结构检查: 文件是否成功写入？（write_file 返回 success → PASS）
  L1 语义检查: 文件行数是否合理？（期望 ~50 行，实际 48 行 → PASS）
              文件行数是否合理？（期望 ~50 行，实际 3 行 → FAIL — 可能是内容截断）

Agent 调用: npm run docs:build
  L1 结构检查: 命令是否成功执行？（exit code 0 → PASS）
  L1 语义检查: 构建时间是否异常？（通常 6s，实际 6.2s → PASS）
              构建时间是否异常？（通常 6s，实际 45s → FAIL — 可能是死循环或无限递归）
```

### L2 场景检查

一个场景 = 一个用户可感知的完整工作流。场景检查验证的不是单个操作，而是操作的组合。

```
场景: "用户新增一个 MCP 教程页面"

步骤:
  1. 创建 docs/guide/mcp/new-page.md
  2. 在 docs/.vitepress/config.ts 的 sidebar 中注册
  3. npm run docs:build

L2 检查:
  [ ] 新页面在构建后的 dist/ 中可访问
  [ ] 侧边栏中出现了新条目
  [ ] 页面之间的链接（prev/next）正确
  [ ] 没有引入新的构建警告
```

### L3 回归检查

回归检查的核心是"before/after 对比"：

```
PR 前:
  npm run docs:check-links → 0 errors
  npm run docs:build → 6.2s, 102 pages

PR 后:
  npm run docs:check-links → 0 errors (无回归)
  npm run docs:build → 6.4s, 103 pages (新增 1 页，合理)

如果 PR 后:
  npm run docs:check-links → 3 errors ← REGRESSION
  → 阻止合并，直到修复
```

### L4 发布检查

这是最后一道门，检查的是"发布准备就绪"：

| 检查项 | 工具 | 阈值 |
|--------|------|------|
| 构建验证 | `npm run docs:build` | 零错误零警告 |
| 链接审计 | `npm run docs:check-links` | 零断链 |
| 路由验证 | `npm run docs:check-routes` | 所有侧边栏链接可达 |
| 性能 | Lighthouse | Performance ≥ 90 |
| 可访问性 | axe-core / Lighthouse | Accessibility ≥ 95 |
| 移动端 | 手动截图 375px | 无溢出，无截断 |
| 暗色模式 | 手动截图 | 所有页面暗色可读 |
| 内容审查 | 人工 | 无事实错误，无错别字 |

## 示例：为"新增 Loop Engineering 子页"定义四层检查

```
L1 单例检查（每次 write_file 后）:
  [ ] 文件行数 ≥ 50（非空页面）
  [ ] frontmatter 存在（如果有）

L2 场景检查（所有子页写完后）:
  [ ] npm run docs:build 通过
  [ ] 新增的 3 个子页在构建输出中
  [ ] 子页之间的 next-step 链接可达

L3 回归检查（提交前）:
  [ ] npm run docs:check-links → 0 errors
  [ ] npm run docs:check-routes → 侧边栏包含了新子页

L4 发布检查（合并前）:
  [ ] 每个子页 ≥ 80 行（符合模块学习标准）
  [ ] 侧边栏 config 中 collapsed: false（新内容不应默认折叠）
```

## 练习

为一个"修改 config.ts 的 sidebar 结构"的 PR 定义四层检查：

1. L1：修改 config.ts 后，Agent 应该用什么命令检查格式正确性？
2. L2：什么场景验证能确保 sidebar 修改没有破坏现有导航？
3. L3：哪些已有页面可能被这次修改影响？
4. L4：如果这个 PR 要发布，还需要检查什么？

## 排错

| 症状 | 可能原因 | 修复 |
|------|----------|------|
| L1 通过但 L2 失败 | 单次操作正确但组合起来出错（如 sidebar 注册了但页面路径错误） | 确保 L2 覆盖了端到端流程 |
| L3 发现大量回归 | PR 范围过大，触及了太多文件的链接 | 拆分 PR 为多个小变更 |
| L4 每次都失败在同一项 | 门禁阈值设置不合理或缺少修复工具 | 调整阈值或提供自动修复脚本 |
