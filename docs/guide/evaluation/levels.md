# 评测层级

## 概念

评测的目标不是"给 AI 输出打一个抽象分数"，而是**判断它是否满足可发布的验收标准**。不同层级的评测回答不同的问题，对应不同的工具和证据类型。

四层评测模型让 Agent 在每一次操作后都能收到合适粒度的反馈——越早发现问题，修复成本越低。

## 为什么需要分层？

单层评测有两个致命缺陷：

**1. 粒度不匹配**

一个"代码质量分数"无法告诉你问题是"API 签名错了"还是"变量命名不规范"。一个 L4 级别的 Lighthouse 分数无法定位到具体是哪一行代码导致了性能下降。

**2. 反馈延迟**

如果只在最后才跑全量评测，Agent 可能在错误方向上浪费了很多轮迭代。一个在第一步就写错的文件路径，如果到 L4 才被发现，Agent 已经在这个错误的基础上写了 500 行代码。

**3. 成本不对等**

L1 级别的检查可以在毫秒内完成，几乎零成本；L4 级别的全量检查可能需要几分钟甚至十几分钟。每次都跑 L4 是浪费；只跑 L1 则会遗漏系统级问题。

四层模型正是为了解决这三个问题。

## 四层模型总览

```
┌─────────────────────────────────────────────────────────┐
│ L1 单例检查 (Unit Check)                                │
│ 问题: 这一个输入是否得到了正确的输出？                     │
│ 工具: fixture, 快照, assertion                          │
│ 频率: 每次工具调用后                                     │
│ 反馈延迟: 秒级                                           │
│ 示例: "这个 API 调用返回了 200 还是 404？"               │
├─────────────────────────────────────────────────────────┤
│ L2 场景检查 (Scenario Check)                            │
│ 问题: 一个完整的工作流是否从头到尾正确？                    │
│ 工具: Harness scenario, trace, e2e test                 │
│ 频率: 每个子任务完成后                                   │
│ 反馈延迟: 分钟级                                         │
│ 示例: "创建 PR → 跑 CI → 部署预览 → 链接检查 全流程正确？" │
├─────────────────────────────────────────────────────────┤
│ L3 回归检查 (Regression Check)                          │
│ 问题: 旧的行为是否被这次变更破坏了？                        │
│ 工具: 测试套件, 链接审计, 快照对比                        │
│ 频率: 每个 PR 提交前                                     │
│ 反馈延迟: 分钟到小时级                                    │
│ 示例: "新增的页面是否破坏了已有页面的链接？"               │
├─────────────────────────────────────────────────────────┤
│ L4 发布检查 (Release Gate)                              │
│ 问题: 这个变更是否适合公开发布？                           │
│ 工具: 构建验证, 可访问性审计, 性能测试, 内容审查           │
│ 频率: 每次发布前                                         │
│ 反馈延迟: 分钟到小时级                                    │
│ 示例: "Lighthouse a11y ≥ 95? 移动端无溢出？暗色模式正常？" │
└─────────────────────────────────────────────────────────┘
```

## L1 单例检查：每次工具调用后的即时反馈

这是最快、最便宜的评测层。Agent 在每次工具调用后应回答两个问题：

```
1. 返回值是否符合预期格式？（结构检查）
2. 返回值是否在合理范围内？（语义检查）
```

### 结构检查 vs 语义检查

```
Agent 调用: write_file("src/auth.ts", content)
  L1 结构检查: 文件是否成功写入？（write_file 返回 success → PASS）
  L1 语义检查: 文件行数是否合理？（期望 ~50 行，实际 48 行 → PASS）
              文件行数是否合理？（期望 ~50 行，实际 3 行 → FAIL — 可能是内容截断）

Agent 调用: npm run docs:build
  L1 结构检查: 命令是否成功执行？（exit code 0 → PASS）
  L1 语义检查: 构建时间是否异常？（通常 6s，实际 6.2s → PASS）
              构建时间是否异常？（通常 6s，实际 45s → FAIL — 可能是死循环或无限递归）
```

### L1 的设计要点

- **不替代人工判断**：L1 检查的是"操作是否成功"，不检查"内容是否好"。一个文件写入成功但内容是胡言乱语，L1 不会报错——这是 L2 和 L4 的职责。
- **阈值要合理**：文件行数的"合理范围"不能太窄（否则会误报正常的短文件），也不能太宽（否则会漏报截断）。
- **快速失败**：L1 检查必须快到可以每次调用后都跑，不能拖慢 Agent 的工作流。

## L2 场景检查：工作流级别的验证

一个场景 = 一个用户可感知的完整工作流。场景检查验证的不是单个操作，而是操作的组合和顺序。

### 场景定义

```
场景: "用户新增一个 MCP 教程页面"

前置条件: 项目已 clone，依赖已安装

步骤:
  1. 创建 docs/guide/mcp/new-page.md
  2. 在 docs/.vitepress/config.ts 的 sidebar 中注册
  3. npm run docs:build

验证点:
  [ ] 新页面在构建后的 dist/ 中可访问
  [ ] 侧边栏中出现了新条目
  [ ] 页面之间的链接（prev/next）正确
  [ ] 没有引入新的构建警告
```

### L1 通过但 L2 失败的情况

这是最常见的"层级缝隙"问题：

```
L1 单例检查:
  write_file → PASS（文件写入成功）
  edit_file(config.ts) → PASS（编辑成功）
  npm run docs:build → PASS（构建成功）

L2 场景检查:
  新页面在 dist/ 中可访问？→ FAIL（文件名拼写和 sidebar 中的路径不一致）
```

每个 L1 检查都通过了，但组合起来的场景是失败的。这就是为什么 L2 不可或缺。

### L2 的设计要点

- **覆盖端到端**：场景检查必须从用户视角出发，覆盖完整的操作链，不能只检查中间步骤。
- **验证组合效果**：关注操作之间的交互——文件 A 写入后，文件 B 的引用是否仍然有效？
- **频率适中**：每个子任务完成后跑一次 L2，不需要每次工具调用都跑。

## L3 回归检查：确保没有倒退

回归检查的核心是"before/after 对比"。它回答的问题是：**这次变更是否破坏了任何已有功能？**

### 回归检查 vs 场景检查

| 维度 | L2 场景检查 | L3 回归检查 |
|------|------------|------------|
| 关注点 | "这个新功能是否正常工作？" | "已有功能是否被破坏？" |
| 范围 | 只检查本次变更涉及的场景 | 检查所有已有的场景 |
| 时机 | 子任务完成后 | PR 提交前 |
| 工具 | 手写验证脚本 | 维护的测试套件 |

### 典型的回归检查

```
PR 前:
  npm run docs:check-links → 0 errors
  npm run docs:build → 6.2s, 102 pages

PR 后:
  npm run docs:check-links → 0 errors (无回归)
  npm run docs:build → 6.4s, 103 pages (新增 1 页，合理)

如果 PR 后:
  npm run docs:check-links → 3 errors ← REGRESSION
  → 阻止合并，直到修复
```

### 漂移检测

回归检查不只是"断链检测"。它还包括趋势监控：

```
对比维度:
  ├── 链接健康度: 断链数（期望: 0, 告警: >0）
  ├── 构建时间:   秒数（期望: 6-8s, 告警: >15s）
  ├── 页面数量:   页数（期望: 持续增长, 告警: 突然减少）
  ├── 文件大小:   最大 CSS/JS bundle（期望: 稳定, 告警: 增长 > 20%）
  └── 构建警告:   警告数（期望: 0, 告警: >0）
```

漂移不一定意味着回归——可能是正常的项目增长。区分两者的关键是**变化率**：

```
正常: 页面数量从 100 → 103（新增 3 页，符合 PR 描述）
回归: 页面数量从 100 → 97（有 3 页丢失了！）
```

### L3 的设计要点

- **维护成本**：回归套件需要持续维护。每次项目结构变化（新增模块、删除页面），对应的快照和 fixture 也需要更新。
- **Golden Dataset**：回归套件依赖固定的测试数据来保证一致性。详见 [回归套件](./regression-suite)。
- **CI 集成**：回归检查必须集成到 CI，不能只靠"Agent 自觉运行"。

## L4 发布检查：最后的质量门

这是最后一道门，检查的是"发布准备就绪"。L4 的独特之处在于它包含**人工判断**——有些质量标准无法自动化验证。

### 自动化检查项

| 检查项 | 工具 | 阈值 |
|--------|------|------|
| 构建验证 | `npm run docs:build` | 零错误零警告 |
| 链接审计 | `npm run docs:check-links` | 零断链 |
| 路由验证 | `npm run docs:check-routes` | 所有侧边栏链接可达 |
| 性能 | Lighthouse | Performance ≥ 90 |
| 可访问性 | axe-core / Lighthouse | Accessibility ≥ 95 |
| LCP | Lighthouse | < 2.5s |
| CLS | Lighthouse | < 0.1 |

### 人工检查项

| 检查项 | 为什么需要人工 |
|--------|---------------|
| 首页首屏清晰度 | 设计感和信息传达是主观判断 |
| 移动端适配 | 需要在真实设备上验证布局 |
| 暗色/亮色主题 | 需要视觉判断"是否看起来像有意设计的" |
| 内容事实准确性 | 需要领域知识判断代码示例是否正确 |
| 中英文一致性 | 需要语言能力判断翻译质量 |
| 新内容教学完整性 | 每个新页面是否包含概念+步骤+示例+练习+下一步 |

### L4 的设计要点

- **自动化 + 人工互补**：自动化覆盖客观可判定的标准，人工覆盖主观审美和领域知识。
- **阈值要保守**：L4 是最后的门，阈值应该比 L3 更严格。宁可多拦截几次，也不要让低质量内容上线。
- **处理 false positive**：如果 L4 频繁误报（比如外部链接被反爬虫返回 403），需要调整规则或增加白名单。

## 示例：为"新增子页"定义四层检查

```
L1 单例检查（每次 write_file 后）:
  [ ] 文件行数 ≥ 50（非空页面）
  [ ] frontmatter 存在（如果有）

L2 场景检查（所有子页写完后）:
  [ ] npm run docs:build 通过
  [ ] 新增的子页在构建输出中
  [ ] 子页之间的 next-step 链接可达

L3 回归检查（提交前）:
  [ ] npm run docs:check-links → 0 errors
  [ ] npm run docs:check-routes → 侧边栏包含了新子页

L4 发布检查（合并前）:
  [ ] 每个子页 ≥ 80 行（符合模块学习标准）
  [ ] 侧边栏 config 中 collapsed: false（新内容不应默认折叠）
  [ ] 人工审查：新页面的教学完整性
```

## 练习

为一个"修改 config.ts 的 sidebar 结构"的 PR 定义四层检查：

1. L1：修改 config.ts 后，Agent 应该用什么命令检查格式正确性？
2. L2：什么场景验证能确保 sidebar 修改没有破坏现有导航？
3. L3：哪些已有页面可能被这次修改影响？
4. L4：如果这个 PR 要发布，还需要检查什么？

## 排错

| 症状 | 可能原因 | 修复 |
|------|----------|------|
| L1 通过但 L2 失败 | 单次操作正确但组合起来出错（如 sidebar 注册了但页面路径错误） | 确保 L2 覆盖了端到端流程 |
| L3 发现大量回归 | PR 范围过大，触及了太多文件的链接 | 拆分 PR 为多个小变更 |
| L4 每次都失败在同一项 | 门禁阈值设置不合理或缺少修复工具 | 调整阈值或提供自动修复脚本 |
| 某个层级完全被跳过 | 工作流中没有集成对应检查 | 在 prompt/system message 中加入强制检查步骤 |
