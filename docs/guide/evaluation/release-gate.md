# 发布门禁

## 概念

发布门禁是最后一道关卡。它回答一个问题：**这个变更准备好面对真实用户了吗？**

这不是一个技术检查——它是产品决策。技术检查能告诉你"构建通过了"，但只有发布门禁能告诉你"这个版本的用户体验不会比上一个版本差"。

## 为什么需要独立的发布门禁？

回归套件通过 ≠ 可以发布。

- 回归套件验证"没有破坏已有的"
- 发布门禁验证"新增的质量达标"

一个新页面可能通过了所有回归检查（没有破坏任何现有链接），但它本身只有 30 行、没有练习章节、没有下一步链接——不符合模块学习标准。

### 回归检查的盲区

```
回归检查: "这次变更有没有破坏已有功能？"
  → 答案: 没有 ✓
  → 但是: 新页面只有 30 行，没有练习章节
  → 回归检查看不到这个问题

发布门禁: "新增内容的质量是否达标？"
  → 答案: 没有 ✗
  → 阻止发布，直到补全内容
```

### 发布门禁的独特价值

| 检查类型 | 回归检查 | 发布门禁 |
|----------|---------|---------|
| 关注点 | 向后兼容 | 向前质量 |
| 检查范围 | 已有功能 | 新增内容 |
| 验证对象 | "没有变差" | "足够好" |
| 包含人工判断 | 否 | 是 |

## 发布门禁检查清单

### 自动化检查（必须全部通过）

```
[ ] npm run docs:build          零错误零警告
[ ] npm test                    全套自查通过
[ ] npm run docs:check-stale   无僵尸变更
[ ] Lighthouse Performance      ≥ 90
[ ] Lighthouse Accessibility    ≥ 95
[ ] Lighthouse Best Practices   ≥ 90
[ ] Lighthouse SEO               ≥ 90
[ ] LCP                         < 2.5s
[ ] CLS                         < 0.1
[ ] 构建 bundle 大小             ≤ 上次发布的 120%
```

### 人工检查（至少 2 人确认）

```
[ ] 首页首屏            清晰传达"这是什么网站，给谁用"
[ ] 移动端 375px        无水平溢出，文字可读，CTA 可点击
[ ] 暗色/亮色双主题      都看起来有意设计的，不像默认模板
[ ] 新增内容质量         每个新页面 ≥ 概念+步骤+示例+练习+下一步
[ ] 中英文导航          两种语言的侧边栏都对应当前语言
[ ] 链接可发现性         重要的新入口是否从首页或其他页面可达
[ ] 事实准确性           代码示例能否运行，概念解释是否正确
[ ] 拼写和语法           中文无错别字，英文无语法错误
```

## 自动 vs 人工门禁的分工

```
自动化门禁应该覆盖:
  ✓ 可客观判定的标准（"链接返回 200"、"构建警告 = 0"）
  ✓ 高频重复的检查（每次 PR 都跑）
  ✓ 人类容易漏掉的检查（100+ 页的链接审计）

人工门禁应该覆盖:
  ✓ 主观审美判断（"这个设计看起来像默认模板吗？"）
  ✓ 低频高价值决策（"这个新模块的教学质量达标吗？"）
  ✓ 人类专长的检查（拼写、语法、事实准确性）
```

### 分工的边界

有些检查处于灰色地带，需要根据项目情况决定：

```
可自动化的:
  - 代码示例是否能运行（可以实际执行）
  - 页面行数是否 ≥ 80（可以 AST 解析）
  - frontmatter 是否完整（可以规则检查）

建议人工的:
  - 代码示例是否"有意义"（不只是能运行，还要有教学价值）
  - 页面行数是否"合理"（80 行的废话不如 40 行的精华）
  - frontmatter 的 description 是否准确描述了页面内容
```

## 处理 False Positive 和 False Negative

任何门禁都会出错：

| 情况 | 定义 | 处理 |
|------|------|------|
| **False Positive** | 门禁报 FAIL，但实际没问题 | 调整门禁规则或增加豁免条件 |
| **False Negative** | 门禁报 PASS，但实际有问题 | 增加新的检查规则，不能靠"下次人工注意" |

### False Positive 的处理

```
场景: link-checker 报了一个链接 404，但那个链接指向的是外部站点且目标确实存在（只是反爬虫返回了 403）
处理: 给外部链接增加白名单域名，或增加重试机制后再判定
原则: 不能因为 false positive 而放松整个门禁——只针对特定场景豁免
```

### False Negative 的处理

```
场景: 自动化门禁全绿，但用户反馈"这个教程的代码示例跑不通"
处理: 分析用户报的 bug，新增一条自动化检查（如"代码示例必须在沙箱中验证通过"）
原则: 每一个 false negative 都应该转化为一条新的自动化检查，而不是"下次注意"
```

### 防御性设计

```
宁可误报（false positive）也不要漏报（false negative）

误报的代价: 多花 10 分钟人工确认
漏报的代价: 低质量内容上线，用户流失

所以: 如果不确定某个检查是否应该通过，选择阻止发布
```

## 回滚标准

不是所有的门禁失败都应该阻止发布。定义回滚触发条件：

```
必须回滚（阻止发布）:
  - 链接审计新增 > 0 个断链
  - 构建失败或新增警告 > 0
  - Lighthouse a11y < 90（比基线下降 5 分以上）
  - 首页 CLS > 0.15（严重布局偏移）

可以带已知问题发布（记录到 TODOS）:
  - Lighthouse Performance 从 95 降到 92（仍在 ≥ 90 阈值内）
  - 新增的 1 个页面翻译质量标记为 "待优化"（不影响核心用户）
  - 非关键页面的 mobile 排版需要微调（不影响核心学习流程）
```

### 回滚决策框架

```
问题: 这个问题是否影响核心用户体验？
  → 是: 阻止发布
  → 否: 可以带已知问题发布

问题: 这个问题是否会在后续 PR 中自然修复？
  → 是: 记录到 TODOS，不阻止发布
  → 否: 必须在本次发布前修复

问题: 这个问题的修复成本是多少？
  → 低（< 30min）: 修复后再发布
  → 高（> 2h）: 评估是否可以带已知问题发布
```

## 示例：发布内容的完整门禁流程

```
Step 1: 自动化门禁
  npm run docs:build → PASS (6.8s, 106 pages, +4 页)
  npm test → PASS (links 0 errors, routes ok, frontmatter ok)
  npm run docs:check-stale → PASS
  Lighthouse home → Perf 93, A11y 97, LCP 1.8s, CLS 0.02 → 全部 ≥ 阈值

Step 2: 人工检查
  首页首屏 → 无变化（只新增了子页，没动首页）
  移动端 375px → 新增页面的代码块无溢出 ✓
  暗色/亮色 → 新页面两个主题都可读 ✓
  新内容质量 → 4 页，每页 80-200 行，都有概念+步骤+示例+练习+下一步 ✓
  中英文导航 → 中文 sidebar 已更新（+4 条目），英文 sidebar 暂未更新（标 WIP）→ 可接受
  事实准确性 → 代码示例在概念层面正确（非可执行代码） ✓

Step 3: 决策
  所有自动化门禁通过 ✓
  所有人工检查通过 ✓
  英文 sidebar 的 WIP 标记已在 TODOS 中记录

  → RELEASE: GO
  → 已知问题: EN 版本缺翻译（记录在 TODOS Week 3）
```

### 门禁流程的关键点

- **自动化先于人工**：先跑自动化检查，避免浪费人工时间在明显不合格的内容上。
- **人工检查有结构**：人工检查不是"随便看看"，而是按清单逐项确认。
- **决策有记录**：每次发布的决策（GO/NO-GO）和已知问题都应该记录下来。

## 练习

为一个"新增教程页（~180 行）"的 PR 设计发布门禁流程：

1. 自动化门禁应该检查什么？
2. 这次变更可能影响哪些已有的门禁结果？
3. 如果 Lighthouse Performance 从 93 降到 88（因为新页面多了一个大图），应该阻止发布吗？
4. 人工检查应该重点看什么？

## 排错

| 症状 | 可能原因 | 修复 |
|------|----------|------|
| 自动化门禁全绿但用户报 bug | False negative — 某类问题没有对应检查 | 分析用户报的 bug，新增一条自动化检查 |
| 每次发布都被同一项人工检查挡下 | 人工检查的标准太模糊或太高 | 把可量化的部分抽成自动化检查 |
| 门禁太松导致低质量内容上线 | 人工检查被跳过或敷衍 | 把"新增内容质量"拆成多个具体子项 |
| 发布决策没有记录 | 缺少发布日志模板 | 创建标准化的发布决策记录格式 |
| 已知问题不断累积 | 没有定期清理 TODOS | 每周审查一次已知问题，决定修复或关闭 |
