# 发布门禁

## 概念

发布门禁是最后一道关卡。它回答一个问题：**这个变更准备好面对真实用户了吗？**

这不是一个技术检查——它是产品决策。技术检查能告诉你"构建通过了"，但只有发布门禁能告诉你"这个版本的用户体验不会比上一个版本差"。

## 为什么需要独立的发布门禁？

回归套件通过 ≠ 可以发布。

- 回归套件验证"没有破坏已有的"
- 发布门禁验证"新增的质量达标"

一个新页面可能通过了所有回归检查（没有破坏任何现有链接），但它本身只有 30 行、没有练习章节、没有下一步链接——不符合模块学习标准。

## 发布门禁检查清单

### 自动化检查（必须全部通过）

```
[ ] npm run docs:build          零错误零警告
[ ] npm test                    全套自查通过
[ ] npm run docs:check-stale   无僵尸 openspec 变更
[ ] Lighthouse Performance      ≥ 90
[ ] Lighthouse Accessibility    ≥ 95
[ ] Lighthouse Best Practices   ≥ 90
[ ] Lighthouse SEO               ≥ 90
[ ] LCP                         < 2.5s
[ ] CLS                         < 0.1
[ ] 构建 bundle 大小             ≤ 上次发布的 120%
```

### 人工检查（至少 2 人确认）

```
[ ] 首页首屏            清晰传达"这是什么网站，给谁用"
[ ] 移动端 375px        无水平溢出，文字可读，CTA 可点击
[ ] 暗色/亮色双主题      都看起来有意设计的，不像默认模板
[ ] 新增内容质量         每个新页面 ≥ 概念+步骤+示例+练习+下一步
[ ] 中英文导航          两种语言的侧边栏都对应当前语言
[ ] 链接可发现性         重要的新入口是否从首页或其他页面可达
[ ] 事实准确性           代码示例能否运行，概念解释是否正确
[ ] 拼写和语法           中文无错别字，英文无语法错误
```

## 自动 vs 人工门禁的分工

```
自动化门禁应该覆盖:
  ✓ 可客观判定的标准（"链接返回 200"、"构建警告 = 0"）
  ✓ 高频重复的检查（每次 PR 都跑）
  ✓ 人类容易漏掉的检查（100+ 页的链接审计）

人工门禁应该覆盖:
  ✓ 主观审美判断（"这个设计看起来像默认模板吗？"）
  ✓ 低频高价值决策（"这个新模块的教学质量达标吗？"）
  ✓ 人类专长的检查（拼写、语法、事实准确性）
```

## 处理 false positive 和 false negative

任何门禁都会出错：

| 情况 | 定义 | 处理 |
|------|------|------|
| **False Positive** | 门禁报 FAIL，但实际没问题 | 调整门禁规则或增加豁免条件 |
| **False Negative** | 门禁报 PASS，但实际有问题 | 增加新的检查规则，不能靠"下次人工注意" |

示例：link-checker 报了一个链接 404，但那个链接指向的是外部站点且目标确实存在（只是反爬虫返回了 403）。→ False Positive。解决方案：给外部链接增加 `data-ignore-check` 属性或白名单域名。

## 回滚标准

不是所有的门禁失败都应该阻止发布。定义回滚触发条件：

```
必须回滚（阻止发布）:
  - 链接审计新增 > 0 个断链
  - 构建失败或新增警告 > 0
  - Lighthouse a11y < 90（比基线下降 5 分以上）
  - 首页 CLS > 0.15（严重布局偏移）

可以带已知问题发布（记录到 TODOS）:
  - Lighthouse Performance 从 95 降到 92（仍在 ≥ 90 阈值内）
  - 新增的 1 个 EN 页面翻译质量标记为 "待优化"（不影响中文用户）
  - 非关键页面的 mobile 排版需要微调（不影响核心学习流程）
```

## 示例：发布 "Context Engineering 4 子页" 的完整门禁流程

```
Step 1: 自动化门禁
  npm run docs:build → PASS (6.8s, 106 pages, +4 页)
  npm test → PASS (links 0 errors, routes ok, frontmatter ok)
  npm run docs:check-stale → PASS
  Lighthouse home → Perf 93, A11y 97, LCP 1.8s, CLS 0.02 → 全部 ≥ 阈值

Step 2: 人工检查
  首页首屏 → 无变化（只新增了子页，没动首页）
  移动端 375px → 新增页面的代码块无溢出 ✓
  暗色/亮色 → 新页面两个主题都可读 ✓
  新内容质量 → 4 页，每页 80-200 行，都有概念+步骤+示例+练习+下一步 ✓
  中英文导航 → 中文 sidebar 已更新（+4 条目），英文 sidebar 暂未更新（标 WIP）→ 可接受
  事实准确性 → 代码示例在概念层面正确（非可执行代码） ✓

Step 3: 决策
  所有自动化门禁通过 ✓
  所有人工检查通过 ✓
  英文 sidebar 的 WIP 标记已在 TODOS.md 中记录

  → RELEASE: GO
  → 已知问题: EN 版本缺 Context Engineering 子页翻译（记录在 TODOS.md Week 3）
```

## 练习

为一个"新增 Loop Engineering retry-and-breaker.md（~180 行）"的 PR 设计发布门禁流程：

1. 自动化门禁应该检查什么？
2. 这次变更可能影响哪些已有的门禁结果？
3. 如果 Lighthouse Performance 从 93 降到 88（因为新页面多了一个大 ASCII 图），应该阻止发布吗？
4. 人工检查应该重点看什么？

## 排错

| 症状 | 可能原因 | 修复 |
|------|----------|------|
| 自动化门禁全绿但用户报 bug | False negative — 某类问题没有对应检查 | 分析用户报的 bug，新增一条自动化检查 |
| 每次发布都被同一项人工检查挡下 | 人工检查的标准太模糊或太高 | 把可量化的部分抽成自动化检查 |
| 门禁太松导致低质量内容上线 | 人工检查被跳过或敷衍 | 把"新增内容质量"拆成多个具体子项 |
