# Evaluator 设计

## 概念

Evaluator 是把验收标准转化为可自动执行的检查的程序。好的 evaluator 不是"打分器"，而是"决策辅助工具"——它告诉你**具体的失败原因**，让你（或 Agent）知道该修什么。

## 为什么 Evaluator 设计很难？

大多数 evaluator 的失败不是因为逻辑错误，而是因为**验收标准本身不清晰**。如果你说不清楚"好"是什么样的，你也写不出能判断"好"的代码。

另一个常见问题是**标准和实现脱节**。验收标准说"内容质量达标"，evaluator 却只检查"文件行数 ≥ 80"——行数和质量之间没有因果关系。

## Evaluator 设计五原则

### 原则 1：单标准

一个 evaluator 只评估一个明确的标准。如果一个 evaluator 同时检查"格式正确"和"内容准确"，失败时你无法知道是格式问题还是内容问题。

```
✗ 坏 evaluator: "检查文档质量"
   → 失败。原因不明。

✓ 好 evaluator: "检查所有内部链接返回 200"
   → 失败。3 个链接返回 404: /guide/old-page, ...
```

单标准原则的深层含义是：**每个标准需要独立的失败路径**。如果"格式正确"和"内容准确"被捆绑在一个 evaluator 里，修复格式问题后重新运行，你会得到一个 PASS——但内容问题可能仍然存在。

### 原则 2：失败必须有原因

Evaluator 的输出必须包含足够信息让 Agent 自动修复：

```
{
  "criterion": "所有内部链接返回 2xx",
  "status": "FAIL",
  "failures": [
    {
      "file": "docs/guide/skills/index.md",
      "line": 47,
      "link": "/guide/old-reference",
      "status_code": 404,
      "suggestion": "页面不存在。可能的正确路径: /guide/skills/reference"
    }
  ]
}
```

不是：

```
{
  "score": 0.7,
  "status": "FAIL"
}
```

一个好的失败报告应该回答三个问题：

1. **什么失败了？** — 具体的文件、行号、值
2. **为什么失败？** — 期望值 vs 实际值
3. **怎么修复？** — 具体的修复建议或可能的方向

### 原则 3：处理边界输入

好的 evaluator 不会在边界输入上崩溃：

| 边界输入 | 期望行为 |
|----------|----------|
| 空文件 | 报告"无链接可检查"，不报错 |
| 纯英文页面 | 正常检查（不因缺少中文而失败） |
| 非常大的文件（>500 行） | 正常处理，不超时 |
| 只有外部链接的页面 | 跳过内部链接检查 |
| 链接中包含特殊字符 | 正确解析，不崩溃 |
| 文件不存在 | 报告明确错误，不抛异常 |
| 文件格式不支持 | 跳过并记录，不中断整个套件 |

边界输入是 evaluator 最容易出错的地方。一个只在"正常情况"下工作的 evaluator，在生产环境中遇到 1% 的边界情况就会频繁误报。

### 原则 4：与人工验收标准对齐

Evaluator 的通过条件应该和人的判断一致：

```
人工验收标准: "所有侧边栏链接都能到达正确的页面"
Evaluator 实现: 遍历 sidebar config → 逐个 HEAD → 检查 2xx
→ 对齐 ✓
```

不对齐的情况：

```
人工验收标准: "页面内容准确且更新到最新"
Evaluator 实现: 检查 lastUpdated 字段非空
→ 不对齐 ✗（lastUpdated 非空 ≠ 内容准确）
```

校准方法：找 10 个已知"好"的页面和 10 个已知"差"的页面，分别跑 evaluator。如果"好"页面的通过率 < 95%（误报太多），或"差"页面的检出率 < 90%（漏报太多），需要调整 evaluator。

### 原则 5：跨模型和 Prompt 变更稳定

好的 evaluator 不应该因为 Agent 换了模型或 prompt 调整了措辞就失效。规则式 evaluator（解析输出结构、检查链接状态）比 LLM-as-judge 更稳定。

```
稳定（规则式）:
  node scripts/check-doc-links.mjs
  → 解析 HTML/markdown，提取链接，HEAD 请求验证状态码
  → 不受 Agent 模型影响

不稳定（LLM-as-judge）:
  "请用 1-10 分评估这个页面的质量"
  → 模型换了 → 分数分布变了 → 阈值失效
```

## Evaluator 类型

### 规则式 Evaluator

基于确定性规则的检查，结果完全可预测：

```
规则: 所有内部链接返回 2xx
实现: 解析 markdown → 提取链接 → HEAD 请求 → 检查状态码
优点: 稳定、快速、可调试
缺点: 只能检查明确的规则，无法判断"内容好不好"
```

### LLM-as-Judge Evaluator

用 LLM 来评判输出质量：

```
规则: 页面的教学内容完整且准确
实现: 给 LLM 页面内容 + 评分标准 → 返回评分和理由
优点: 能处理主观判断（"这个解释清楚吗？"）
缺点: 不稳定（换模型就失效）、成本高、不可调试
```

### 混合 Evaluator

先用规则式做基础检查，再用 LLM-as-judge 做质量判断：

```
Step 1: 规则式检查
  - 文件行数 ≥ 80? → 如果不是，直接 FAIL
  - 有 frontmatter? → 如果不是，直接 FAIL

Step 2: LLM-as-judge（仅在 Step 1 通过时执行）
  - 教学内容完整吗？（概念+步骤+示例+练习）
  - 代码示例正确吗？
  - 解释清楚吗？
```

混合模式的成本效益最优：规则式检查快速排除明显不合格的输出，LLM-as-judge 只在必要时介入。

## Evaluator 校准

如果你的 evaluator 使用 LLM 评判（LLM-as-judge），需要校准：

```
Golden Set: 10 个已知"好"的页面 + 10 个已知"差"的页面

Evaluator 在 Golden Set 上运行:
  - 对"好"页面的通过率: 应 ≥ 95%（不应误报）
  - 对"差"页面的检出率: 应 ≥ 90%（不应漏报）

如果通过率太低:
  → 阈值太严格，调高一点

如果检出率太低:
  → 阈值太宽松，或 evaluator 标准不对，调低或重写
```

### 校准流程

1. **收集 Golden Set**：从历史数据中挑选 10 个确定"好"的输出和 10 个确定"差"的输出。
2. **运行 Evaluator**：记录每个输出的评分和判定结果。
3. **计算指标**：
   - True Positive（差的被正确识别为差）/ 总差的 = 检出率
   - True Positive（好的被正确识别为好）/ 总好的 = 通过率
4. **调整**：通过率 < 95% → 放宽标准；检出率 < 90% → 收紧标准或重写 evaluator。
5. **验证**：调整后重新跑 Golden Set，直到两个指标都达标。
6. **定期重校**：模型更新后，Golden Set 的判定可能需要更新。

## 示例：设计一个"检查页面是否有练习部分"的 Evaluator

```
验收标准: 每个教程页必须包含"练习"章节

Evaluator 实现:
  1. 读取页面的 markdown 源
  2. 查找 ## 练习 或 ## Exercise 标题
  3. 如果找到 → 检查标题下是否有 ≥ 50 字符的非标题内容
  4. 如果有 ≥ 50 字符 → PASS
  5. 如果标题不存在或内容不足 → FAIL

边界输入:
  - 非教程页面（如 examples/） → 跳过（不在检查范围内）
  - 页面语言是英文 → 同时匹配 ## Exercise 和 ## 练习

输出:
  {
    "criterion": "每个教程页包含练习章节",
    "status": "FAIL",
    "file": "docs/guide/context/compression.md",
    "reason": "存在 ## 练习 标题，但内容仅 12 字符（< 50）",
    "suggestion": "练习章节至少需要一个完整的问题陈述或操作任务"
  }
```

这个 evaluator 的设计体现了所有五个原则：

- **单标准**：只检查"有练习章节"
- **失败有原因**：指出了具体文件、问题（内容不足）、建议
- **处理边界**：跳过非教程页面，支持中英文
- **与人工对齐**：人工验收也是"每个教程页必须有练习"
- **跨模型稳定**：基于 markdown 解析，不依赖 LLM

## 练习

为一个"检查每个新页面是否有 next-step 链接"的 requirement 设计 evaluator：

1. evaluator 的输入是什么？
2. 怎么判断"有 next-step 链接"？（具体匹配规则）
3. 哪些页面应该被跳过？（非教程页、首页等）
4. 边界输入有哪些？怎么处理？

## 排错

| 症状 | 可能原因 | 修复 |
|------|----------|------|
| Evaluator 对明显正确的输出报 FAIL | 规则太严格或没处理合法的变体格式 | 检查边界输入，放宽匹配规则 |
| Evaluator 对明显错误的输出报 PASS | 规则太宽松或没覆盖这种错误类型 | 增加新的检查条件 |
| Evaluator 在 CI 中通过但人工审查发现问题 | 验收标准和 evaluator 实现不对齐 | 重读人工验收标准，重写 evaluator |
| LLM-as-judge 在新模型下完全失效 | 新模型的评分分布和旧模型不同 | 在新模型上重新校准 golden set |
| Evaluator 误报率突然上升 | 项目结构变化导致旧规则不再适用 | 检查项目结构变化，更新 evaluator |
