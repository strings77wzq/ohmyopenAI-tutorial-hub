# 评测与质量

评测的目标不是给 AI 输出打一个抽象分数，而是判断它是否满足可发布的验收标准。

## 你无法改进你无法衡量的东西

在传统软件开发中，"质量"可以靠 code review + 手工测试兜底。但在 AI Agent 场景下，输出是非确定性的——同一个 prompt 可能产生不同的代码、不同的文档、不同的决策。如果你没有评测，你甚至不知道质量是在变好还是变差。

评测解决三个核心问题：

| 问题 | 没有评测时的困境 | 有评测后的状态 |
|------|-----------------|---------------|
| **当前质量如何？** | "看起来还行"——依赖主观感觉 | 每次变更都有量化快照 |
| **变更是否引入了问题？** | 发现问题靠用户反馈 | 发布前自动拦截 |
| **模型更新是否影响了输出？** | 换模型后才知道坏了 | Golden Set 即时检测 |

没有评测的 Agent 开发就像没有单元测试的后端开发——你可能碰巧写对了，但你永远无法确信。

## 评测不是一次性的

一个常见的误解是：评测是"最后跑一遍测试"。实际上，评测贯穿整个开发周期：

```
构思阶段     → 定义验收标准（什么算"好"？）
开发阶段     → 每次工具调用后做 L1 单例检查
子任务完成时 → 做 L2 场景检查
PR 提交前    → 做 L3 回归检查
发布前       → 做 L4 发布检查
发布后       → 监控实际用户行为，验证假设
```

越早发现问题，修复成本越低。一个在 L1 阶段被发现的格式错误，修复只需要 30 秒；如果漏到 L4 才被用户发现，可能需要回滚、重新发布、通知用户。

## 评测层级概览

本模块将评测分为四个层级，每个层级回答不同的问题：

| 层级 | 问题 | 频率 | 反馈延迟 | 工具 |
|------|------|------|----------|------|
| L1 单例检查 | 这一个输入是否得到正确输出？ | 每次工具调用后 | 秒级 | fixture, 快照, 断言 |
| L2 场景检查 | 一个完整工作流是否从头到尾正确？ | 每个子任务完成后 | 分钟级 | harness scenario, trace |
| L3 回归检查 | 旧行为是否被这次变更破坏？ | 每个 PR 提交前 | 分钟到小时级 | 测试套件, 快照对比 |
| L4 发布检查 | 是否适合公开发布给真实用户？ | 每次发布前 | 分钟到小时级 | Lighthouse, a11y 审计 |

这四个层级不是互相替代的，而是互补的。L1 发现的粒度问题 L4 不一定能发现（因为 L4 关注的是全局指标），L4 发现的设计问题 L1 完全看不到。

## Evaluator：评测的原子单元

每个层级的评测都由若干 evaluator 组成。Evaluator 是把验收标准转化为可执行检查的程序。一个好的 evaluator：

- **只评估一个明确标准**——如果同时检查"格式正确"和"内容准确"，失败时你不知道是哪个问题
- **给出失败原因**——不只是 PASS/FAIL，而是"文件 X 第 47 行链接返回 404"
- **能处理边界输入**——空文件、超大文件、特殊字符不会让它崩溃
- **与人工标准对齐**——evaluator 说 PASS 时，人也会说 PASS
- **跨模型稳定**——换了模型或调了 prompt，evaluator 的判断标准不变

详细的 evaluator 设计指南见 [Evaluator 设计](./evaluator-design)。

## 评测的成本效益

评测不是免费的——每个 evaluator 都需要编写、维护、运行。关键是用最小的成本覆盖最大的风险：

```
高价值评测（优先做）:
  ✓ 链接检查 — 100+ 页面的断链检测，人工几乎不可能全覆盖
  ✓ 构建验证 — 确保每次变更都能成功构建
  ✓ 路由验证 — 确保所有侧边栏链接可达

低价值评测（可以不做）:
  ✗ 每个文件的字符编码检查 — 现代编辑器几乎不会出错
  ✗ 每个图片的 alt 文本长度检查 — 收益太低
  ✗ 每个代码块的语言标记检查 — 不影响功能
```

### 投入产出分析

```
阶段 1: 从 0 到 1（1-2 小时）
  投入: 写 2-3 个简单 evaluator（链接检查 + 构建验证）
  收益: 拦截 80% 的常见错误
  ROI: 极高

阶段 2: 从 1 到 5（半天）
  投入: 补充路由检查、frontmatter 检查、快照对比
  收益: 覆盖 95% 的可自动化检查
  ROI: 高

阶段 3: 从 5 到 20（1-2 天）
  投入: 添加 Lighthouse、a11y 审计、性能监控
  收益: 覆盖 99% 的检查场景
  ROI: 中等（边际收益递减）

阶段 4: 从 20 到 100+（持续投入）
  投入: 添加各种边界情况检查
  收益: 覆盖 99.9% 的检查场景
  ROI: 低（大部分检查永远不会触发）
```

大多数项目只需要阶段 1-2 的投入。阶段 3 适合有明确质量要求的项目。阶段 4 通常不值得。

## 评测 ≠ 测试

评测和测试经常被混用，但它们有不同的侧重点：

| 维度 | 传统测试 | AI 评测 |
|------|---------|---------|
| 目标 | 验证代码逻辑正确 | 验证输出质量达标 |
| 输入 | 确定性的测试用例 | 可能有变化的 prompt |
| 输出 | 通过/失败 | 通过/失败 + 质量评分 |
| 关注点 | "代码做了它该做的" | "输出对用户有价值" |
| 稳定性 | 完全可重复 | 可能有随机性 |

AI 评测继承了传统测试的很多思想（自动化、可重复、失败有原因），但它还需要处理传统测试不需要面对的问题：非确定性输出、主观质量判断、模型版本漂移。

## 常见误区

### 误区 1：评测 = 打分

"给这个页面打 1-10 分"不是评测。分数没有告诉你哪里需要改进，也没有给你一个明确的 PASS/FAIL 判定。好的评测是基于标准的，不是基于主观打分的。

### 误区 2：评测越多越好

200 个 evaluator 全部跑一遍需要 10 分钟，但其中 150 个在检查你永远不会出错的东西。评测的价值在于**以最小的成本覆盖最大的风险**。一个项目只需要几个关键 evaluator，而不是几百个。

### 误区 3：自动化一切

有些检查天然适合人工判断（"这个设计看起来像默认模板吗？"），有些检查天然适合自动化（"链接返回 200 吗？"）。强行把主观判断自动化只会得到不可靠的结果。

### 误区 4：评测通过 = 可以发布

回归套件验证"没有破坏已有功能"，但不验证"新增内容质量达标"。一个新页面可能通过了所有回归检查，但它本身只有 30 行、没有练习章节——不符合发布标准。

### 误区 5：过度拟合评测指标

如果你把所有精力都优化"evaluator 通过率"，你可能会得到一个"evaluator 全绿但用户体验很差"的系统。评测指标是手段，不是目的。始终要回到用户视角：这个输出对用户有价值吗？

### 误区 6：忽略评测的维护成本

写一个 evaluator 只需要 30 分钟，但维护它可能需要持续投入。项目结构变化、模型更新、标准调整都会让已有的 evaluator 失效。在写新 evaluator 之前，先问自己：这个检查的维护成本是否值得它的收益？

## 模块结构

本模块包含四个部分，建议按顺序阅读：

1. **[评测层级](./levels)** — 四层评测模型的详细设计：L1 单例检查、L2 场景检查、L3 回归检查、L4 发布检查
2. **[Evaluator 设计](./evaluator-design)** — 如何编写好的 evaluator：五原则、校准方法、类型选择
3. **[回归套件](./regression-suite)** — 如何把 evaluator 组织成测试套件：分层组织、Golden Dataset、漂移检测
4. **[发布门禁](./release-gate)** — 何时是质量达标可以发布的：自动化 vs 人工、false positive/negative 处理、回滚标准

每个部分都建立在前面的基础上——理解了层级才知道 evaluator 服务于哪一层，理解了 evaluator 才知道回归套件由什么组成，理解了回归套件才知道发布门禁还需要补充什么。
