# Harness 最佳实践

这些准则来自生产环境中 Agent 系统的实战经验。遵循它们可以避免常见的陷阱，建立可持续演进的 Harness 体系。

## 1. 场景小而稳

**原则**：每条场景只验证一个核心行为，避免"一个失败全盘失败"。

```json
// ❌ 不好：一个场景验证太多东西
{
  "name": "代码分析全能测试",
  "expected": {
    "contains": ["功能说明", "参数描述", "复杂度分析", "改进建议", "测试用例"]
  }
}

// ✅ 好：拆成独立场景
{ "name": "代码功能解释", "expected": { "contains": ["功能说明"] } }
{ "name": "参数描述", "expected": { "contains": ["参数描述"] } }
{ "name": "复杂度分析", "expected": { "contains": ["复杂度"] } }
```

**为什么重要**：
- 定位问题更快：失败直接指向具体能力
- 修复影响更小：改一个场景不会破坏其他测试
- 结果更清晰：通过率真实反映每个能力的状态

## 2. 评估器组合使用

**原则**：不要只用单一评估器，推荐 `contains + no-error + json-valid` 组合。

```
┌─────────────────────────────────────────┐
│           评估器组合策略                   │
├─────────────────────────────────────────┤
│  基础层: no-error (所有场景必须)          │
│  内容层: contains (关键词检查)            │
│  格式层: json-valid 或 schema-valid       │
│  语义层: semantic-match (高质量要求时)     │
│  语言层: language-check (多语言场景)       │
└─────────────────────────────────────────┘
```

**为什么不单独使用 `contains`**：
- `contains` 检查"有没有说对"，但不检查"有没有说错"
- 一个输出可能包含所有关键词，但同时包含大量错误信息
- `no-error` 是最低成本的质量保障——永远不要省略

## 3. Mock 优先，真实验证兜底

**原则**：日常回归用 Mock，真实 API 仅做冒烟验证。

```
CI/CD 流水线分层：

┌─────────────────────────────────────┐
│  第一层：Mock 回归测试 (100% 场景)    │
│  - 运行时间: <1 分钟                 │
│  - 成本: $0                          │
│  - 频率: 每次提交                     │
├─────────────────────────────────────┤
│  第二层：真实 API 冒烟测试 (10% 场景)  │
│  - 运行时间: ~5 分钟                  │
│  - 成本: ~$0.50/次                    │
│  - 频率: 每次合并到主分支              │
├─────────────────────────────────────┤
│  第三层：真实 API 全量测试 (100% 场景) │
│  - 运行时间: ~30 分钟                 │
│  - 成本: ~$5/次                       │
│  - 频率: 每周一次或发布前              │
└─────────────────────────────────────┘
```

**为什么这种分层有效**：
- 第一层保证基本功能不退化（快速反馈）
- 第二层保证 Mock 与真实行为一致（防止 Mock 过时）
- 第三层保证全量质量（发布信心）

## 4. 指标可追踪

**原则**：至少追踪三项核心指标——通过率、平均时延、回归失败 Top3 原因。

### 通过率追踪

```
日期        总场景  通过  通过率   变化
2024-01-10  100    95   95.0%    -
2024-01-11  100    93   93.0%    ↓ 2.0%
2024-01-12  102    98   96.1%    ↑ 3.1%
2024-01-13  102    97   95.1%    ↓ 1.0%
```

### 延迟追踪

```
场景类型        P50     P90     P99     目标
简单函数解释    0.8s    1.2s    2.0s    <2s
递归函数解释    1.1s    1.8s    3.0s    <3s
长代码解释      2.5s    4.0s    8.0s    <5s
```

### 失败原因分析

```
Top 3 失败原因 (本周):
1. 缺少关键词 "复杂度" - 15次失败 - 建议: 在 Prompt 中明确要求
2. 超时 (>30s) - 8次失败 - 建议: 优化长代码截断逻辑
3. 语言混杂 (中英混合) - 5次失败 - 建议: 在 Prompt 中强调中文输出
```

## 5. 失败可诊断

**原则**：每次失败保留完整上下文——输入、模型输出、评估器详情、环境信息。

### 失败记录模板

```json
{
  "failure_id": "20240115-143000-explain-code",
  "timestamp": "2024-01-15T14:30:00Z",
  "scenario": "解释递归函数",
  "input": {
    "skill": "explain-code",
    "code": "function fib(n){return n<=1?n:fib(n-1)+fib(n-2)}"
  },
  "output": "This is a recursive function...",
  "evaluators": {
    "contains": {
      "passed": false,
      "missing": ["递归", "斐波那契"],
      "found": ["recursive", "function"]
    },
    "no-error": { "passed": true },
    "language-check": {
      "passed": false,
      "detected": "en",
      "expected": "zh-CN"
    }
  },
  "environment": {
    "model": "gpt-4",
    "mock": true,
    "harness_version": "1.2.0"
  }
}
```

### 诊断决策树

```
评估器报告失败
    │
    ▼
检查 details 字段
    │
    ├── 缺少关键词 → Prompt 是否明确引导了这些内容？
    │       ├── 是 → 模型能力不足，考虑换模型
    │       └── 否 → 调整 Prompt，明确要求
    │
    ├── 语言错误 → Prompt 是否指定了输出语言？
    │       ├── 是 → 模型未遵守指令，考虑加 language-check 评估器
    │       └── 否 → 在 Prompt 中添加语言要求
    │
    ├── 格式错误 → 输出解析逻辑是否正确？
    │       ├── 是 → Mock 数据与真实行为不一致，更新 Mock
    │       └── 否 → 修复解析逻辑
    │
    └── 超时 → 代码是否过长？
            ├── 是 → 实现代码截断或分块处理
            └── 否 → 检查网络和 API 延迟
```

## 6. 场景即文档

**原则**：好的测试场景本身就是最好的文档——它精确地描述了 Agent 应该做什么。

```json
{
  "name": "递归函数解释必须覆盖递归调用过程",
  "description": "当用户输入一个递归函数时，Agent 应该：\n1. 识别出这是递归函数\n2. 解释递归的调用过程\n3. 说明基础情况和递归情况\n4. 分析时间复杂度",
  "input": {
    "skill": "explain-code",
    "code": "function factorial(n) { return n <= 1 ? 1 : n * factorial(n-1); }"
  },
  "expected": {
    "contains": ["递归", "阶乘", "基础情况", "调用过程"],
    "evaluators": ["contains", "no-error"]
  }
}
```

这个场景同时回答了三个问题：
1. **需求**：递归函数的解释应该包含什么
2. **验证**：如何确认 Agent 做到了
3. **示例**：具体的输入输出是什么

## 7. 渐进式构建

**原则**：不要试图一次性建立完美的 Harness。从最小可用集开始，逐步扩展。

```
阶段 1: 最小可用 (1-2 天)
├── 5 个核心场景
├── contains + no-error 评估器
├── 基础 Mock 配置
└── 简单报告

阶段 2: 基本覆盖 (1 周)
├── 20+ 场景覆盖正常/边界/异常
├── 添加 json-valid, language-check
├── 完整 Mock 数据
└── CI/CD 集成

阶段 3: 生产就绪 (2-4 周)
├── 50+ 场景全面覆盖
├── 自定义评估器
├── 真实 API 冒烟测试
├── 指标追踪和趋势分析
└── 反馈循环集成
```

## 常见错误

### 错误 1：场景写得太泛

```json
// ❌ 太泛：无法定位具体问题
{ "name": "代码分析测试", "expected": { "contains": ["分析结果"] } }

// ✅ 具体：失败直接指向问题
{ "name": "冒泡排序解释必须包含时间复杂度 O(n²)", "expected": { "contains": ["O(n²)", "时间复杂度"] } }
```

### 错误 2：只看通过率

通过率 95% 不代表没有问题。如果 5 个失败全部集中在同一个能力上，说明那个能力有严重缺陷。

**正确做法**：按能力维度分析通过率，而不是只看总数。

### 错误 3：评估器阈值不合理

阈值太高（>0.95）：大量误判，团队疲于应对假阳性
阈值太低（<0.6）：漏掉真正的质量问题

**正确做法**：从 0.75 开始，根据实际通过/失败分布调整。

### 错误 4：Mock 数据长期不更新

Mock 数据如果超过一个月没有用真实 API 验证过，很可能已经过时。

**正确做法**：每月用真实 API 运行一次全量测试，对比 Mock 和真实结果。

### 错误 5：忽略失败场景

测试失败后只修复代码，不把失败转化为新的测试场景。

**正确做法**：每个生产环境的失败都应该变成一条新的测试场景，确保同样的问题不会再次发生。
