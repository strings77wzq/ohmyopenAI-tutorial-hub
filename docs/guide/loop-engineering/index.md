# Loop Engineering

Loop Engineering 关注一个核心问题：**Agent 如何在"规划—执行—反思"的循环中保持稳定、可恢复，并最终收敛到正确结果？**

## 为什么需要 Loop Engineering？

单个 Prompt 无法解决复杂工程任务。Agent 工作本质上是一个迭代过程：

```
Plan ──▶ Execute ──▶ Reflect ──▶ Adapt
  ▲                                  │
  └──────────────────────────────────┘
```

如果没有精心设计的 Loop 机制，Agent 会面临三个致命问题：

| 问题 | 表现 | 后果 |
|------|------|------|
| **无限循环** | Agent 反复尝试同一策略，无法收敛 | Token 爆炸，任务永不完成 |
| **过早退出** | 遇到第一个错误就放弃 | 可恢复的临时故障导致整体失败 |
| **目标漂移** | 多次迭代后偏离原始意图 | 产出的代码与需求无关 |

## 核心循环模型

### OODA Loop（观察—判断—决策—行动）

Agent 的规划-执行循环可以映射到经典的 OODA 模型：

```
Observe (观察) ──▶ Orient (判断) ──▶ Decide (决策) ──▶ Act (行动)
     ▲                                                    │
     └────────────────────────────────────────────────────┘
```

- **Observe**: 读取工具输出、测试结果、错误日志
- **Orient**: 对比当前状态与目标状态的差距
- **Decide**: 选择下一步策略（重试 / 换方案 / 询问用户 / 退出）
- **Act**: 执行选定的工具调用

### 三阶段退出机制

每一次 Agent 迭代必须经过三层退出判断：

```
┌─────────────────────────────────────────────────────┐
│                   ITERATION START                    │
├─────────────────────────────────────────────────────┤
│                                                     │
│  L1: TASK COMPLETE?                                 │
│  ├── YES → 验证输出 → EXIT (success)                │
│  └── NO  → continue                                 │
│                                                     │
│  L2: MAKING PROGRESS?                               │
│  ├── YES → continue next iteration                  │
│  └── NO  → different approach / escalate            │
│                                                     │
│  L3: WITHIN BUDGET?                                 │
│  ├── YES → continue                                 │
│  └── NO  → EXIT (graceful degradation)              │
│                                                     │
└─────────────────────────────────────────────────────┘
```

## 错误重试策略

### 指数退避（Exponential Backoff）

对于网络超时、API 限流等可恢复错误：

```
Attempt 1: wait 1s  → fail
Attempt 2: wait 2s  → fail
Attempt 3: wait 4s  → fail
Attempt 4: wait 8s  → fail → ESCALATE
```

### 错误分类与路由

| 错误类型 | 策略 | 最大重试 |
|----------|------|----------|
| 网络超时 (TimeoutError) | 指数退避重试 | 3 次 |
| API 限流 (RateLimitError) | 等待 Retry-After 头 | 3 次 |
| 工具调用格式错误 | 修正参数后重试 | 2 次 |
| 编译/构建错误 | 分析错误 → 修复 → 重试 | 3 次 |
| 权限拒绝 | **立即停止，不重试** | 0 次 |
| 模型幻觉（输出不符合 schema） | 要求重新生成 | 2 次 |

### 重试熔断器（Circuit Breaker）

```
连续失败 > 3 次 → 暂停循环 → 输出根因分析 → 等待人工决策
```

这防止了 Agent 在不可恢复的错误上浪费 Token 和计算资源。

## 反馈循环

### 内部反馈（Agent ↔ 工具）

Agent 的每次工具调用都携带隐式反馈：

```
Agent 调用 read_file("auth.ts")
  → 返回文件内容        ← 成功：继续分析
  → 返回 FileNotFound   ← 失败：修正路径后重试
  → 返回 PermissionDenied ← 失败：立即退出
```

### 外部反馈（Agent ↔ Harness）

Harness 提供结构化的质量反馈：

```
Agent 修改代码
  → Harness 运行测试套件
    → 全部通过   ← 继续下一步
    → 部分失败   ← Agent 分析失败原因，修复代码
    → 构建失败   ← Agent 检查编译错误，修复后重试
```

### 人工反馈（Agent ↔ 用户）

当 Agent 无法自行决策时，Loop 必须暂停并请求人工输入：

- 多个可行方案且无法判断优劣
- 需要安全确认（删除代码、修改 API）
- 连续重试失败超过阈值

## 在不同 Agent 框架中的实现

### OMO (Oh-My-OpenAgent)

OMO 的验证回路是 Loop Engineering 的实践：

```
意图分类 → 任务分发 → Agent 执行 → 验证
                                   │
                          ┌────────┘
                          ▼
                    自验证 (Agent 自己检查)
                    交叉验证 (@oracle 审查)
                    独立验证 (独立实例验证)
                          │
                          ▼
                    通过 → 提交
                    失败 → 循环修复
```

### Claude Code / gstack

工程师通过 `/loop`、`ralph`、`autopilot` 等机制实现不同粒度的 Loop 控制：

- **ralph**: 自引用循环直至任务完成，带验证审查者
- **autopilot**: 从想法到工作代码的完全自主执行
- **ultrawork**: 高吞吐量任务完成的并行执行引擎

## Loop Engineering 与其他维度的关系

```
                    ┌──────────────────┐
                    │  Prompt Engineering│ ← 定义每次迭代的输入格式
                    └────────┬─────────┘
                             │
        ┌────────────────────┼────────────────────┐
        ▼                    ▼                    ▼
┌───────────────┐   ┌───────────────┐   ┌───────────────┐
│Context Eng.   │   │   Tool Use    │   │    Skills     │
│精准上下文注入  │   │ 原子工具调用   │   │ 可复用能力模块 │
└───────┬───────┘   └───────┬───────┘   └───────┬───────┘
        │                   │                   │
        └───────────────────┼───────────────────┘
                            ▼
                  ┌──────────────────┐
                  │   MCP 协议       │ ← 标准化外部接入
                  └────────┬─────────┘
                           │
                           ▼
                  ┌──────────────────┐
                  │  Harness Eng.    │ ← 质量验证反馈
                  └────────┬─────────┘
                           │
                           ▼
                  ┌──────────────────┐
                  │ Loop Engineering │ ← 闭环迭代控制
                  └──────────────────┘
```

Loop Engineering 是所有其他维度的"指挥家"——它决定了何时调用 Prompt、何时注入 Context、何时触发 Harness 验证，以及何时停止并报告结果。

## 设计检查清单

- [ ] 每个循环迭代有明确的终止条件
- [ ] 错误按类型分类，不同类别有不同的重试策略
- [ ] 存在熔断机制，防止无限重试
- [ ] 反馈来自多个来源：工具输出、Harness 测试、用户确认
- [ ] 循环状态可追踪，每次迭代有日志
- [ ] 退出时输出结构化报告（成功 / 部分完成 / 失败 + 原因）

## 练习

为一个"自动修复文档站断链"的 Agent 设计 Loop 策略：

1. 成功标准是什么？（所有链接 200？还需要什么？）
2. 发现一个断链后，Agent 应该执行什么操作序列？
3. 什么情况下 Agent 应该停止并请求人工帮助？
4. 如何防止 Agent 在同一个链接上反复循环？
