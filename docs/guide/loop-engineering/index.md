# Loop Engineering：闭环迭代控制

单个 Prompt 能解决的问题极其有限。当你让 Agent 去"重构一个模块"或"修复生产事故"，它面对的是一个需要多步推理、反复验证、持续调整的过程。**Loop Engineering 就是工程化地设计这个"规划—执行—反思"的闭环，让 Agent 在迭代中保持稳定、可恢复，并最终收敛到正确结果。**

## 为什么 Agent 需要 Loop？

LLM 本质上是无状态的。每次调用都是一个独立的函数：输入 token，输出 token，没有记忆，没有持续性。一个没有 Loop 的 Agent，就像一个失忆的工人——每次你跟他说话，他都忘了之前做了什么。

Loop 为 Agent 提供了两样 LLM 本身不具备的东西：

### 1. 状态（State）

Loop 维护了一个跨迭代的"世界模型"：已经尝试了什么、结果如何、还有哪些未解决的问题。没有 Loop，Agent 在第 5 次迭代时已经不记得第 1 次的尝试结果。

```
Without loop:
  Iter 1: "试试方法 A" → 失败 → （记忆丢失）
  Iter 2: "试试方法 A" → 失败 → （记忆丢失）
  Iter 3: "试试方法 A" → 失败 → ...

With loop:
  Iter 1: "试试方法 A" → 失败 → record("A failed: reason X")
  Iter 2: "试试方法 B" → 失败 → record("B failed: reason Y")
  Iter 3: "试试方法 C" → 成功 → record("C worked")
```

### 2. 收敛（Convergence）

没有 Loop 的 Agent 不知道什么时候该停。它可能：
- 过早退出：遇到第一个错误就放弃，本可以修复的问题被放弃
- 永不停止：反复尝试同一种方法，陷入无限循环
- 目标漂移：多次迭代后偏离原始意图，产出与需求无关的结果

Loop 通过**退出机制**（什么时候停）、**熔断器**（什么时候强制停）和**目标锚定**（每次都回顾原始目标）来保证收敛。

## 三个致命问题

| 问题 | 表现 | 后果 |
|------|------|------|
| **无限循环** | Agent 反复尝试同一策略，无法收敛 | Token 爆炸，任务永不完成 |
| **过早退出** | 遇到第一个错误就放弃 | 可恢复的临时故障导致整体失败 |
| **目标漂移** | 多次迭代后偏离原始意图 | 产出的代码与需求无关 |

## 闭环的核心结构

一个完整的闭环迭代包含四个阶段，遵循 OODA 模型：

```
Plan ──▶ Execute ──▶ Reflect ──▶ Adapt
  ▲                                  │
  └──────────────────────────────────┘
```

更具体地说，每次迭代都经历：

```
┌─────────────────────────────────────────────────┐
│                ITERATION START                   │
├─────────────────────────────────────────────────┤
│                                                 │
│  1. OBSERVE（观察）                               │
│     读取上一步的返回值、错误日志、测试输出           │
│                                                 │
│  2. ORIENT（判断）                                │
│     对比目标与现状，评估进展                        │
│                                                 │
│  3. DECIDE（决策）                                │
│     选择下一步：继续 / 换策略 / 升级 / 停止          │
│                                                 │
│  4. ACT（行动）                                   │
│     执行工具调用，写文件、跑测试、搜索代码            │
│                                                 │
│  EXIT CHECK（退出检查）                            │
│     任务完成？有进展？还在预算内？                   │
│                                                 │
└─────────────────────────────────────────────────┘
```

## 关键设计原则

设计 Agent Loop 时，有几条原则必须牢记：

**1. 每次迭代必须有可观察的输出。** 不可观察的迭代无法判断进展，也无法触发退出条件。

**2. 退出条件必须由外部证据决定，而非 Agent 自我判断。** "我觉得完成了"是不可靠的——需要测试通过、构建成功、链接检查通过等客观信号。

**3. 预算约束必须是硬限制。** Token 预算、时间预算、重试次数——这些不是建议值，到了就必须停。

**4. 失败时必须输出上下文。** 熔断或超时退出时，不能只说"失败了"，必须输出：做了什么、为什么失败、已经尝试了什么、建议下一步怎么做。
