# 重试与熔断

## 概念

Agent 的每次工具调用都可能失败——API 超时、文件不存在、权限不够、格式错误。重试策略决定了"失败后怎么办"；熔断器决定了"什么时候该停下"。这两个机制共同防止 Agent 在不可恢复的错误上浪费资源。

没有重试策略，Agent 会在第一个临时故障时放弃，本可以修复的问题被放弃。没有熔断器，Agent 会在持续失败时无限重试，Token 被耗光却毫无进展。

## 为什么需要错误分类？

不是所有错误都应该重试。把"API 限流"和"权限拒绝"用同一策略处理，会导致 Agent 在真正无解的问题上反复撞墙。

**关键原则：可恢复错误可以重试，不可恢复错误必须立即停止。** 区分标准是"重试会不会改变结果"——权限拒绝重试 100 次也还是拒绝。

## 错误分类与路由

```
工具调用失败
    │
    ├── 可恢复错误（重试可能改变结果）
    │   ├── 瞬时故障：网络超时、API 限流
    │   │   → 指数退避重试，最多 3 次
    │   ├── 状态错误：参数格式错误、文件路径错误
    │   │   → 修正参数后重试，最多 2 次
    │   └── 逻辑错误：编译失败、测试失败
    │       → 分析错误信息 → 修复 → 重试，最多 3 次
    │
    └── 不可恢复错误（重试不会改变结果）
        ├── 权限拒绝：无 sudo、无 API key
        │   → 立即停止，不重试
        ├── 资源不存在：文件/页面/端点确实不存在
        │   → 验证后重试一次，仍失败则停止
        └── 语义错误：模型输出不符合 schema
            → 加强约束后重试，最多 2 次
```

| 错误类型 | 典型触发场景 | 策略 | 最大重试 |
|----------|-------------|------|----------|
| **网络超时** | API 调用、文件下载 | 指数退避重试 | 3 次 |
| **API 限流** | 高频 API 调用 | 等待 Retry-After 头后重试 | 3 次 |
| **工具调用格式错误** | 参数类型不匹配 | 修正参数后重试 | 2 次 |
| **编译/构建错误** | 语法错误、类型错误 | 分析错误信息 → 修复 → 重试 | 3 次 |
| **模型幻觉** | 输出不符合 schema | 要求重新生成，加强约束 | 2 次 |
| **权限拒绝** | 写保护目录、无权限 API | **立即停止，不重试** | 0 次 |
| **资源不存在** | 文件路径错误、API 端点不存在 | 验证路径后重试一次 | 1 次 |

## 指数退避（Exponential Backoff）

对于可恢复的瞬时错误，指数退避是最经典的策略。核心思想：第一次失败后等 1 秒，第二次等 2 秒，第三次等 4 秒——给系统恢复的时间。

```
Attempt 1: wait 1s   → fail (timeout)
Attempt 2: wait 2s   → fail (timeout)
Attempt 3: wait 4s   → fail (timeout)
Attempt 4: wait 8s   → fail → ESCALATE (超过最大重试次数)
```

### 退避实现要点

**基数（Base）：** 初始等待时间不宜太小（建议 ≥ 1s）。太短的等待会对过载的服务雪上加霜——它还在处理上一个请求，你又发了一个。

**上限（Cap）：** 最大等待时间不应超过任务的总超时限制（建议 ≤ 30s）。如果退避时间已经接近任务超时，不如直接放弃。

**抖动（Jitter）：** 在退避时间中加入随机因子（±20%），避免多个 Agent 同时重试造成惊群效应。

```
base_wait = min(initial * (2 ^ attempt), max_wait)
actual_wait = base_wait * (0.8 + random() * 0.4)  // ±20% jitter
```

### 退避策略的适用场景

| 场景 | 是否适用 | 原因 |
|------|---------|------|
| API 限流（429） | ✅ 适用 | 服务临时过载，等一会就好了 |
| 网络超时 | ✅ 适用 | 可能是网络抖动，重试可能成功 |
| 权限拒绝（403） | ❌ 不适用 | 权限不会因为等待而改变 |
| 服务器错误（500） | ⚠️ 谨慎 | 如果是持久性错误，退避只是拖延时间 |
| 参数错误（400） | ❌ 不适用 | 需要修正参数，不是等待 |

## 熔断器（Circuit Breaker）

熔断器是防止级联失败的经典模式。核心思想：当失败次数超过阈值时，立即停止重试，进入"熔断"状态。

```
        ┌──────────┐
        │  CLOSED  │ ← 正常状态：请求正常通过
        └────┬─────┘
             │ 连续失败 ≥ N 次
             ▼
        ┌──────────┐
        │   OPEN   │ ← 熔断状态：立即拒绝所有请求
        └────┬─────┘
             │ 冷却时间过后
             ▼
        ┌──────────┐
        │ HALF-OPEN│ ← 试探状态：允许少量请求通过
        └────┬─────┘
      成功    │    失败
       ▼      │     ▼
    CLOSED    │   OPEN（重置冷却时间）
```

### Agent 场景的熔断触发条件

| 条件 | 阈值建议 | 触发后行为 |
|------|----------|-----------|
| 同一工具调用连续失败 | ≥ 3 次 | 暂停循环，报告根因 |
| 同一类错误在 5 次迭代内重复出现 | ≥ 3 次 | 强制切换策略 |
| Token 消耗速率异常（单次迭代 > 预期 3 倍） | 立即触发 | 输出已完成部分，等待人工决策 |
| Build 连续失败 | ≥ 3 次 | 暂停，输出错误分析报告 |

### 熔断后的行为

熔断不是简单地"停了"。熔断后必须输出结构化的报告：

```
熔断报告应包含：
1. 什么操作失败了（具体的工具调用和参数）
2. 失败的原因（错误类型和错误消息）
3. 已经尝试了哪些方案（已尝试策略列表）
4. 建议的下一步（继续 / 换方案 / 需要人工介入）
```

## 示例：修复编译错误的完整重试流程

**场景 1：可恢复错误——编译失败**

```
Agent 修改了 src/auth.ts
   → npm run build → FAIL (TypeError: undefined is not a function)

[错误分类] 编译/构建错误 → 允许重试，最多 3 次

Attempt 1: 分析错误 → 发现调用了不存在的函数 → grep 找到正确函数名
           → 修复 → npm run build → FAIL (另一个类型错误)

Attempt 2: 分析新错误 → 发现类型导入缺失 → 添加 import
           → 修复 → npm run build → PASS

[熔断器] 未触发（仅 1 次连续失败，未达阈值）
```

**场景 2：不可恢复错误——权限拒绝**

```
Agent 尝试修改 /etc/hosts（需要 sudo）
   → Permission denied

[错误分类] 权限拒绝 → 不允许重试 → 立即停止

[熔断器] 不触发（不是"连续失败"，而是"不可恢复错误"）
Agent 应立即向用户报告：
  - 需要什么权限（sudo）
  - 为什么需要（修改系统文件）
  - 用户如何手动执行（sudo vim /etc/hosts）
```

**场景 3：熔断触发——连续构建失败**

```
Agent 修改了 src/parser.ts
   → npm run build → FAIL (SyntaxError)
   → 修复 → npm run build → FAIL (另一个 SyntaxError)
   → 修复 → npm run build → FAIL (第三个 SyntaxError)

[熔断器] 触发：连续 3 次构建失败

输出熔断报告：
  - 失败操作：npm run build
  - 根因：parser.ts 的语法错误可能来自对语言特性的误解
  - 已尝试：修复了 3 个不同的语法错误
  - 建议：需要人工审查 parser.ts 的修改，可能需要重新设计
```

## 超时策略

超时是熔断器的补充——它处理的是"没有明确失败，但也卡住了"的情况：

| 超时类型 | 建议值 | 触发后行为 |
|----------|--------|-----------|
| 单次工具调用超时 | 30 秒 | 重试（如果可恢复）或跳过 |
| 单次迭代超时 | 5 分钟 | 进入下一次迭代，记录本次未完成 |
| 整个任务超时 | 30 分钟 | 优雅降级：输出已完成部分 |
| 用户无响应超时 | 10 分钟 | 采用默认策略或暂停 |

## 设计检查清单

- [ ] 所有可能的错误类型都有明确的分类（可恢复 vs 不可恢复）
- [ ] 指数退避有基数（≥ 1s）、上限（≤ 30s）和随机抖动（±20%）
- [ ] 熔断器有明确的触发条件（连续失败 ≥ 3 次）和冷却时间
- [ ] 熔断后的输出包含根因分析、已尝试方案、建议下一步
- [ ] 不可恢复错误立即停止，不做无意义重试
- [ ] 超时策略覆盖单次调用、单次迭代、整个任务三个层级
- [ ] 所有退出路径都输出结构化报告（不是简单说"失败了"）

## 练习

为一个"调用 GitHub API 创建 PR"的 Agent 设计错误处理策略：

1. 列出至少 5 种可能发生的错误
2. 为每种错误分类并给出重试策略
3. 什么情况下需要设置熔断器？
4. 熔断后 Agent 应该输出什么给用户？
5. 如何处理"API rate limit exceeded"——立即停止还是退避重试？

## 排错

| 症状 | 可能原因 | 修复 |
|------|----------|------|
| Agent 对同一个权限错误反复重试 | 错误分类缺失"不可恢复"类别 | 增加 PermissionDenied → 0 次重试 |
| 熔断器太敏感，正常波动就触发 | 连续失败阈值太低 | 调高阈值到 5 次 |
| 熔断器太迟钝，浪费了大量 Token 才触发 | 阈值太高或无 Token 监控 | 降低阈值到 3 次或增加 Token 速率检查 |
| 冷却后重试仍然失败 | 根因没有修复（比如 API key 已过期） | 熔断后输出应检查根因是否可自动修复 |
| 退避时间太长，用户等不及 | 基数或上限设置过大 | 降低基数到 1s，上限到 10s |
