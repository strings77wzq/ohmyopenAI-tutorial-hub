# 多源反馈

## 概念

单靠 Agent 自己的判断来评估"我做得怎么样"是不可靠的——这就像让学生自己给自己打分。Agent 存在系统性偏见：确认偏误（倾向于看到支持自己结论的证据）、盲点（无法检测自己不知道的错误）、范围局限（只能看到上下文窗口内的信息）。

多源反馈的核心思想是：**让 Agent 从至少三条独立通道获取信号，交叉验证自己的进展。** 当多个独立来源都指向同一个结论时，Agent 才有信心认为"我真的做对了"。

## 为什么单通道反馈不够？

```
Agent 写了一段代码
   → Agent 自己觉得 "写得不错"
   → 实际：代码有 3 个 bug，测试覆盖率 40%
```

Agent 的自我评估存在系统性偏差：

| 偏差类型 | 表现 | 后果 |
|----------|------|------|
| **确认偏误** | 倾向于看到支持自己结论的证据 | Agent 认为"修好了"但实际没修好 |
| **盲点** | 无法检测自己不知道的错误 | 不知道函数名拼错了（因为 Agent 认为那个拼写是正确的） |
| **范围局限** | 只能看到上下文窗口内的信息 | 修复了 A 文件但破坏了 B 文件 |
| **近因效应** | 最近的操作影响最大 | 忘记了早期引入的问题 |

## 三条反馈通道

```
                          ┌─────────────┐
                          │    Agent    │
                          └──────┬──────┘
                                 │
            ┌────────────────────┼────────────────────┐
            ▼                    ▼                    ▼
   ┌────────────────┐   ┌────────────────┐   ┌────────────────┐
   │   内部反馈      │   │   外部反馈      │   │   人工反馈      │
   │ Agent ↔ 工具    │   │ Agent ↔ Harness│   │ Agent ↔ 用户    │
   └────────┬───────┘   └────────┬───────┘   └────────┬───────┘
            │                    │                    │
            ▼                    ▼                    ▼
   ┌────────────────┐   ┌────────────────┐   ┌────────────────┐
   │ 工具返回值       │   │ 测试/构建/审计  │   │ 确认/否决/修改  │
   │ 文件内容         │   │ Evaluator 评分  │   │ 方向判断        │
   │ 错误消息         │   │ 静态分析结果    │   │ 安全决策        │
   └────────────────┘   └────────────────┘   └────────────────┘
```

### 通道 1：内部反馈（Agent ↔ 工具）

每次工具调用都是一次隐式反馈。这是最快、最廉价的通道——不需要额外基础设施：

```
Agent 调用 read_file("src/auth.ts")
  → 返回 200 行代码       ← 成功：文件存在，继续分析
  → 返回 FileNotFound     ← 失败：路径错误，修正后重试
  → 返回 PermissionDenied ← 失败：权限不够，立即停止
```

**内部反馈的局限：** Agent 只能看到它主动请求的信息。它不知道链接断了，除非它主动调用 link-checker。它不知道测试失败了，除非它主动运行测试。

**设计要点：**
- 在每次迭代的 Observe 阶段，强制读取所有相关输出，不只是工具返回值
- 记录每次工具调用的结果（成功/失败/部分成功），用于 Orient 阶段的趋势分析
- 对于关键操作（修改文件后），强制运行验证工具（测试、构建、lint）

### 通道 2：外部反馈（Agent ↔ Harness）

Harness 提供结构化的、自动化的质量反馈。它的核心价值：**提供 Agent 无法自产的信息。**

```
Agent 修改了文档站的 5 个页面
  → Harness 跑 link-checker
    → 0 个断链 ← 通过，继续
    → 3 个断链 ← 失败，Agent 分析原因并修复

Agent 提交了 PR
  → Harness 跑全套门禁
    → npm test     ← PASS
    → npm run build ← PASS
    → npm run lint  ← FAIL（2 个 frontmatter 缺失）
```

**外部反馈的类型：**

| 反馈类型 | 信息内容 | 适用场景 |
|----------|---------|---------|
| 测试结果 | 通过/失败/跳过，覆盖率 | 代码修改后 |
| 构建状态 | 成功/失败，警告 | 代码修改后 |
| 静态分析 | lint 错误，类型错误 | 代码修改后 |
| 链接检查 | 断链数量和位置 | 文档修改后 |
| 性能指标 | 页面加载时间，bundle 大小 | 前端修改后 |
| 安全审计 | 漏洞数量，依赖风险 | 依赖修改后 |

**关键原则：外部反馈必须在每次关键操作后触发，而不是只在任务结束时。** 等到任务结束才发现问题，返工成本巨大。

### 通道 3：人工反馈（Agent ↔ 用户）

当 Agent 走到决策边界时，必须把控制权交还给用户。人工反馈是最慢但最可靠的通道。

**必须暂停并询问用户的场景：**

| 场景 | 原因 |
|------|------|
| 多个可行方案且 Agent 无法判断优劣 | 需要人类的偏好判断 |
| 涉及安全或权限的决策 | 删除文件、修改 API、访问敏感数据 |
| 连续 3 次重试后仍然失败 | 可能遇到了 Agent 无法解决的问题 |
| 任务范围超出原始指令 | "修这个 bug 需要重构 3 个文件" |
| 需要领域知识的决策 | 业务逻辑、设计偏好、品牌规范 |

**不应询问用户的场景：**

| 场景 | 原因 |
|------|------|
| 纯机械操作 | 格式化代码、更新链接 |
| 已有明确规范的决策 | 按照项目的 lint 规则修改 |
| Agent 有 100% 把握且操作可逆 | git 记录的修改都可以 revert |
| 重复性操作 | 已经确认过一次的模式 |

## 反馈融合：从三通道到决策

三条通道的信号需要融合成一个统一的决策。融合的原则是：**独立信号互相验证，矛盾信号触发升级。**

**场景 1：三通道一致——直接行动**

```
内部反馈: "link-checker 输出 3 个断链"
    +
外部反馈: "npm run build 通过，所以不是配置问题"
    +
人工反馈: （无需 — 修复断链是机械操作）
    ↓
决策: Agent 分析 3 个断链 → 修复 → 重跑 link-checker → 确认通过
```

**场景 2：信号矛盾——升级给人类**

```
内部反馈: "测试全部通过"
    +
外部反馈: "Lighthouse performance 从 92 降到 78"
    +
人工反馈: 需要确认：换新字体导致 LCP 回归 → 用户决定是否接受
    ↓
决策: Agent 暂停，报告性能回归 → 等待用户选择：接受 / 回退字体
```

**场景 3：信号缺失——补全信息**

```
内部反馈: "代码修改完成，语法正确"
    +
外部反馈: （缺失 — 没有运行测试）
    +
人工反馈: （无需）
    ↓
决策: Agent 必须先运行测试，获取外部反馈后再决定下一步
```

## 信噪比：如何让反馈有用

不是所有反馈都同样重要。Agent 需要学会区分"信号"和"噪声"：

| 信号类型 | 信噪比 | 处理方式 |
|----------|--------|---------|
| 测试失败 | 高 | 立即关注，分析失败原因 |
| lint 警告 | 中 | 批量修复，不阻塞主流程 |
| 构建警告 | 低 | 记录但不立即处理 |
| "代码看起来不错" | 极低 | 忽略——这是 Agent 自己的反馈 |

**设计要点：**
- 外部反馈（测试、构建、审计）的权重高于内部反馈（工具返回值）
- 内部反馈的权重高于 Agent 的自我评估
- 当外部反馈和内部反馈矛盾时，以外部反馈为准

## 示例：多源反馈在翻译任务中的应用

为一个"自动翻译英文文档"的 Agent 设计多源反馈：

```
迭代 1:
  O: 翻译完成 5 个章节
  内部反馈: Agent 检查格式一致性 → 通过
  外部反馈: 检查链接有效性 → 3 个链接断了
  决策: 修复断链 → 进入迭代 2

迭代 2:
  O: 断链已修复
  内部反馈: Agent 检查术语一致性 → 发现 2 个术语不一致
  外部反馈: 检查格式 → 通过
  决策: 统一术语 → 进入迭代 3

迭代 3:
  O: 术语已统一
  内部反馈: 格式 + 术语 → 通过
  外部反馈: 格式 + 链接 → 通过
  人工反馈: 需要人工 review 翻译质量（信噪比最低但最可靠的通道）
  决策: 提交人工 review → 等待反馈
```

## 练习

为一个"自动生成 API 文档"的 Agent 设计多源反馈方案：

1. 内部反馈：文档生成完成后 Agent 自己能检查什么？
2. 外部反馈：Harness 能自动验证什么（格式？链接？术语一致性？）
3. 人工反馈：什么情况下需要人工 review 文档质量？
4. 三条通道的反馈如何汇总为一个"是否发布"的决策？
5. 如果内部反馈说"文档质量不错"但外部反馈说"链接有 5 个断了"，Agent 应该怎么做？

## 排错

| 症状 | 可能原因 | 修复 |
|------|----------|------|
| Agent 反复重试但每次都得到相同的外部反馈 | 没有把反馈信息反馈到 Orient 阶段 | 确保每次迭代都对比上一次的反馈变化 |
| 人工反馈通道使用过度 | Agent 在不该问的时候反复询问 | 明确"必须询问"和"不应询问"的边界规则 |
| 外部反馈被忽略 | Agent 只看内部反馈（工具返回值），跳过了 Harness 输出 | 在 Decide 阶段强制检查所有通道 |
| Agent 在信号矛盾时没有升级 | 融合规则缺失，Agent 选择性忽略矛盾信号 | 当内部和外部反馈矛盾时，强制暂停并报告 |
| 反馈太多导致 Agent 无法决策 | 信噪比太低，Agent 被噪声淹没 | 过滤低价值反馈，只关注测试失败和关键警告 |
