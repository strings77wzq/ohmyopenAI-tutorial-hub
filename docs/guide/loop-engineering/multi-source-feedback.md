# 多源反馈

## 概念

单靠 Agent 自己的判断来评估"我做得怎么样"是不可靠的——这就像让学生自己给自己打分。多源反馈的核心思想是：**让 Agent 从至少三条独立通道获取信号，交叉验证自己的进展**。

## 为什么单通道反馈不够？

```
Agent 写了一段代码
   → Agent 自己觉得 "写得不错"
   → 实际：代码有 3 个 bug，测试覆盖率 40%
```

Agent 的自我评估存在系统性偏差：
- **确认偏误**：倾向于看到支持自己结论的证据
- **盲点**：Agent 无法检测自己不知道的错误（不知道函数名拼错了，因为它认为那个拼写是正确的）
- **范围局限**：Agent 只能看到它上下文窗口内的信息

## 三条反馈通道

```
                          ┌─────────────┐
                          │    Agent    │
                          └──────┬──────┘
                                 │
            ┌────────────────────┼────────────────────┐
            ▼                    ▼                    ▼
   ┌────────────────┐   ┌────────────────┐   ┌────────────────┐
   │   内部反馈      │   │   外部反馈      │   │   人工反馈      │
   │ Agent ↔ 工具    │   │ Agent ↔ Harness│   │ Agent ↔ 用户    │
   └────────┬───────┘   └────────┬───────┘   └────────┬───────┘
            │                    │                    │
            ▼                    ▼                    ▼
   ┌────────────────┐   ┌────────────────┐   ┌────────────────┐
   │ 工具返回值       │   │ 测试/构建/审计  │   │ 确认/否决/修改  │
   │ 文件内容         │   │ Evaluator 评分  │   │ 方向判断        │
   │ 错误消息         │   │ Lighthouse 分数 │   │ 安全决策        │
   └────────────────┘   └────────────────┘   └────────────────┘
```

### 通道 1：内部反馈（Agent ↔ 工具）

每次工具调用都是一次隐式反馈：

```
Agent 调用 read_file("src/auth.ts")
  → 返回 200 行代码       ← 成功：文件存在，继续分析
  → 返回 FileNotFound     ← 失败：路径错误，修正后重试
  → 返回 PermissionDenied ← 失败：权限不够，立即停止
```

内部反馈是最快、最廉价的通道——不需要额外基础设施。但它也是最容易产生盲点的通道，因为 Agent 只能看到它主动请求的信息。

### 通道 2：外部反馈（Agent ↔ Harness）

Harness 提供结构化的、自动化的质量反馈：

```
Agent 修改了文档站的 5 个页面
  → Harness 跑 link-checker
    → 0 个断链 ← 通过，继续
    → 3 个断链 ← 失败，Agent 分析原因并修复

Agent 提交了 PR
  → Harness 跑全套门禁
    → npm test     ← PASS
    → npm run build ← PASS
    → npm run lint  ← FAIL（2 个 frontmatter 缺失）
```

外部反馈的核心价值：**它提供了 Agent 无法自产的信息**。Agent 不知道链接断了，除非 link-checker 告诉它。

### 通道 3：人工反馈（Agent ↔ 用户）

当 Agent 走到决策边界时，必须把控制权交还给用户：

**必须暂停并询问用户的场景：**
- 多个可行方案且 Agent 无法判断优劣
- 涉及安全或权限的决策（删除文件、修改 API、访问敏感数据）
- 连续 3 次重试后仍然失败
- 任务范围超出原始指令（Agent 发现"修这个 bug 需要重构 3 个文件"）

**不应询问用户的场景：**
- 纯机械操作（格式化代码、更新链接）
- 已有明确规范的决策（按照项目的 lint 规则修改）
- Agent 有 100% 把握且操作可逆（git 记录的修改都可以 revert）

## 反馈融合：从三通道到决策

```
内部反馈: "link-checker 输出 3 个断链"
    +
外部反馈: "npm run build 通过，所以不是配置问题"
    +
人工反馈: （无需 — 修复断链是机械操作）
    ↓
决策: Agent 分析 3 个断链 → 修复 → 重跑 link-checker → 确认通过
```

```
内部反馈: "测试全部通过"
    +
外部反馈: "Lighthouse performance 从 92 降到 78"
    +
人工反馈: 需要确认：换新字体导致 LCP 回归 → 用户决定是否接受
    ↓
决策: Agent 暂停，报告性能回归 → 等待用户选择：接受 / 回退字体
```

## 示例：多源反馈在 golem 中的实践

golem 的验证回路是三层反馈的工程实现：

```
                     ┌──────────────────┐
                     │   意图分类        │
                     └────────┬─────────┘
                              │
                     ┌────────▼─────────┐
                     │   任务分发        │
                     └────────┬─────────┘
                              │
                     ┌────────▼─────────┐
                     │   Agent 执行      │
                     └────────┬─────────┘
                              │
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
     ┌────────────┐  ┌────────────┐  ┌────────────┐
     │  自验证     │  │  @oracle   │  │ 独立验证    │
     │ (内部反馈)  │  │ 审查       │  │ (外部反馈)  │
     │            │  │ (人工反馈)  │  │            │
     └─────┬──────┘  └─────┬──────┘  └─────┬──────┘
           │               │               │
           └───────────────┼───────────────┘
                           ▼
                   ┌──────────────┐
                   │ 通过 → 提交   │
                   │ 失败 → 循环   │
                   └──────────────┘
```

## 练习

为一个"自动翻译英文文档"的 Agent 设计多源反馈方案：

1. 内部反馈：翻译完成后 Agent 自己能检查什么？
2. 外部反馈：Harness 能自动验证什么（格式？链接？术语一致性？）
3. 人工反馈：什么情况下需要人工 review 翻译质量？
4. 三条通道的反馈如何汇总为一个"是否发布"的决策？

## 排错

| 症状 | 可能原因 | 修复 |
|------|----------|------|
| Agent 反复重试但每次都得到相同的外部反馈 | 没有把反馈信息反馈到 Orient 阶段 | 确保每次迭代都对比上一次的反馈变化 |
| 人工反馈通道使用过度 | Agent 在不该问的时候反复询问 | 明确"必须询问"和"不应询问"的边界规则 |
| 外部反馈被忽略 | Agent 只看内部反馈（工具返回值），跳过了 Harness 输出 | 在 Decide 阶段强制检查所有通道 |
