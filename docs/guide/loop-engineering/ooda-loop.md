# OODA Loop 与退出机制

## 概念

OODA Loop 是军事战略家 John Boyd 提出的决策模型：**Observe（观察）→ Orient（判断）→ Decide（决策）→ Act（行动）**。Agent 的每次迭代天然符合这个循环。

## 为什么 Agent 需要 OODA？

没有结构化循环的 Agent 本质上是在"盲飞"——它不知道上一步发生了什么，也不知道当前应该做什么。OODA 提供了每次迭代的四个明确步骤：

```
Observe (观察) ──▶ Orient (判断) ──▶ Decide (决策) ──▶ Act (行动)
     ▲                                                    │
     └────────────────────────────────────────────────────┘
```

### 每一步的具体含义

- **Observe**：读取工具调用的返回值、测试输出、错误日志、文件内容。这一步的核心问题是"现在实际发生了什么？"
- **Orient**：把观察到的结果与目标做对比。差距在哪？上一步的假设是否正确？当前状态离完成还有多远？
- **Decide**：选择下一步做什么。选项包括：继续当前策略、换一个方案、回退到上一个 checkpoint、询问用户、或者声明任务完成。
- **Act**：执行选定的工具调用（写文件、跑测试、搜索代码等）。

## 三阶段退出机制

每一次 Agent 迭代必须经过三层退出判断：

```
┌─────────────────────────────────────────────────────┐
│                   ITERATION START                    │
├─────────────────────────────────────────────────────┤
│                                                     │
│  L1: TASK COMPLETE?                                 │
│  ├── YES → 验证输出 → EXIT (success)                │
│  └── NO  → continue                                 │
│                                                     │
│  L2: MAKING PROGRESS?                               │
│  ├── YES → continue next iteration                  │
│  └── NO  → different approach / escalate            │
│                                                     │
│  L3: WITHIN BUDGET?                                 │
│  ├── YES → continue                                 │
│  └── NO  → EXIT (graceful degradation)              │
│                                                     │
└─────────────────────────────────────────────────────┘
```

### L1：任务是否完成？

这是最高优先级的检查。但"完成"的定义需要明确：

| 任务类型 | 完成标准 |
|----------|----------|
| 写代码 | 所有测试通过 + 构建成功 + 代码审查通过 |
| 修 bug | 复现步骤不再触发 bug + 回归测试通过 |
| 文档更新 | 链接检查通过 + 拼写检查通过 |
| 部署 | 健康检查返回 200 + 关键路径 smoke test 通过 |

关键原则：**L1 不能只靠 Agent 自己判断"我觉得完成了"**。必须有外部证据（测试结果、构建日志、链接检查输出）。

### L2：是否有进展？

进展的判断需要量化指标，而不是主观感觉：

| 进展指标 | 信号 |
|----------|------|
| 测试通过率 | 上次 3/10 → 这次 6/10 |
| 断链数 | 上次 15 个 → 这次 8 个 |
| 构建状态 | 上次失败 → 这次通过 |
| diff 大小 | 上次 +200 行 → 这次 +50 行 |

如果连续 2 次迭代在所有指标上都无进展，Agent 应该换策略，而不是继续用同一种方法尝试。

### L3：是否还在预算内？

预算是硬约束：

- **Token 预算**：单次任务消耗的 Token 不能超过预设上限
- **时间预算**：如果 CI 超时或用户不在了，Agent 不应继续消耗资源
- **重试预算**：同一操作的连续失败次数不能超过阈值

L3 触发的退出应该是"优雅降级"——输出已完成的部分、未完成的原因、以及后续步骤建议。

## 示例：修复文档站断链

一个"修复 100 个断链"的 Agent 的 OODA 循环：

```
Iteration 1:
  O: link-checker 输出 100 个断链
  O: 分析发现 60 个是路径拼写错误，40 个是页面不存在
  D: 先修路径拼写错误（批量化，一次修 20 个）
  A: sed 批量替换 → 提交 → 跑 link-checker

Iteration 2:
  O: link-checker 输出 40 个断链（60 个已修复）
  O: 40 个全部是页面不存在 → 需要建立新页面或更新引用
  D: 逐个分析目标是否应存在，新建 5 个、更新引用 35 个
  A: 新建 5 个页面 + 更新 35 个链接 → 提交 → 跑 link-checker

Iteration 3:
  O: link-checker 输出 0 个断链
  L1: 所有链接 2xx → EXIT (success)
```

## 练习

为一个"自动生成 API 文档"的 Agent 设计 OODA 循环：

1. Observe 阶段应该检查哪些输出？
2. Orient 阶段的核心对比是什么？
3. 什么信号会让 Agent 在 Decide 阶段选择"询问用户"而不是"继续执行"？
4. L1 的"任务完成"标准怎么定义？

## 排错

| 症状 | 可能原因 | 修复 |
|------|----------|------|
| Agent 在同一个操作上反复循环 | Orient 阶段没有检测到"无进展" | 加强 L2 的量化指标 |
| Agent 过早退出 | L1 条件太宽松（Agent 自己说了算） | 引入外部验证（测试结果、构建日志） |
| Agent 在多个策略间来回切换 | Decide 阶段没有记录已尝试的策略 | 维护"已尝试策略"列表，避免重复 |
| Token 消耗远超预期 | L3 预算检查太晚触发 | 每次迭代开始时预测 Token 消耗，提前告警 |
