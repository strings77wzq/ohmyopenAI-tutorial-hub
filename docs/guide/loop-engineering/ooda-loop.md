# OODA Loop 与退出机制

## 概念

OODA Loop 是军事战略家 John Boyd 提出的决策模型：**Observe（观察）→ Orient（判断）→ Decide（决策）→ Act（行动）**。Agent 的每次迭代天然符合这个循环——从环境中获取信息，分析当前状态，选择下一步行动，然后执行。

但天然符合不等于设计合理。没有结构化的 OODA，Agent 会在"盲飞"：它不知道上一步发生了什么，不知道当前应该做什么，也不知道什么时候该停。

## 为什么 Agent 需要 OODA？

LLM 是无状态的。每次调用都是一个独立的函数，没有记忆，没有持续性。OODA 为 Agent 提供了每次迭代的四个明确步骤，解决了三个核心问题：

| 问题 | OODA 如何解决 |
|------|--------------|
| "上一步发生了什么？" | Observe：明确收集上一步的所有输出 |
| "现在该做什么？" | Orient + Decide：基于当前状态选择最优行动 |
| "什么时候该停？" | Orient：每次迭代都评估是否还有必要继续 |

没有 OODA，Agent 的迭代就像没有仪表盘的飞行——它可能在原地打转，可能已经偏航，可能燃料耗尽还在飞。

## 四阶段详细拆解

### Observe（观察）

**核心问题："现在实际发生了什么？"**

Observe 不是"看一眼"，而是系统性地收集上一步的所有信号：

```
Observe 收集什么：
├── 工具调用返回值（成功/失败/部分成功）
├── 错误日志和堆栈信息
├── 测试输出（通过/失败/跳过）
├── 构建状态（成功/失败/警告）
├── 文件内容变化（diff）
└── 外部系统状态（API 响应、数据库状态）
```

**关键陷阱：** Agent 可能只看它主动请求的信息，忽略"意外信号"。比如修复了一个 bug 但引入了另一个——如果只检查修复目标的测试，会错过回归。

**设计要点：**
- 每次迭代开始时，强制读取所有相关输出，不只是工具返回值
- 记录上一次 Observe 的结果，以便 Orient 阶段做对比
- 对于长任务，维护一个"观察历史"，防止 Agent 忘记早期发现

### Orient（判断）

**核心问题："距离目标还有多远？上一步的假设正确吗？"**

Orient 是 OODA 中最关键的阶段——它把观察到的原始信息转化为有意义的判断：

```
Orient 的三个子步骤：
1. 对比：当前状态 vs 目标状态
   → "测试通过率从 3/10 提升到 6/10"（有进展）
   → "测试通过率从 3/10 降到 2/10"（退步了）

2. 归因：为什么发生了这个变化？
   → "因为我修复了登录模块的类型错误"
   → "因为重构引入了新的循环依赖"

3. 预测：按当前趋势，还需要几次迭代？
   → "按每次 +3 个测试，还需 2 次迭代"
   → "如果继续退步，需要换策略"
```

**Orient 的判断直接驱动退出决策：**

| Orient 结论 | 退出行动 |
|-------------|---------|
| 任务已完成（所有目标达成） | → L1 退出（成功） |
| 连续 2 次迭代无进展 | → 切换策略或升级 |
| 预算即将耗尽 | → 准备 L3 退出 |
| 任务范围超出预期 | → 暂停，等待用户确认 |

### Decide（决策）

**核心问题："下一步做什么？"**

基于 Orient 的判断，Decide 需要从多个选项中选择：

```
Decide 的选项空间：
├── 继续当前策略（如果 Orient 显示有进展）
├── 切换策略（如果 Orient 显示无进展）
├── 回退到上一个 checkpoint（如果引入了回归）
├── 询问用户（如果遇到决策边界）
├── 升级/报告（如果超出能力范围）
└── 声称完成（如果 Orient 显示目标达成 + 外部验证通过）
```

**关键原则：** Decide 必须维护"已尝试策略"列表，避免在同一策略上反复循环。

```
已尝试策略记录：
Iter 1: 尝试 sed 批量替换 → 成功修复 60/100
Iter 2: 尝试逐个分析 → 成功修复 35/100
Iter 3: 剩余 5 个需要新建页面 → 新建页面

✅ 每次迭代都用不同的策略
❌ 反复用 sed 替换同一个文件（没有策略变化）
```

### Act（行动）

**核心问题："具体执行什么工具调用？"**

Act 阶段将 Decide 的决策转化为具体的工具调用。这是 OODA 中唯一"改变世界"的阶段。

**Act 的设计要点：**
- 每次只执行一个原子操作（一个工具调用），而不是一次修改多个文件
- 每个操作都要有可观察的结果（返回值、测试输出）
- 操作完成后立即进入下一轮 Observe

## 三阶段退出机制

每次迭代必须经过三层退出判断——这是防止无限循环和过早退出的核心机制：

```
┌─────────────────────────────────────────────────────┐
│                   ITERATION START                    │
├─────────────────────────────────────────────────────┤
│                                                     │
│  L1: TASK COMPLETE?                                 │
│  ├── YES → 验证输出 → EXIT (success)                │
│  └── NO  → continue                                 │
│                                                     │
│  L2: MAKING PROGRESS?                               │
│  ├── YES → continue next iteration                  │
│  └── NO  → different approach / escalate            │
│                                                     │
│  L3: WITHIN BUDGET?                                 │
│  ├── YES → continue                                 │
│  └── NO  → EXIT (graceful degradation)              │
│                                                     │
└─────────────────────────────────────────────────────┘
```

### L1：任务是否完成？

这是最高优先级的检查。但"完成"的定义必须明确，且不能只靠 Agent 自己判断：

| 任务类型 | 完成标准 | 验证方式 |
|----------|---------|---------|
| 写代码 | 所有测试通过 + 构建成功 | 运行 `npm test` + `npm run build` |
| 修 bug | 复现步骤不再触发 bug | 运行复现脚本 + 回归测试 |
| 文档更新 | 链接检查通过 + 拼写检查通过 | 运行 link-checker + spell-checker |
| 部署 | 健康检查返回 200 + smoke test 通过 | curl health endpoint + 运行 smoke test |

**关键原则：L1 不能只靠 Agent 自己说"我觉得完成了"。必须有外部证据（测试结果、构建日志、检查输出）。**

### L2：是否有进展？

进展需要量化指标，而不是主观感觉：

| 进展指标 | 信号示例 | 判断 |
|----------|---------|------|
| 测试通过率 | 3/10 → 6/10 | 有进展 |
| 断链数 | 15 → 8 | 有进展 |
| 构建状态 | 失败 → 通过 | 有进展 |
| diff 大小 | +200 行 → +50 行 | 有进展（改动收敛） |
| 测试通过率 | 6/10 → 6/10 | 无进展 |
| 错误数量 | 3 → 3 | 无进展 |

**关键规则：如果连续 2 次迭代在所有指标上都无进展，Agent 必须换策略，而不是继续用同一种方法尝试。**

### L3：是否还在预算内？

预算是硬约束，不是建议值：

| 预算类型 | 建议上限 | 触发后行为 |
|----------|---------|-----------|
| Token 预算 | 单次任务 ≤ 100K tokens | 输出已完成部分 + 未完成原因 |
| 时间预算 | 单次任务 ≤ 30 分钟 | 输出已完成部分 + 继续执行的建议 |
| 重试预算 | 同一操作 ≤ 3 次连续失败 | 输出根因分析 + 建议替代方案 |
| 迭代预算 | 单次任务 ≤ 20 次迭代 | 输出进展总结 + 剩余工作量评估 |

**L3 触发的退出应该是"优雅降级"——输出已完成的部分、未完成的原因、以及后续步骤建议。** 不是简单地说"超时了"。

## 目标漂移（Goal Drift）

目标漂移是 Loop 中最隐蔽的问题——Agent 在多次迭代后逐渐偏离原始意图：

```
原始目标："修复登录页面的密码重置 bug"

迭代 5："密码重置的邮件模板需要优化"
迭代 8："邮件模板的 CSS 需要响应式适配"
迭代 12："响应式适配需要重构整个布局组件"

结果：Agent 在重构布局，而密码重置 bug 从未修复
```

### 目标漂移的原因

1. **上下文窗口被中间产物占满**：Agent 的注意力被最近的操作吸引，忘了最初的目标
2. **Orient 阶段只看局部进展**：每次迭代都"有进展"（CSS 优化了），但整体目标没推进
3. **没有"目标锚定"机制**：没有地方记录原始目标，也没有地方检查是否偏离

### 防止目标漂移

```
每次迭代的 Orient 阶段强制执行：
1. 重读原始目标（从任务描述中提取）
2. 对比当前工作 vs 原始目标
3. 如果偏离 → 回退到与原始目标直接相关的任务
4. 记录偏离历史，防止下次再偏
```

**设计要点：**
- 在任务开始时提取并保存"目标锚点"（原始需求的简短描述）
- 每次迭代的 Orient 阶段强制检查：当前工作是否直接服务于目标锚点？
- 如果 Agent 发现需要做的事情超出原始目标范围，必须暂停并询问用户

## 示例：修复文档站断链

```
原始目标：修复 100 个断链

Iteration 1:
  O: link-checker 输出 100 个断链
  O: 分析发现 60 个是路径拼写错误，40 个是页面不存在
  D: 先修路径拼写错误（批量化，一次修 20 个）
  A: sed 批量替换 → 提交 → 跑 link-checker

Iteration 2:
  O: link-checker 输出 40 个断链（60 个已修复）
  O: 40 个全部是页面不存在 → 需要建立新页面或更新引用
  D: 逐个分析目标是否应存在，新建 5 个、更新引用 35 个
  A: 新建 5 个页面 + 更新 35 个链接 → 提交 → 跑 link-checker

Iteration 3:
  O: link-checker 输出 0 个断链
  O: L1 检查 → 所有链接返回 2xx
  L1: 任务完成 → EXIT (success)
```

**注意每次迭代的 Orient 阶段都做了什么：**
1. 读取 link-checker 输出（Observe）
2. 对比上次结果（40 vs 100）（Orient）
3. 分析剩余错误的类型（Orient）
4. 选择最优策略（Decide）

## 练习

为一个"自动生成 API 文档"的 Agent 设计 OODA 循环：

1. Observe 阶段应该检查哪些输出？
2. Orient 阶段的核心对比是什么？
3. 什么信号会让 Agent 在 Decide 阶段选择"询问用户"而不是"继续执行"？
4. L1 的"任务完成"标准怎么定义？
5. 如何防止目标漂移（比如 Agent 开始优化文档的 CSS 而不是生成内容）？

## 排错

| 症状 | 可能原因 | 修复 |
|------|----------|------|
| Agent 在同一个操作上反复循环 | Orient 阶段没有检测到"无进展" | 加强 L2 的量化指标，连续 2 次无进展强制换策略 |
| Agent 过早退出 | L1 条件太宽松（Agent 自己说了算） | 引入外部验证（测试结果、构建日志） |
| Agent 在多个策略间来回切换 | Decide 阶段没有记录已尝试的策略 | 维护"已尝试策略"列表，避免重复 |
| Token 消耗远超预期 | L3 预算检查太晚触发 | 每次迭代开始时预测 Token 消耗，提前告警 |
| Agent 做了很多工作但偏离目标 | 目标漂移——Orient 没有检查目标锚点 | 每次 Orient 强制重读原始目标并对比 |
