# 部署与安全

> Agent 系统上线前要回答两个问题：它能否稳定工作，以及它能否在失败时保持可控。

## 为什么 Agent 部署比传统应用更难

传统 Web 应用的部署是确定性的——同样的代码、同样的输入，产生同样的输出。Agent 系统打破了这个假设：

| 维度 | 传统应用 | Agent 系统 |
|------|---------|-----------|
| 输出确定性 | 相同输入 → 相同输出 | 相同输入 → 概率性输出 |
| 依赖外部服务 | 数据库、缓存（可控） | LLM API（不可控、会变化） |
| 失败模式 | 崩溃、超时、500 | 输出质量下降、幻觉、循环、token 耗尽 |
| 回滚复杂度 | 代码回滚即可 | 代码 + Prompt + 模型版本 + 上下文策略 |
| 安全边界 | 明确的用户输入/输出 | Agent 可自主读写文件、调用 API、执行命令 |
| 成本模型 | 固定（服务器） | 弹性（按 token 计费，难以预测） |

这意味着部署 Agent 系统需要一套专门的工程实践，而不仅仅是"把它跑起来"。

## 部署生命周期

```
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│  开发    │───▶│  预检    │───▶│  部署    │───▶│  监控    │
│  (Dev)   │    │ (Pre-flight)│  │ (Deploy) │    │ (Monitor)│
└──────────┘    └──────────┘    └──────────┘    └──────────┘
                      │                               │
                      │         ┌──────────┐          │
                      └────────▶│  回滚    │◀─────────┘
                                │ (Rollback)│
                                └──────────┘
```

每个阶段都有 Agent 特有的挑战：

### 1. 开发阶段

- Prompt 变更可能悄悄破坏下游功能
- 模型提供商的更新可能改变输出格式
- 多 Agent 协作时，一个 Agent 的行为变化会影响整个链路

### 2. 预检阶段

预检（Pre-flight Check）是部署前的自动化质量门禁：

```
预检清单:
  ✓ 构建通过（npm run docs:build）
  ✓ 链接检查通过（npm run docs:check-links）
  ✓ 示例代码可运行
  ✓ 权限边界已定义且经过测试
  ✓ 密钥不进入仓库或 Agent 上下文
  ✓ 失败路径有用户可理解的错误消息
  ✓ 回滚路径已验证
  ✓ 性能基线已建立（构建时间、页面加载）
  ✓ 安全扫描通过（密钥泄露、依赖漏洞）
```

### 3. 部署阶段

- 灰度发布：先部署到小比例流量，验证无异常后再全量
- 分支预览：每个 PR 自动生成预览环境，合并前可人工验证
- 原子部署：一次部署要么全部成功，要么全部回滚，不出现半成品状态

### 4. 监控阶段

部署后观测才刚刚开始——详见[观测与回滚](./observability-rollback)。

### 5. 回滚阶段

当监控发现问题时，需要快速回滚到上一个可用状态。

## 发布前安全检查清单

部署 Agent 系统时，安全检查不是可选项，而是必须项：

### 权限检查

| 检查项 | 状态 | 说明 |
|--------|------|------|
| Agent 能访问的目录已限制 | ☐ | 白名单机制，最小权限 |
| Agent 不能执行危险命令 | ☐ | rm -rf、sudo、chmod 等已禁止 |
| 网络访问范围已限定 | ☐ | 只允许访问必要的域名 |
| 写入操作需用户确认 | ☐ | diff 预览 + 手动审批 |
| 删除操作已禁用或需审批 | ☐ | 几乎所有场景都不应允许删除 |

### 密钥检查

| 检查项 | 状态 | 说明 |
|--------|------|------|
| .env 文件在 .gitignore 中 | ☐ | 防止意外提交 |
| 密钥通过环境变量注入 | ☐ | 不硬编码在代码中 |
| CI/CD 使用 Secrets Manager | ☐ | GitHub Secrets 或 Vault |
| Agent 无法读取密钥目录 | ☐ | 权限隔离 |
| 日志中不包含密钥 | ☐ | 输出脱敏 |

### 观测检查

| 检查项 | 状态 | 说明 |
|--------|------|------|
| 构建日志可追溯 | ☐ | 每次构建的完整日志 |
| 关键路径 smoke test | ☐ | 部署后立即验证核心功能 |
| 用户反馈入口可用 | ☐ | Issue tracker 或反馈表单 |
| 回滚路径已验证 | ☐ | 至少手动执行过一次回滚 |

## 常见部署失败模式

### 模式 1：静默质量退化

```
症状: 部署成功，构建通过，但用户反馈内容质量下降
原因: 模型提供商更新了模型，Prompt 不再产生预期输出
检测: 回归测试 + 输出质量监控
修复: 锁定模型版本，或调整 Prompt 适配新模型
```

### 模式 2：成本失控

```
症状: 月度 token 费用突然翻倍
原因: Agent 陷入循环、Prompt 膨胀、或新功能引入了高 token 消耗路径
检测: token 用量监控 + 单次调用上限
修复: 设置 token 预算、优化 Prompt、增加循环退出条件
```

### 模式 3：权限逃逸

```
症状: Agent 意外读取了敏感文件或执行了未授权命令
原因: 权限白名单有漏洞（如路径穿越）、或使用了黑名单但未覆盖所有危险操作
检测: 操作审计日志 + 权限拒绝告警
修复: 改用白名单机制、路径规范化检查
```

### 模式 4：跨 Agent 泄露

```
症状: Agent B 的上下文中出现了 Agent A 处理过的敏感信息
原因: 共享上下文摘要未脱敏、或 Agent 间通信未隔离
检测: 上下文审计 + 敏感信息扫描
修复: Agent 间通信加密、摘要脱敏、上下文隔离
```

## 部署决策矩阵

面对部署问题时，使用这个矩阵决定行动：

```
              影响范围小              影响范围大
            ┌─────────────────┬─────────────────┐
严重程度低  │  前滚修复        │  前滚修复 +     │
            │  (hotfix)       │  加强监控       │
            ├─────────────────┼─────────────────┤
严重程度高  │  前滚修复        │  立即回滚       │
            │  (快速修复)     │  + 事后分析     │
            └─────────────────┴─────────────────┘
```

- **前滚修复（Hotfix）**：问题小，不值得回滚，直接修复并部署新版本
- **立即回滚**：问题严重或影响范围大，先恢复到上一个可用版本，再排查根因

## 练习

为一个"自动修复文档断链"的 Agent 系统设计部署方案：

1. 预检阶段需要哪些自动化检查？
2. 权限模型应该允许哪些操作？禁止哪些？
3. 部署后如何验证修复效果？
4. 如果 Agent 误删了正常链接，回滚流程是什么？
5. 如何防止 Agent 在修复过程中引入新的问题？

## 排错

| 症状 | 可能原因 | 修复 |
|------|----------|------|
| 部署成功但页面白屏 | base 路径配置错误、JS bundle 加载失败 | 检查 VitePress base 配置，立即 revert |
| 部署后旧版本缓存未清除 | CDN 缓存、GitHub Pages 部署延迟 | 等待 5 分钟，或手动清除 CDN 缓存 |
| 构建通过但链接检查失败 | 部署环境和本地环境的 URL 不同 | smoke test 使用部署后的实际 URL |
| Agent 部署后消耗 token 异常 | Prompt 膨胀或 Agent 陷入循环 | 检查 token 用量日志，设置调用上限 |
