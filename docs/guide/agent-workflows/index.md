# Agent 工作流编排

## 概念

稳定的 Agent 工作流不是"让模型一次性解决所有问题"，而是把意图、上下文、工具和验证拆成可恢复的步骤。工作流是 Agent 从接收任务到交付结果之间的所有决策、操作和检查的结构化序列。

## 为什么需要工作流？

一个 Agent 可以直接读文件、写代码、跑测试。但当任务变复杂时，"即兴执行"会出现三个致命问题：

```
即兴执行的典型崩塌路径:

用户: "给这个项目加一个用户认证模块"

Agent 的即兴行为:
  1. 直接开始写代码（没有读现有架构）
  2. 用了项目里不存在的库（没有检查 package.json）
  3. 写完了发现和现有路由冲突（没有验证集成）
  4. 用户问"测试呢？"→ Agent 开始补测试（但代码结构已经错了）

结果: 3 小时后代码不能用，需要全部重写
```

工作流解决的正是这个问题——通过**预定义的步骤序列**和**每一步的验证检查**，让 Agent 的行为可预测、可重复、可恢复。

## 工作流 vs 即兴执行

| 维度 | 即兴执行 | 工作流 |
|------|----------|--------|
| 路径 | 不确定——模型每一步现场决策 | 预定义——步骤和顺序提前确定 |
| 可预测性 | 低——同样任务可能得到不同结果 | 高——相同输入产生相同输出序列 |
| 错误发现 | 晚——写完才发现方向错了 | 早——每一步有验证检查 |
| 可恢复性 | 差——失败后不知道从哪里重来 | 好——每一步有明确的输入输出状态 |
| 适用场景 | 探索性任务、头脑风暴 | 生产任务、需要交付的工程工作 |

关键洞察：**即兴执行不是"坏的"工作流，而是"没有显式化"的工作流。** 模型仍然在做决策——只是这些决策没有被记录、检查和复用。工作流编排的本质是把这些隐式决策显式化。

## Agent 工作流的核心组件

一个完整的工作流由五个组件构成：

```
┌─────────────────────────────────────────────────┐
│                  Agent 工作流                     │
├─────────┬─────────┬─────────┬──────────┬────────┤
│  意图    │  上下文  │  计划   │   执行    │  验证  │
│ (Intent) │(Context)│ (Plan)  │ (Execute) │(Verify)│
├─────────┼─────────┼─────────┼──────────┼────────┤
│ 用户目标 │ 项目文件 │ 任务分解 │ 工具调用  │ 测试   │
│ 验收标准 │ 文档    │ 依赖分析 │ 代码修改  │ 构建   │
│ 范围约束 │ 历史决策 │ 优先级  │ 文件操作  │ 链接   │
│         │ API 文档 │ 风险点  │ 外部调用  │ 视觉   │
└─────────┴─────────┴─────────┴──────────┴────────┘
         │                                        │
         └──────── 每一步的输出是下一步的输入 ────────┘
```

- **意图（Intent）**：明确用户想要什么、验收标准是什么、哪些不在范围内。跳过这一步是最常见的错误——Agent 开始工作后才发现理解错了需求。
- **上下文（Context）**：读取项目文件、官方文档、历史决策。Agent 不是全知的，它需要在每一步获取足够的信息来做出正确决策。
- **计划（Plan）**：把大任务拆成可验证的小任务。好的计划让每一步都可以独立验证，失败后可以从失败点重来。
- **执行（Execute）**：保持 diff 小，遵守项目约定。每一步执行后记录状态。
- **验证（Verify）**：构建、测试、链接检查、视觉检查。没有验证的执行等于没有完成。

## 编排检查清单

在设计任何 Agent 工作流时，逐项检查：

```
[ ] 每一步都有明确的输入和输出
[ ] 工具调用有权限边界（Agent 不能访问它不需要的东西）
[ ] 失败后能恢复或回滚（知道从哪里重来）
[ ] 关键行为有构建验证或测试检查
[ ] 最终报告包含证据，不只描述"已完成"
[ ] 步骤之间的依赖关系是 DAG（没有循环）
[ ] 有超时和退出条件（不会无限循环）
```

## 基础闭环

所有 Agent 工作流都可以归结为一个六步闭环：

1. **明确目标**：写下用户意图、范围和验收标准。
2. **读取上下文**：优先读取本地项目文件和官方文档，而不是依赖模型记忆。
3. **制定计划**：拆成可验证的小任务，标注依赖关系。
4. **执行变更**：保持 diff 小，遵守项目约定。
5. **验证结果**：构建、测试、链接检查、视觉检查。
6. **记录状态**：更新任务清单和剩余风险。

这个闭环可以递归——每一步内部又可以展开成一个子闭环。关键是：**每次递归都要有明确的验证出口，否则子闭环会无限展开。**

## 常见反模式

### 反模式 1：跳过意图直接执行

```
✗ 用户: "加个缓存"
  Agent 立刻开始写 Redis 代码

✓ 用户: "加个缓存"
  Agent: "缓存什么数据？用内存还是 Redis？过期策略是什么？"
  用户: "用户配置，内存，5 分钟过期"
  Agent: 开始执行
```

### 反模式 2：没有验证就宣称完成

```
✗ Agent: "我已经添加了认证模块"
  → 没有跑测试，没有检查构建

✓ Agent: "我已经添加了认证模块。验证结果:
  - npm test: 12/12 通过
  - npm run build: 成功
  - 手动检查: 登录/登出/Token 刷新 均正常"
```

### 反模式 3：大范围无状态变更

```
✗ Agent 一次性修改 20 个文件，中间没有检查点

✓ Agent 每修改 3-5 个文件就运行一次验证，
  确保之前的变更仍然正确
```

## 练习

为以下任务设计一个 Agent 工作流：

任务："给这个文档站添加一个新的教程模块，包含 4 个子页面"

1. 意图阶段需要收集什么信息？
2. 上下文阶段需要读取哪些文件？
3. 计划阶段怎么拆分任务？哪些可以并行？
4. 验证阶段需要运行哪些检查？
