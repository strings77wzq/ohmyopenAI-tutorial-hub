# 检索与知识

## 概念

检索让 Agent 不必把所有项目知识塞进 prompt，而是在需要时查找最相关的文档、代码和记录。这是工作流中的"按需加载"机制——就像操作系统的虚拟内存，只把当前需要的页面加载到内存中。

## 为什么需要检索？

一个中等规模的项目，所有源代码、API 文档、测试、历史决策可能有几 MB，远超上下文窗口。没有检索，Agent 只能用它"记住"的碎片信息；有了检索，Agent 可以随时查到它需要的任何信息。

检索的本质是**在正确的时间，把正确的信息，以正确的粒度，注入到 Agent 的上下文中。**

## RAG 基础

RAG（Retrieval-Augmented Generation）是检索增强生成的缩写。核心流程：

```
用户查询 → 查询改写 → 检索索引 → 重排序 → Top-K 结果 → 注入 Prompt → 生成回答
```

- **查询改写**：用户的原始查询可能不适合直接检索。比如"认证怎么做的"可以改写成"认证模块的实现文件路径"。
- **检索索引**：把查询和预建的文档索引进行匹配。
- **重排序**：检索返回的候选结果可能有 20-50 条，需要根据相关性排序，取 Top-K。
- **注入 Prompt**：把排序后的结果作为上下文注入到 Agent 的 prompt 中。

## 三种检索策略

### 1. 朴素检索（Naive Retrieval）

把文档切块（每 512 tokens 一块），建立向量索引，用余弦相似度匹配。

**优点**：实现简单，覆盖广
**缺点**：不理解查询意图，可能返回"语义相关但实际无用"的结果
**适用**：项目规模小（<50 个文档），查询模式单一。

### 2. 混合检索（Hybrid Retrieval）

结合关键词检索（BM25）和向量检索（Embedding）：

```
查询 ─┬─▶ 关键词检索（BM25）───┬─▶ 合并去重 ──▶ 重排序 ──▶ Top-K
      └─▶ 向量检索（Embedding）─┘
```

**优点**：关键词精确匹配（文件名、函数名），向量捕捉语义
**缺点**：需要维护两套索引
**适用**：项目规模中等（50-500 个文档），查询既有精确需求也有模糊需求。

### 3. Agentic 检索（Agentic Retrieval）

Agent 主动决定何时检索、检索什么、如何验证结果：

```
Agent: "我需要了解路由结构"
  → 搜 routing 相关文件
  → 搜 config.ts 中的路由配置
  → 评估结果，过滤旧版本配置
  → 追加检索 middleware 中的路由守卫
  → 整合: 路由结构 = 文件路由 + 中间件守卫 + 配置映射
```

**优点**：最灵活，Agent 可以根据中间结果调整策略
**缺点**：需要多次调用，成本最高
**适用**：项目规模大（>500 个文档），查询复杂，需要多轮推理。

## 知识注入模式

检索到的知识如何注入到 Agent 的上下文中？有三种模式：

### 模式 A：直接注入

把检索结果直接拼接到 prompt 中。简单直接，但结果太多会挤占 prompt 空间。

### 模式 B：摘要注入

把检索结果先压缩成摘要，再注入。节省上下文空间，但摘要可能丢失细节。

### 模式 C：工具化注入

不直接注入知识，而是提供检索工具（`search_files`、`read_file`、`search_code`）让 Agent 按需查询。Agent 精确控制检索范围，按需获取信息，但延迟更高。

**选择依据**：结果少且精确 → 直接注入；结果多且需要压缩 → 摘要注入；需要多轮探索 → 工具化注入。

## 何时检索 vs 何时缓存

```
                    ┌─────────────────┐
                    │   变化频率       │
                    │   高 ──── 低     │
                    ├─────────────────┤
         高 ────────┤  按需检索        │
   访    │         │  每次重新获取     │
   问    │         ├─────────────────┤
   频    │         │  缓存但定期刷新   │
   率    │         ├─────────────────┤
         低 ────────┤  固定注入        │
                    │  初始化时加载一次 │
                    └─────────────────┘
```

**缓存在 prompt 中**：项目架构概览、编码规范、验收标准、固定 API 端点。
**按需检索**：具体文件内容、历史决策记录、第三方库文档、测试结果和错误日志。

## 检索质量标准

| 标准 | 说明 | 不合格的示例 |
|------|------|-------------|
| 相关性 | 结果直接支持当前问题 | 搜"路由"返回了"样式"文件 |
| 新鲜度 | 来源没有过期 | 返回了已废弃的 API 文档 |
| 可追踪 | 能回到文件、URL 或提交 | 只给了代码片段，没有文件路径 |
| 小而准 | 摘要足够短，不淹没上下文 | 返回了 5000 tokens 的完整文件 |
| 可验证 | 结论可以被测试或二次读取确认 | 检索结果和实际代码不一致 |

## 与 MCP 的关系

MCP（Model Context Protocol）可以把检索能力包装成 resource 或 tool：

- **Resource**：适合读取稳定资料（如项目 README、架构文档）。Agent 在工作流开始时一次性加载。
- **Tool**：适合带参数的搜索、过滤或聚合（如搜索代码、查询日志）。Agent 在工作流中间按需调用。

选择依据：**信息是静态的且每次都需要 → 用 resource；信息是动态的或只在特定条件下需要 → 用 tool。**

## 练习

为教程站设计一个检索策略：

1. 哪些目录应该被索引？（哪些内容是 Agent 可能需要查询的？）
2. 检索结果最多返回几条？（太多会挤占上下文，太少可能遗漏关键信息）
3. 每条结果需要哪些字段？（标题、路径、摘要、更新时间？）
4. 如何避免返回过期页面或 404 链接？
5. 哪些信息应该缓存在 prompt 中，哪些应该按需检索？
