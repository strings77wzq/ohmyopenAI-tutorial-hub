# 上下文注入策略

## 概念

上下文注入不是"一次性倒入"——那是 Prompt Engineering 的思路。上下文工程的做法是**渐进式披露**：先给摘要，Agent 需要细节时再展开；先给高频信息，低频信息按需加载。

## 为什么需要注入策略？

把 5 层上下文一次性全部注入窗口的结果：
- 窗口前 20% 被高频信息占据，Agent 能有效处理
- 窗口后 80% 是低频碎片，Agent 的注意力密度急剧下降（"lost in the middle" 效应）
- Token 在每次迭代中重复消耗，但大部分内容根本没被用过

## 三种注入模式

```
┌──────────────────────────────────────────────────────────┐
│ 模式 A: 预注入 (Pre-injection)                           │
│ 在 Agent 开始工作前，把最高优先级的信息放入窗口            │
│ 适用：L1 目标层 + L2 项目知识层的摘要                     │
│ 优点：Agent 从一开始就有正确的方向                         │
│ 缺点：占用初始窗口空间                                    │
├──────────────────────────────────────────────────────────┤
│ 模式 B: 懒注入 (Lazy Injection)                          │
│ Agent 需要时通过工具调用获取，类似于按需加载的模块          │
│ 适用：L4 外部知识层（API 文档、库源码）                    │
│ 优点：只在使用时才消耗 Token                              │
│ 缺点：Agent 需要"知道它不知道什么"才能主动查询              │
├──────────────────────────────────────────────────────────┤
│ 模式 C: 触发注入 (Triggered Injection)                   │
│ 当特定条件满足时（构建失败、测试失败），自动注入相关信息      │
│ 适用：L5 操作证据层                                       │
│ 优点：上下文自动跟随系统状态变化                           │
│ 缺点：需要事件监听和条件判断逻辑                           │
└──────────────────────────────────────────────────────────┘
```

## Token 预算分配

以一个 100K Token 的上下文窗口为例：

```
┌─────────────────────────────────────┐
│ L1 目标层          5K  (5%)         │ ← 最高密度：每个字都有用
│ L2 项目知识        20K (20%)        │ ← 缓存不变部分
│ L3 工作状态        15K (15%)        │ ← 每次迭代轮换
│ L4 外部知识        15K (15%)        │ ← 按需加载，用后释放
│ L5 操作证据        5K  (5%)         │ ← 只注入摘要
│ 保留（对话历史等）  40K (40%)        │ ← 留给工具调用结果和对话
└─────────────────────────────────────┘
```

这不是固定模板，不同任务类型有不同的分配：

| 任务类型 | L1 | L2 | L3 | L4 | L5 | 保留 |
|----------|----|----|----|----|----|------|
| 修复 bug | 10% | 10% | 15% | 5% | 20% | 40% |
| 新增功能 | 10% | 25% | 10% | 15% | 5% | 35% |
| 代码审查 | 5% | 15% | 5% | 5% | 20% | 50% |
| 文档编写 | 10% | 15% | 10% | 20% | 5% | 40% |

## 注入顺序

不是所有层同时注入——注入顺序影响 Agent 的注意力分布：

```
Step 1: L1 目标层 (最先注入 — Agent 先看到"要做什么")
Step 2: L2 项目知识层摘要 (注入结构但不注入所有文件)
Step 3: L3 工作状态层 (如果这是一个恢复任务，注入上次的进度)
Step 4: Agent 开始工作 → 按需拉取 L4
Step 5: 工具调用返回 → L5 操作证据自动流入
Step 6: 每次迭代后 → L3 工作状态更新，替换旧版本
```

## 何时用全文 vs 摘要

| 内容 | 策略 | 原因 |
|------|------|------|
| 验收标准 | **全文** | 不可压缩，Agent 必须精确理解 |
| 安全规则 | **全文** | 压缩可能导致漏掉关键约束 |
| 项目架构文档 | 摘要 → 按需全文 | 大部分时候 Agent 只需要知道"在哪" |
| API 文档 | 摘要 → 按需全文 | 只有在实际调用时才需要完整签名 |
| 测试输出 | **摘要** | 只需失败数和关键错误行 |
| 构建日志 | **摘要** | 只需第一个错误，不需要完整堆栈 |

## 示例：为"新增部署文档页"设计注入方案

```
Phase 1: 预注入
  L1: "新增 docs/guide/deployment/observability-rollback.md，概念+步骤+练习"
  L2: VitePress 配置摘要 + 现有 deployment/index.md 的 5 行摘要

Phase 2: Agent 开始工作
  Agent: "我需要看 deployment/index.md 的完整内容和现有页面的结构模板"
  → 懒注入: 读取两个文件

Phase 3: Agent 写完后
  → 触发注入: npm run docs:check-links 的输出
  → 触发注入: npm run docs:check-frontmatter 的输出

Phase 4: 质量门禁通过
  L3 更新: "deployment/observability-rollback.md 已完成，所有检查通过"
```

## 练习

为一个"重构 auth.ts（200 行→拆成 3 个模块）"的任务设计注入策略：

1. 预注入阶段应该包含什么？
2. 懒注入阶段 Agent 最可能请求哪些文件？
3. 触发注入会在什么时候发生？注入什么？
4. 如果 Token 预算被工具输出占满，应该压缩哪一层？

## 排错

| 症状 | 可能原因 | 修复 |
|------|----------|------|
| Agent 频繁读取同一类文件 | 预注入没有给出足够的结构信息 | 在 L2 中增加项目结构摘要 |
| Agent 忽略了验收标准中的细节 | L1 被 L2 的大量文本挤到后面 | L1 放在最前面，用 `[GOAL]` 标记分隔 |
| 懒注入导致 Agent 做出错误假设 | Agent 不知道有信息可查 | 在 L2 中列出"可查询的信息源"列表 |
