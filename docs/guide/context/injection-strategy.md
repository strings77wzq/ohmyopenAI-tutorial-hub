# 上下文注入策略

## 核心概念

上下文注入不是"一次性倒入"——那是 Prompt Engineering 的思路。上下文工程的做法是**渐进式披露**：先给摘要，Agent 需要细节时再展开；先给高频信息，低频信息按需加载。

注入策略解决的核心问题是：**如何在有限的窗口空间里，让 Agent 在每个时刻都能看到最相关的信息？**

## 为什么需要注入策略？

把五层上下文一次性全部注入窗口的结果是灾难性的：

- 窗口前 20% 被高频信息占据，Agent 能有效处理
- 窗口后 80% 是低频碎片，Agent 的注意力密度急剧下降（"Lost in the Middle" 效应）
- Token 在每次迭代中重复消耗，但大部分内容根本没被用过

更糟糕的是，一次性注入会制造一个假象：Agent 以为它"知道"所有注入的信息，但实际上它只有效处理了其中一部分。这导致 Agent 基于不完整的信息做决策，而它自己并不知道自己遗漏了什么。

## 三种注入模式

### 模式 A：预注入（Pre-injection）

在 Agent 开始工作前，把最高优先级的信息放入窗口。

```
适用层：L1 目标层 + L2 项目知识层摘要
时机：任务开始前
优点：Agent 从一开始就有正确的方向
缺点：占用初始窗口空间
```

预注入的关键是**精简**。不要把整个项目文档塞进窗口，而是提供一个结构化索引：

```
预注入 L2 示例：
  项目：ai-tutorial-hub
  框架：VitePress 1.6.4
  目录结构：docs/guide/{skills,mcp,context,harness,...}/
  链接约定：内部页面 /guide/... 格式，不带 .md
  配置文件：docs/.vitepress/config.ts
  验证命令：npm run docs:check-links
```

这个 6 行的摘要覆盖了 Agent 修复链接需要的所有项目知识。如果 Agent 需要查看具体的链接格式或路由配置，可以通过工具读取原始文件。

### 模式 B：懒注入（Lazy Injection）

Agent 需要时通过工具调用获取，类似于按需加载的模块。

```
适用层：L4 外部知识层（API 文档、库源码）
时机：Agent 主动请求时
优点：只在使用时才消耗 Token
缺点：Agent 需要"知道它不知道什么"才能主动查询
```

懒注入的挑战是 Agent 的"元认知"——它需要意识到自己缺少某个信息，才能主动查询。解决方案是在 L2 中提供信息源索引：

```
L2 补充 — 可查询信息源：
  - API 文档：docs/api-reference.md（如果需要查看接口定义）
  - 路由配置：docs/.vitepress/config.ts（如果需要查看侧边栏结构）
  - 历史断链：docs/link-checker-output.json（如果需要查看之前的检查结果）
```

有了这个索引，Agent 知道"有哪些信息可以查询"，即使它当前没有加载这些信息。

### 模式 C：触发注入（Triggered Injection）

当特定条件满足时（构建失败、测试失败），自动注入相关信息。

```
适用层：L5 操作证据层
时机：工具调用返回后
优点：上下文自动跟随系统状态变化
缺点：需要事件监听和条件判断逻辑
```

触发注入是上下文工程中自动化程度最高的模式。它不需要 Agent 主动请求——当系统状态变化时，相关信息自动流入窗口。

```
触发注入的典型场景：
  1. Agent 运行测试 → 测试结果自动注入 L5
  2. Agent 修改代码 → 构建结果自动注入 L5
  3. Agent 运行 lint → lint 报告自动注入 L5
  4. Agent 运行链接检查 → 检查结果自动注入 L5
```

## Token 预算分配

以一个 100K Token 的上下文窗口为例：

```
┌─────────────────────────────────────┐
│ L1 目标层          5K  (5%)         │ ← 最高密度：每个字都有用
│ L2 项目知识        20K (20%)        │ ← 缓存不变部分
│ L3 工作状态        15K (15%)        │ ← 每次迭代轮换
│ L4 外部知识        15K (15%)        │ ← 按需加载，用后释放
│ L5 操作证据        5K  (5%)         │ ← 只注入摘要
│ 保留（对话历史等）  40K (40%)        │ ← 留给工具调用结果和对话
└─────────────────────────────────────┘
```

这不是固定模板——不同任务类型有不同的分配策略：

| 任务类型 | L1 | L2 | L3 | L4 | L5 | 保留 |
|----------|----|----|----|----|----|------|
| 修复 bug | 10% | 10% | 15% | 5% | 20% | 40% |
| 新增功能 | 10% | 25% | 10% | 15% | 5% | 35% |
| 代码审查 | 5% | 15% | 5% | 5% | 20% | 50% |
| 文档编写 | 10% | 15% | 10% | 20% | 5% | 40% |

### 为什么修复 bug 需要更多 L5？

修复 bug 时，测试输出是关键信息。Agent 需要看到完整的错误堆栈和测试结果来定位问题。但这些信息只在当前迭代有用——一旦修复完成，旧的测试输出就应该被压缩或移除。

### 为什么新增功能需要更多 L2？

新增功能时，Agent 需要理解项目的架构约定、现有代码的模式、以及如何保持一致性。这些信息在任务期间很少变化，适合缓存在 L2 中。

### 为什么代码审查需要更多保留空间？

代码审查需要处理大量的 diff 输出。这些输出通常很大（可能几十 K Token），需要足够的保留空间来容纳。

## 注入顺序

不是所有层同时注入——注入顺序影响 Agent 的注意力分布：

```
Step 1: L1 目标层 (最先注入 — Agent 先看到"要做什么")
Step 2: L2 项目知识层摘要 (注入结构但不注入所有文件)
Step 3: L3 工作状态层 (如果这是一个恢复任务，注入上次的进度)
Step 4: Agent 开始工作 → 按需拉取 L4
Step 5: 工具调用返回 → L5 操作证据自动流入
Step 6: 每次迭代后 → L3 工作状态更新，替换旧版本
```

### 为什么 L1 必须最先注入？

LLM 对上下文开头的信息关注度最高。把最重要的信息（任务目标和验收标准）放在最前面，确保 Agent 在整个执行过程中都能"看到"它。

如果 L1 被放在窗口中间或末尾，Agent 可能会在执行过程中逐渐"遗忘"关键约束，导致偏离目标。

### 为什么 L2 紧随 L1？

在 Agent 理解"要做什么"之后，它需要立即知道"在这个项目中怎么做"。项目知识层提供了实现的约束和约定，确保 Agent 的方案从一开始就符合项目规范。

### 为什么 L3 在恢复任务时需要注入？

如果 Agent 被中断后恢复执行，它需要知道之前做了什么。L3 的"已完成步骤"和"已尝试方案"帮助 Agent 从断点继续，而不是从头开始。

## 何时用全文 vs 摘要

| 内容 | 策略 | 原因 |
|------|------|------|
| 验收标准 | **全文** | 不可压缩，Agent 必须精确理解 |
| 安全规则 | **全文** | 压缩可能导致漏掉关键约束 |
| 用户最新指令 | **全文** | 用户说的话不能由模型"总结"——会丢失意图 |
| 项目架构文档 | 摘要 → 按需全文 | 大部分时候 Agent 只需要知道"在哪" |
| API 文档 | 摘要 → 按需全文 | 只有在实际调用时才需要完整签名 |
| 测试输出 | **摘要** | 只需失败数和关键错误行 |
| 构建日志 | **摘要** | 只需第一个错误，不需要完整堆栈 |
| 搜索结果列表 | **摘要** | 只需最相关的 2-3 条结果 |

### 摘要的质量标准

好的摘要应该满足：

1. **可行动**：Agent 看到摘要后能做出正确的决策
2. **可展开**：Agent 需要细节时知道去哪里获取
3. **无歧义**：摘要不会误导 Agent 做出错误判断

坏的摘要示例：
```
❌ "一些测试失败了" — Agent 不知道是哪些测试
❌ "API 有认证要求" — Agent 不知道具体怎么认证
❌ "代码有问题" — Agent 不知道是什么问题
```

好的摘要示例：
```
✓ "7/8 测试通过，Test 47 失败：expected 200 got 404 (line 128)"
✓ "API 需要 Bearer token，通过 POST /auth/login 获取"
✓ "src/auth/middleware.ts:47 有类型错误：Argument of type 'string' is not assignable to parameter of type 'number'"
```

## 动态上下文加载

静态的预注入策略在某些场景下不够灵活。动态上下文加载根据 Agent 的实际行为调整注入内容：

### 基于工具调用的动态加载

```
Agent 调用 read_file("src/auth/login.ts")
→ 自动注入：该文件的依赖关系摘要
→ 自动注入：该文件的测试文件位置
→ 自动注入：项目中类似文件的命名约定
```

### 基于错误类型的动态加载

```
Agent 遇到类型错误
→ 自动注入：项目中处理类型错误的常见模式
→ 自动注入：相关类型的定义文件
→ 自动注入：之前修复类似类型错误的记录
```

### 基于任务阶段的动态加载

```
任务开始时：注入 L1 + L2 摘要
诊断阶段：注入更多 L5（测试输出、错误日志）
修复阶段：注入更多 L2（代码约定、架构约束）
验证阶段：注入更多 L5（测试结果、构建日志）
```

## 注入策略的常见陷阱

### 陷阱一：注入过多

过度注入浪费 Token 并分散注意力。解决方法：
- 严格执行 Token 预算
- 定期检查窗口使用率
- 对超过预算的内容强制压缩

### 陷阱二：注入过少

注入不足导致 Agent 缺乏必要信息，做出错误假设。解决方法：
- 确保 L1 和 L2 的摘要足够完整
- 在 L2 中提供信息源索引
- 允许 Agent 通过工具获取缺失信息

### 陷阱三：注入时机错误

信息注入太早可能过时，注入太晚可能错过决策窗口。解决方法：
- L1 和 L2 在任务开始前注入
- L3 在每次迭代后更新
- L5 在工具调用后立即注入

### 陷阱四：忽略信息冲突

不同层级的信息可能冲突（例如 L4 的搜索结果与 L2 的项目约定矛盾）。解决方法：
- 在 L2 中明确标注项目约定的优先级
- 在 L3 中记录信息冲突的处理决策
- 遇到无法判断的冲突时，暂停并询问用户

## 示例：为"重构认证模块"设计注入方案

```
Phase 1: 预注入
  L1: "将 auth.ts（200 行）拆分为 3 个模块：login、middleware、types。
       验收标准：所有现有测试通过，类型检查无错误。"
  L2: 项目结构摘要 + 认证模块的依赖关系图

Phase 2: Agent 开始工作
  Agent: "我需要看 auth.ts 的完整代码和它的测试文件"
  → 懒注入: 读取 src/auth.ts 和 tests/auth.test.ts

Phase 3: Agent 第一次修改后
  → 触发注入: TypeScript 编译结果（如果失败，注入错误信息）
  → 触发注入: 测试运行结果

Phase 4: Agent 迭代修复
  → 每次修改后：触发注入新的编译和测试结果
  → L3 更新：当前假设、已完成步骤、已尝试方案

Phase 5: 所有测试通过
  L3 更新: "重构完成，3 个模块已创建，所有测试通过"
```

## 练习

为一个"重构 auth.ts（200 行→拆成 3 个模块）"的任务设计注入策略：

1. 预注入阶段应该包含什么？
2. 懒注入阶段 Agent 最可能请求哪些文件？
3. 触发注入会在什么时候发生？注入什么？
4. 如果 Token 预算被工具输出占满，应该压缩哪一层？

## 排错指南

| 症状 | 可能原因 | 修复 |
|------|----------|------|
| Agent 频繁读取同一类文件 | 预注入没有给出足够的结构信息 | 在 L2 中增加项目结构摘要 |
| Agent 忽略了验收标准中的细节 | L1 被 L2 的大量文本挤到后面 | L1 放在最前面，用分隔标记分隔 |
| 懒注入导致 Agent 做出错误假设 | Agent 不知道有信息可查 | 在 L2 中列出"可查询的信息源"列表 |
| Token 预算被工具输出耗尽 | L5 没有压缩策略 | 对 L5 只保留摘要，详见[压缩与摘要](./compression) |
| Agent 重复注入相同信息 | 注入策略没有去重机制 | 在注入前检查窗口中是否已存在相同内容 |
