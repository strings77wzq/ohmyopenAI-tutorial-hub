# 上下文分层模型

## 核心概念

上下文工程的第一原则：**不是"把所有信息塞进窗口"，而是"在正确的时间把正确的信息放进正确的层级"。**

五层上下文模型把 Agent 的上下文窗口按优先级和来源分为五层，每一层有不同的注入策略和刷新频率。这个模型不是理论框架——它是解决实际 Agent 问题的工程工具。

## 为什么需要分层？

没有分层的上下文是一个"信息汤"——Agent 分不清什么是目标、什么是参考、什么是历史噪音。分层解决了三个核心问题：

**优先级混乱。** 当所有信息平铺在窗口中时，Agent 不知道应该先看任务描述还是先看项目架构。一个修复 bug 的 Agent 可能花大量 Token 阅读完整的架构文档，而不是直接聚焦于错误堆栈。

**信息过时。** 上次迭代的错误日志还在窗口里，但 Agent 以为它还是当前的。没有分层意味着没有"刷新"的概念——旧信息和新信息混在一起，Agent 无法区分。

**Token 浪费。** 每次迭代都把所有信息重新注入，大部分其实没变。项目架构文档在任务期间很少变化，但每次都重新注入会浪费宝贵的窗口空间。

## 五层模型详解

```
┌─────────────────────────────────────────────────────────┐
│ L1 目标层 (Goal)                                        │
│ 用户任务、验收标准、限制条件、不可变约束                    │
│ 写入者：用户 / 规划系统                                   │
│ 刷新：整个任务期间不变                                    │
│ 优先级：最高 — 任何决策必须对齐这一层                      │
├─────────────────────────────────────────────────────────┤
│ L2 项目知识层 (Project Knowledge)                       │
│ 架构文档、编码约定、技术栈、依赖关系、项目记忆              │
│ 写入者：开发者 / README / 项目文档 / 项目记忆             │
│ 刷新：按需加载，缓存非变更部分                             │
│ 优先级：高 — 所有实现必须符合项目约定                      │
├─────────────────────────────────────────────────────────┤
│ L3 工作状态层 (Working State)                           │
│ 当前假设、已完成步骤、失败输出、已尝试方案列表              │
│ 写入者：Agent 自身 / 会话笔记 / 任务日志                   │
│ 刷新：每次迭代后更新                                      │
│ 优先级：中 — 指导下一步决策，但不覆盖目标                   │
├─────────────────────────────────────────────────────────┤
│ L4 外部知识层 (External Knowledge)                      │
│ API 文档、搜索结果、库源码、最佳实践参考                   │
│ 写入者：MCP Resource / 检索系统                          │
│ 刷新：按需查询，结果缓存到任务结束                         │
│ 优先级：中 — 辅助实现，在 L2 不覆盖时补充                  │
├─────────────────────────────────────────────────────────┤
│ L5 操作证据层 (Operational Evidence)                    │
│ 测试结果、构建日志、截图、性能报告                         │
│ 写入者：Harness / 工具链                                 │
│ 刷新：每次工具调用后更新                                  │
│ 优先级：低 — 验证性信息，不应主导决策                      │
└─────────────────────────────────────────────────────────┘
```

## 每一层的深度解析

### L1 目标层：不可妥协的锚点

目标层是 Agent 的"北极星"。它包含：

- **用户任务**：要完成什么（例如"修复文档站中所有 404 链接"）
- **验收标准**：怎样算完成（例如"link-checker 输出 0 错误"）
- **限制条件**：不能做什么（例如"不改变任何 URL 结构"）
- **不可变约束**：无论实现多困难都不能违反的规则（例如"不删除任何页面"）

目标层的任何修改必须经过用户确认。Agent 不能因为"这样实现更容易"而悄悄放宽验收标准。这是一个硬性规则——如果 Agent 在实现过程中发现目标不可行，它应该暂停并报告冲突，而不是自行调整目标。

**实际示例：**

```
[L1] 目标层 — 修复文档站断链
  任务：修复 docs/ 中所有返回 HTTP 404 的内部链接
  验收标准：
    - link-checker 输出 0 errors
    - 不改变任何页面的 URL 结构
    - 不删除任何页面
  限制：
    - 操作范围：仅 docs/ 目录
    - 不可操作：openspec/、scripts/、.github/
  不可变约束：
    - 如果链接指向不存在的页面 → 询问用户，不自行判断删除
```

注意验收标准的具体性。"修复链接"是模糊的，"link-checker 输出 0 errors"是精确的可量化标准。好的 L1 应该让任何 Agent 都能独立判断任务是否完成。

### L2 项目知识层：结构化参考

项目知识层回答"这个项目的规则是什么"。它包含：

- **架构文档**：系统如何组织、模块如何划分
- **编码约定**：命名规则、代码风格、设计模式
- **技术栈**：使用了什么框架、版本号、已知约束
- **项目记忆**：之前学到的教训、已知问题、常见模式

**关键原则：摘要优先。** 不要把所有项目文件注入窗口。对于只读参考，先注入结构摘要（目录树、模块索引），Agent 需要具体文件时再用工具读取。高频访问的文件可以缓存摘要到工作状态层。

**实际示例：**

```
[L2] 项目知识层 — 缓存
  项目：ai-tutorial-hub
  框架：VitePress 1.6.4, base="/agent-engineering-hub/"
  链接约定：
    - 内部页面：/guide/skills/what-is-skill（不带 .md 后缀）
    - 英文页面：/en/guide/...
    - 外部链接：完整 https:// URL
  常见断链原因：
    1. 路径拼写错误 (60%+)
    2. 页面被移动但引用未更新
    3. .md 后缀遗留
  文件结构摘要：
    docs/guide/{skills,mcp,openspec,harness,context,...}/
    docs/en/guide/{skills,mcp,openspec,harness,...}/
    侧边栏路由：docs/.vitepress/config.ts
```

这个摘要只用了 10 行就覆盖了 Agent 修复链接需要的所有项目知识。如果 Agent 需要查看具体的链接约定，可以通过工具读取 `docs/.vitepress/config.ts`。

### L3 工作状态层：滚动更新的笔记本

工作状态层是 Agent 的"工作记忆"，它记录当前任务的执行状态：

- **当前假设**：Agent 对问题的当前理解（例如"大部分 404 是拼写错误"）
- **已完成步骤**：已经做了什么（例如"跑了一次 link-checker，输出 12 个断链"）
- **失败输出**：哪些尝试失败了（不应该在窗口中保留完整输出，只保留结论）
- **已尝试方案**：方案 A 失败了、方案 B 部分成功等

**关键原则：只保留最新。** 每次迭代后，工作状态层应该被更新，而不是累积。旧的假设如果被验证或推翻，应该被替换而不是保留。

**实际示例——迭代过程中的 L3 变化：**

```
Iteration 1 后的 L3：
  当前阶段：诊断
  已完成：运行 link-checker，输出 7 个错误
  当前假设：大部分是拼写错误
  已尝试方案：无

Iteration 2 后的 L3：
  当前阶段：修复
  已完成：批量修复 5 个拼写错误
  当前假设：剩余 2 个是页面不存在（需用户决策）
  已尝试方案：sed 批量替换 → 有效（5/7 已修复）

Iteration 3 后的 L3：
  当前阶段：等待用户决策
  已完成：批量修复 5 个拼写错误，分析剩余 2 个
  当前假设：/guide/openspec/spec → 应改为 writing-specs
            /guide/context/layer → 应改为 context/
  已尝试方案：sed 批量替换 → 有效（5/7 已修复）
  待决策：2 个链接指向不存在的页面，等待用户确认映射关系
```

注意 L3 的变化：它不是在追加，而是在**替换**。每个迭代后的 L3 都是完整的当前状态快照。

### L4 外部知识层：按需加载的参考库

外部知识层包含 Agent 需要但不在项目中的信息：

- **API 文档**：第三方服务的接口规范
- **库源码**：依赖库的实现细节
- **搜索结果**：针对特定问题的解决方案
- **最佳实践**：领域内的通用建议

**关键原则：懒加载。** Agent 不应该在任务开始时就加载所有可能用到的外部知识。它应该在需要时通过工具调用获取，类似于按需加载的模块。

**挑战：** 懒加载要求 Agent "知道它不知道什么"。如果 Agent 不知道自己需要查询某个 API 的文档，它就无法主动请求。解决方案是在 L2（项目知识层）中列出"可查询的信息源"索引：

```
[L2 补充] 可查询信息源：
  - VitePress 文档：https://vitepress.dev/（通过 MCP resource 访问）
  - 项目 README：docs/README.md
  - 路由配置：docs/.vitepress/config.ts
```

### L5 操作证据层：验证性信息

操作证据层是工具调用的输出，主要是验证性信息：

- **测试结果**：通过/失败的摘要，不需要完整输出
- **构建日志**：第一个错误和关键警告
- **截图**：UI 变化的视觉证据
- **性能报告**：加载时间、资源大小等指标

**关键原则：只需要结论。** 不要注入完整的测试输出或构建日志。只注入：
- 通过/失败的摘要
- 失败的具体行号和错误消息
- 与前一次运行的对比

**实际示例：**

```
[L5] 操作证据层 — 触发式
  注入前（完整输出，浪费 Token）：
    links (102 source files): 7 errors
    [404] /guide/skills/best-practice → 404 Not Found
    [404] /guide/mcp/concept → 404 Not Found
    ...（50 行详细输出）

  注入后（压缩摘要，节省 Token）：
    links: 7 errors / 102 files
    5 个拼写错误：best-practice→best-practices, concept→concepts...
    2 个页面不存在：openspec/spec, context/layer
```

## 层级间的优先级规则

当两层信息冲突时：

```
L1 > L2 > L3 > L4 > L5
```

**示例一：** L5（测试失败）说"代码有 bug"，但 L1（目标）说"必须在今天发布"。Agent 不应擅自推迟发布，而应报告冲突并询问用户："测试失败了，但目标要求今天发布。你希望怎么处理？"

**示例二：** L4（搜索结果）给出了一个与 L2（项目约定）矛盾的建议。Agent 应优先遵循项目约定，因为项目约定是针对这个项目的特定约束，而搜索结果是通用建议。

**示例三：** L3（工作状态）中的假设被 L5（操作证据）推翻。例如 Agent 假设"bug 在 auth 模块"，但测试显示 auth 模块正常。Agent 应更新 L3 的假设，而不是忽略测试结果。

## 层级设计的深层原则

### 目标层：保护完整性

目标层的保护不仅限于"不修改内容"。还包括：
- 不因为实现困难而选择性忽略某个验收标准
- 不因为发现了更优雅的方案而扩大任务范围
- 不因为上下文窗口紧张而压缩目标层

### 项目知识层：结构化索引

好的 L2 不是把所有文档塞进窗口，而是提供一个"地图"：

```
项目结构：
  docs/guide/
    skills/      — Skill 的概念、创建、管理（4 个子页）
    mcp/         — MCP 协议、服务器、客户端（3 个子页）
    context/     — 上下文工程（5 个子页）
    harness/     — 工具链集成（2 个子页）
  docs/en/guide/ — 英文版对应结构
```

Agent 看到这个索引后，知道去哪里找具体信息，但不需要加载所有页面的内容。

### 工作状态层：防回退

L3 的一个关键功能是防止 Agent 回退。通过维护"已尝试方案"列表，Agent 不会重复已经失败的尝试。这在长任务中尤为重要——当窗口被压缩后，Agent 可能"忘记"之前尝试过什么。

### 操作证据层：对比优于绝对

L5 的价值不仅在于"当前结果是什么"，更在于"和之前相比有什么变化"：

```
L5 对比注入：
  第 1 轮：7 errors
  第 2 轮：2 errors（-5，修复了拼写错误）
  第 3 轮：待运行
```

这种对比信息帮助 Agent 理解自己的进展，而不仅仅是看到一个数字。

## 常见的层级混淆问题

### 问题一：把操作证据当目标

Agent 可能把"测试通过"当成最终目标，而不是把"满足用户验收标准"当成目标。测试通过只是 L5 的证据，真正的目标在 L1。

### 问题二：L3 膨胀

工作状态层随迭代累积，如果不做清理，会占用大量窗口空间。解决方案是每次迭代后压缩 L3，只保留当前状态和关键历史。

### 问题三：L2 缺失

如果项目知识层为空或不完整，Agent 会反复读取相同文件来理解项目结构。这浪费了大量 Token 和时间。在任务开始前，投入少量 Token 构建一个良好的 L2 摘要，可以节省后续大量开销。

## 排错指南

| 症状 | 可能原因 | 修复 |
|------|----------|------|
| Agent 反复读取同一个文件 | L2 没有缓存已读取的摘要 | 读完后摘要写入 L3 |
| Agent 忽略了重要的验收标准 | L1 被后续层的噪声淹没 | 把 L1 放在窗口最顶部，加分隔标记 |
| Agent 基于过时信息做决策 | L3 在迭代之间没有更新 | 每次迭代结束时强制刷新 L3 |
| 上下文窗口超限 | 五层都在膨胀，没有压缩策略 | 对 L4/L5 只保留摘要，详见[压缩与摘要](./compression) |
| Agent 重复尝试已失败的方案 | L3 没有维护"已尝试方案"列表 | 在 L3 中添加 Tried & Failed 列表 |

## 练习

为一个"新增 MCP 教程页"的任务设计五层上下文包：

1. L1 目标层应该包含什么？验收标准怎么量化？
2. L2 项目知识层应该缓存哪些文件？
3. L3 工作状态层在任务过程中会如何变化？
4. L4 和 L5 在这次任务中分别是什么角色？
