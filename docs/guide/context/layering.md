# 上下文分层模型

## 概念

上下文工程的第一原则：**不是"把所有信息塞进窗口"，而是"在正确的时间把正确的信息放进正确的层级"**。

五层上下文模型把 Agent 的上下文窗口按优先级和来源分为五层，每一层有不同的注入策略和刷新频率。

## 为什么需要分层？

没有分层的上下文是一个"信息汤"——Agent 分不清什么是目标、什么是参考、什么是历史噪音。分层解决了三个核心问题：

1. **优先级混乱**：Agent 不知道应该先看任务描述还是先看项目架构
2. **信息过时**：上次迭代的错误日志还在窗口里，但 Agent 以为它还是当前的
3. **Token 浪费**：每次迭代都把所有信息重新注入，大部分其实没变

## 五层模型详解

```
┌─────────────────────────────────────────────────────────┐
│ L1 目标层 (Goal)                                        │
│ 用户任务、验收标准、限制条件、不可变约束                    │
│ 写入者：用户 / OpenSpec                                  │
│ 刷新：整个任务期间不变                                    │
│ 优先级：最高 — 任何决策必须对齐这一层                      │
├─────────────────────────────────────────────────────────┤
│ L2 项目知识层 (Project Knowledge)                       │
│ 架构文档、编码约定、技术栈、依赖关系、项目记忆              │
│ 写入者：开发者 / README / AGENTS.md / 项目记忆            │
│ 刷新：按需加载，缓存非变更部分                             │
│ 优先级：高 — 所有实现必须符合项目约定                      │
├─────────────────────────────────────────────────────────┤
│ L3 工作状态层 (Working State)                           │
│ 当前假设、已完成步骤、失败输出、已尝试方案列表              │
│ 写入者：Agent 自身 / notepad / trace                     │
│ 刷新：每次迭代后更新                                      │
│ 优先级：中 — 指导下一步决策，但不覆盖目标                   │
├─────────────────────────────────────────────────────────┤
│ L4 外部知识层 (External Knowledge)                      │
│ API 文档、搜索结果、库源码、最佳实践参考                   │
│ 写入者：MCP Resource / 检索系统                          │
│ 刷新：按需查询，结果缓存到任务结束                         │
│ 优先级：中 — 辅助实现，在 L2 不覆盖时补充                  │
├─────────────────────────────────────────────────────────┤
│ L5 操作证据层 (Operational Evidence)                    │
│ 测试结果、构建日志、截图、Lighthouse 报告                  │
│ 写入者：Harness / 工具链                                 │
│ 刷新：每次工具调用后更新                                  │
│ 优先级：低 — 验证性信息，不应主导决策                      │
└─────────────────────────────────────────────────────────┘
```

## 层级间的优先级规则

当两层信息冲突时：

```
L1 > L2 > L3 > L4 > L5
```

示例：L5（测试失败）说"代码有 bug"，但 L1（目标）说"必须在今天发布"→ Agent 不应擅自推迟发布，而应报告冲突并询问用户。

另一个示例：L4（搜索结果）给出了一个与 L2（项目约定）矛盾的建议 → Agent 应优先遵循项目约定。

## 层级设计原则

### 目标层：不可妥协

目标层的任何修改必须经过用户确认。Agent 不能因为"这样实现更容易"而悄悄放宽验收标准。

### 项目知识层：摘要优先

不要把所有项目文件注入窗口。对于只读参考：
- 先注入结构摘要（目录树、模块索引）
- Agent 需要具体文件时用工具读取
- 高频访问的文件缓存摘要到工作状态层

### 工作状态层：只保留最新

每次迭代后：
- 更新"已完成步骤"
- 更新"当前假设"（如果被验证或推翻）
- 删除已解决的失败输出
- 追加新的"已尝试方案"

### 操作证据层：只需要结论

不要注入完整的测试输出或构建日志。只注入：
- 通过/失败的摘要
- 失败的具体行号和错误消息
- 与前一次运行的对比

## 示例：修复文档站 404 的上下文包

```
[L1 目标层] — 不可变
- 任务：修复 docs/ 中所有返回 404 的内部链接
- 验收标准：link-checker 输出 0 错误
- 限制：不改变任何页面的 URL 结构

[L2 项目知识层] — 缓存
- 项目结构：VitePress 1.6.4，base=/agent-engineering-hub/
- 链接约定：内部链接用 /guide/... 格式，不加 .md 后缀
- 已知模式：之前有 3 个 404 是因为拼错了路径

[L3 工作状态层] — 每次迭代更新
- 当前假设：大部分 404 是路径拼写错误
- 已完成：跑了一次 link-checker，输出 12 个断链
- 已尝试：无

[L4 外部知识层] — 按需
- （暂无 — 修复链接不需要外部 API）

[L5 操作证据层] — 最新
- link-checker 输出：12 errors，详见 link-checker-output.json
```

## 练习

为一个"新增 MCP 教程页"的任务设计五层上下文包：

1. L1 目标层应该包含什么？验收标准怎么量化？
2. L2 项目知识层应该缓存哪些文件？
3. L3 工作状态层在任务过程中会如何变化？
4. L4 和 L5 在这次任务中分别是什么角色？

## 排错

| 症状 | 可能原因 | 修复 |
|------|----------|------|
| Agent 反复读取同一个文件 | L2 没有缓存已读取的摘要 | 读完后摘要写入 L3 |
| Agent 忽略了重要的验收标准 | L1 被后续层的噪声淹没 | 把 L1 放在窗口最顶部，加分隔标记 |
| Agent 基于过时信息做决策 | L3 在迭代之间没有更新 | 每次迭代结束时强制刷新 L3 |
| 上下文窗口超限 | 五层都在膨胀，没有压缩策略 | 对 L4/L5 只保留摘要，详见[压缩与摘要](./compression) |
