# 实战案例：修复文档站断链

## 任务概述

任务是"修复 Agent Engineering Hub 文档站中所有返回 404 的内部链接"。我们将为这个任务设计一个完整的上下文包，展示五层模型、注入策略和压缩方案如何协同工作。

这个案例选择了一个"修复型"任务，因为它清晰地展示了上下文工程的各个要素：
- 目标明确且可量化（link-checker 输出 0 错误）
- 涉及多轮迭代（诊断 → 修复 → 验证）
- 需要人工决策（不存在的页面如何处理）
- Token 消耗可控（适合教学演示）

## 任务分析

在开始写上下文包之前，先分析任务特征：

| 维度 | 分析 | 上下文工程影响 |
|------|------|---------------|
| 任务类型 | 修复型（修 bug，非新增功能） | L5 需要更多空间（测试输出） |
| 涉及范围 | 可能触及 docs/ 下多个 .md 文件 | L2 需要文件结构索引 |
| 验收标准 | 可量化（link-checker 输出 0 错误） | L1 可以精确定义 |
| 可恢复性 | 高（git revert 可撤销任意修改） | 降低风险，允许更多自动化 |
| 需要外部知识 | 低（修复链接不需要 API 文档） | L4 可以为空 |
| 需要项目知识 | 中（了解 VitePress 链接约定） | L2 需要覆盖链接约定 |

## 完整上下文包设计

```
═══════════════════════════════════════════════════════════
[L1] 目标层 — 不可变
═══════════════════════════════════════════════════════════

任务：修复 docs/ 中所有返回 HTTP 404 的内部链接
验收标准：
  - npm run docs:check-links 输出 "0 errors" 或等效通过标志
  - 不改变任何页面的 URL 结构（已有路由定义在 docs/.vitepress/config.ts）
  - 不删除任何页面
  - 不修改非链接的内容文本
限制：
  - 操作范围：docs/ 目录
  - 不可操作：openspec/、scripts/、.github/
  - 如果某个链接指向的页面确实不存在且不应存在 → 询问用户，不自行判断删除

═══════════════════════════════════════════════════════════
[L2] 项目知识层 — 缓存
═══════════════════════════════════════════════════════════

项目：ai-tutorial-hub
框架：VitePress 1.6.4, base="/agent-engineering-hub/"
链接约定：
  - 内部页面：/guide/skills/what-is-skill（不带 .md 后缀）
  - 首页：/ 或 /index
  - 英文页面：/en/guide/...
  - 外部链接：完整 https:// URL
常见断链原因：
  1. 路径拼写错误 (60%+)
  2. 页面被移动但引用未更新
  3. .md 后缀遗留（早期页面用 xxx.md 格式引用）
文件结构摘要：
  docs/guide/{skills,mcp,openspec,harness,context,loop-engineering,...}/
  docs/en/guide/{skills,mcp,openspec,harness,...}/
  侧边栏路由：docs/.vitepress/config.ts

═══════════════════════════════════════════════════════════
[L3] 工作状态层 — 初始状态（每次迭代后更新）
═══════════════════════════════════════════════════════════

当前阶段：诊断
已尝试方案：（无）
当前假设：（待 link-checker 输出后建立）
已完成步骤：（无）

═══════════════════════════════════════════════════════════
[L4] 外部知识层 — 按需
═══════════════════════════════════════════════════════════

（无需预加载。VitePress 链接格式在 L2 中已覆盖。）

═══════════════════════════════════════════════════════════
[L5] 操作证据层 — 触发式
═══════════════════════════════════════════════════════════

待注入：npm run docs:check-links 的输出（Agent 第一步主动运行）
```

### 上下文包设计分析

**为什么 L1 这么详细？**

L1 的每一条验收标准都是独立的 pass/fail 条件。Agent 在任务完成后可以逐条检查：

```
L1 验收标准检查清单：
  [ ] link-checker 输出 0 errors
  [ ] 未改变 URL 结构
  [ ] 未删除页面
  [ ] 未修改非链接内容
```

如果任何一条不通过，Agent 知道任务没有完成。

**为什么 L2 包含"常见断链原因"？**

这不是随意添加的信息——它帮助 Agent 建立正确的假设。当 Agent 看到 7 个断链时，它会优先检查拼写错误（因为 L2 说 60%+ 是拼写错误），而不是假设所有链接都指向不存在的页面。

**为什么 L4 为空？**

这个任务不需要外部知识。VitePress 的链接格式在 L2 中已经覆盖，Agent 不需要查询外部 API 或文档。保持 L4 为空节省了窗口空间。

**为什么 L5 是触发式的？**

Agent 在第一步会主动运行 link-checker，输出会自动流入 L5。不需要预加载任何操作证据。

## Agent 实际执行过程

### Iteration 1 — 诊断

```
Agent 运行: npm run docs:check-links
→ [L5 注入] links (102 source files): 7 errors

错误摘要（提取式压缩后注入）：
  1. /guide/skills/best-practice → 404（应为 best-practices）
  2. /guide/mcp/concept → 404（应为 concepts）
  3. /guide/openspec/spec → 404（页面不存在）
  4. /en/guide/harness/introduction → 404（应为 intro）
  5. /guide/omo/arch → 404（应为 architecture）
  6. /guide/context/layer → 404（页面不存在）
  7. /guide/loop → 404（应为 /guide/loop-engineering/）

[L3 更新]
  当前阶段：修复
  当前假设：#1, #2, #4, #5, #7 是拼写错误（5个）；#3, #6 是页面不存在（2个）
  已尝试方案：无
```

**上下文变化分析：**

- L5 从"待注入"变为具体的错误列表（提取式压缩：从 50+ 行压缩到 7 行）
- L3 从空状态变为有假设和阶段信息
- L1 和 L2 保持不变（不变的信息不需要重新注入）

### Iteration 2 — 批量修复拼写错误

```
Agent: 使用 sed 批量替换 5 个拼写错误的链接
  s|/guide/skills/best-practice|/guide/skills/best-practices|g
  s|/guide/mcp/concept|/guide/mcp/concepts|g
  s|/en/guide/harness/introduction|/en/guide/harness/intro|g
  s|/guide/omo/arch|/guide/omo/architecture|g
  s|/guide/loop|/guide/loop-engineering/|g

→ npm run docs:check-links
→ [L5 注入] links (102 source files): 2 errors

错误摘要：
  3. /guide/openspec/spec → 404（页面不存在）
  6. /guide/context/layer → 404（页面不存在）

[L3 更新]
  当前阶段：需要决策
  已完成步骤：批量修复 5 个拼写错误
  已尝试方案：sed 批量替换 → 有效（5/7 已修复）
  剩余问题：2 个链接指向不存在的页面
```

**上下文变化分析：**

- L5 更新为新的错误列表（旧的错误列表被替换，不是累积）
- L3 更新了阶段、已完成步骤、已尝试方案
- L3 的"已尝试方案"记录了"sed 批量替换 → 有效"，防止 Agent 重复尝试

### Iteration 3 — 决策

```
Agent 分析:
  /guide/openspec/spec → openspec/ 目录下有 concepts.md, commands.md, workflow.md...
                         但没有 spec.md。最接近的语义是 writing-specs.md
  /guide/context/layer → context/ 是单页模块（只有 index.md）。
                          没有单独的 layer.md。最接近的语义是 index.md 中的
                          "上下文分层" 章节

Agent 暂停，询问用户:
  "2 个断链指向不存在的页面。我的建议：
   1. /guide/openspec/spec → 改为 /guide/openspec/writing-specs
   2. /guide/context/layer → 改为 /guide/context/ (指向上下文工程首页)
   是否同意？或者你希望为这些链接创建新页面？"
```

**为什么 Agent 暂停？**

这是 L1 限制条件的触发："如果某个链接指向的页面确实不存在且不应存在 → 询问用户，不自行判断删除"。Agent 无法自行判断"不存在的页面应该映射到哪个现有页面"，所以它暂停并报告决策点。

**这个暂停的价值：**

- 避免了 Agent 自作主张修改链接（可能映射到错误的页面）
- 把决策权交还给用户（用户最了解页面的语义关系）
- 保持了 L1 的完整性（没有违反"询问用户"的限制）

### Iteration 4 — 用户确认后完成

```
用户: "同意方案 1 和 2"

Agent 执行修改 → npm run docs:check-links
→ [L5 注入] links (102 source files): 0 errors → PASS

L1 验收标准检查:
  [✓] link-checker 输出 0 errors
  [✓] 未改变 URL 结构
  [✓] 未删除页面
  [✓] 未修改非链接内容

→ 任务完成
```

**为什么任务完成前要检查 L1？**

Agent 不能假设"link-checker 通过 = 任务完成"。它必须逐条检查 L1 的所有验收标准，确保没有违反任何限制。这种检查是上下文工程的核心价值——L1 提供了明确的完成定义。

## 这个案例展示了什么

### 1. L5 触发注入

Agent 主动运行 link-checker，输出自动流入操作证据层。注入使用了提取式压缩（从 50+ 行压缩到 7 行），只保留了关键的错误信息。

### 2. L3 滚动更新

每次迭代后工作状态层都更新了当前假设和进度。更新是替换而非累积——L3 始终保持最新的任务状态快照。

### 3. L1 不可变

Agent 始终没有改变验收标准。即使在 Iteration 3 遇到了无法自行判断的决策点，Agent 也是暂停询问用户，而不是放宽限制条件。

### 4. 人工反馈的边界

Agent 在无法判断映射关系时暂停询问，而不是自作主张。这是上下文工程中"人工反馈通道"的典型触发：Agent 走到了决策边界，需要人类判断。

### 5. 压缩未触发

这个任务 Token 消耗很小（只有 4 轮迭代，每轮的工具输出都很短），不需要压缩。但在更长的任务中，L5 的旧错误列表应该被压缩或移除。

## 扩展场景：如果任务更复杂

### 场景一：50 个断链

如果 link-checker 输出 50 个错误，L5 需要压缩：

```
压缩前（50 行）：
  1. /guide/skills/best-practice → 404
  2. /guide/mcp/concept → 404
  ...（50 行）

压缩后（10 行）：
  50 个错误，分类：
  - 拼写错误（35个）：best-practice→best-practices 等
  - 页面不存在（10个）：openspec/spec 等
  - 路径错误（5个）：guide/loop→guide/loop-engineering 等
  详见 link-checker-output.json
```

### 场景二：跨模块影响

如果修复断链需要修改多个模块的代码（不仅是 docs/），L2 需要扩展：

```
L2 补充：
  模块依赖：
    docs/ ← scripts/link-checker.ts（链接检查逻辑）
    docs/ ← .github/workflows/docs.yml（CI 配置）
  注意：修改 docs/ 后需要确认 CI 仍然通过
```

### 场景三：任务中断恢复

如果 Agent 在 Iteration 2 后被中断，恢复时 L3 应该包含：

```
[L3 恢复状态]
  当前阶段：需要决策
  已完成步骤：批量修复 5 个拼写错误
  已尝试方案：sed 批量替换 → 有效（5/7 已修复）
  剩余问题：2 个链接指向不存在的页面
  中断点：等待用户决策（Iteration 3 开始前）
  恢复动作：继续等待用户决策
```

这个恢复状态让新的 Agent（或同一个 Agent 恢复后）能从断点继续，而不需要重新诊断。

## 练习

用同样的框架，为一个"新增 Context Engineering 模块的 3 个子页"的任务设计上下文包并模拟执行过程：

1. 写出完整的五层上下文包
2. 模拟至少 3 轮迭代，标注每一轮后 L3 和 L5 的变化
3. 在什么情况下 Agent 会暂停并询问用户？
4. 如果这个任务中途被中断（用户关闭了终端），恢复时 L3 应该包含什么？

## 排错指南

| 症状 | 可能原因 | 修复 |
|------|----------|------|
| Agent 修复了链接但违反了其他约束 | L1 的限制条件不够详细 | 在 L1 中添加更多限制条件 |
| Agent 在不需要时询问用户 | L1 的限制条件过于严格 | 放宽一些不需要人工判断的限制 |
| Agent 重复运行相同的检查 | L5 的输出没有被缓存 | 在 L3 中记录已运行的检查 |
| Agent 修复了错误的链接 | L2 的链接约定不够清晰 | 在 L2 中提供更详细的约定说明 |

## 本模块总结

通过这个实战案例，我们看到了上下文工程的完整应用：

1. **分层设计**：五层模型提供了清晰的信息组织结构
2. **注入策略**：预注入 L1+L2，触发注入 L5，懒注入 L4
3. **压缩技术**：提取式压缩用于 L5 的操作证据
4. **优先级管理**：L1 永远不压缩，L5 最先压缩
5. **人工边界**：Agent 在决策边界暂停询问用户

这些原则适用于任何 Agent 任务——无论任务大小或复杂度。关键是根据具体任务调整每层的内容和注入策略。
