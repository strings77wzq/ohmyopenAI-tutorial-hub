# 上下文压缩

## 核心概念

压缩上下文的本质不是"删掉信息"，而是**用更少的 Token 保留等价的决策价值**。好的压缩让 Agent 在压缩后的窗口里做出和完整窗口相同的决策。

这个定义中有三个关键词：

- **更少的 Token**：压缩的目标是节省空间，为其他信息腾出窗口
- **等价的决策价值**：压缩后的信息必须保留足够的细节，让 Agent 能做出正确的判断
- **相同的决策**：压缩不应该改变 Agent 的行为——它应该做出和使用完整信息时完全一样的决策

## 为什么需要压缩？

上下文窗口有两个硬约束：

### 约束一：容量上限

即使 200K 窗口，长期运行的任务也会填满。一个典型的 Agent 任务可能涉及：

- 初始注入：5-10K Token（L1 + L2 摘要）
- 每次工具调用：2-10K Token（测试输出、构建日志、文件内容）
- 对话历史：每轮累积 1-5K Token

20 轮迭代后，窗口可能已经用了 80-150K Token，留给新信息的空间非常有限。

### 约束二：注意力衰减

窗口越大，Agent 对中间部分信息的关注度越低。这不是假设——这是经过验证的 LLM 行为。研究表明：

- 对上下文开头（前 20%）的关注度最高
- 对上下文末尾（后 20%）的关注度次之
- 对上下文中间（中间 60%）的关注度最低

这意味着即使窗口没有填满，把大量信息堆在中间也会导致 Agent 遗忘关键细节。

压缩让窗口保持在小而高效的范围内，同时避免"Lost in the Middle"效应。

## 三种压缩策略

### 提取式压缩（Extractive）

保留原文中最关键的句子或段落，丢弃其余。

```
原文（200 行测试输出）:
  Test 1: PASS
  Test 2: PASS
  ...
  Test 47: FAIL - expected 200 got 404
  Test 48: PASS
  ...
  Test 100: PASS

提取式压缩:
  Tests: 99/100 passed, 1 failed
  FAIL: Test 47 - expected 200 got 404 (line 128)
```

**适用场景：**
- 测试输出：只保留通过/失败统计和失败详情
- 构建日志：只保留第一个错误和关键警告
- lint 报告：只保留错误级别的问题
- 搜索结果列表：只保留最相关的 2-3 条

**不适用：**
- 代码（提取式压缩会破坏语法）
- 安全规则（每一条都不可省略）
- 用户指令（不能只保留"关键词"）

**提取式压缩的关键原则：**

1. **保留完整性和可追溯性**：压缩后的摘要应该包含足够的信息，让 Agent 能定位到原始内容中的具体位置
2. **优先保留失败/错误信息**：成功的信息通常可以省略，失败的信息是调试的关键
3. **保留数量和比例**：通过 99/100 比 98/100 更重要，因为比例变化可能暗示新问题

### 摘要式压缩（Abstractive）

用模型生成原文的语义摘要，以更少的 Token 表达相同的信息。

```
原文（500 行 API 文档）:
  POST /api/users - 创建用户。参数：name (string, required),
    email (string, required), role (enum: admin|user, default: user)
  GET /api/users/:id - 获取用户详情。返回用户对象。
  PATCH /api/users/:id - 更新用户。参数：name, email, role（均为可选）
  DELETE /api/users/:id - 删除用户。不可逆操作。
  GET /api/users - 列出所有用户。分页参数：page (default: 1), limit (default: 20)
  所有端点需要 Bearer token 认证。

摘要式压缩:
  API 提供用户 CRUD 操作：
  - POST /api/users 创建（name+email 必填，role 默认 user）
  - GET /api/users/:id 查询
  - PATCH /api/users/:id 更新（参数均可选）
  - DELETE /api/users/:id 删除（不可逆）
  - GET /api/users 分页列表（page+limit）
  所有端点需要 Bearer token。
```

**适用场景：**
- API 文档：完整的接口规范可以压缩为核心要点
- 长对话历史：多轮对话可以压缩为关键决策和当前状态
- 项目架构文档：详细的架构描述可以压缩为核心组件和关系
- 日志摘要：大量日志可以压缩为关键事件的时间线

**风险与缓解：**

摘要式压缩的最大风险是**信息丢失**。模型在生成摘要时可能遗漏关键细节：

```
原文中的关键细节：
  "DELETE /api/users/:id - 删除用户。不可逆操作。
   需要 admin 角色权限。"

可能丢失的信息：
  "需要 admin 角色权限" — 摘要可能只说"删除操作"而遗漏权限要求
```

**缓解策略：**

1. **关键约束保留**：安全规则、权限要求、不可逆操作等关键约束必须全文保留
2. **可追溯性**：在摘要中标注"详见原文第 X 行"，让 Agent 知道去哪里获取完整信息
3. **摘要验证**：在摘要生成后，用另一个模型或规则验证摘要是否遗漏了关键信息

### 结构化压缩（Structural）

用结构化的元数据替代原始内容，Agent 需要时再展开。

```
原始（一个 2000 行的 src/ 目录）:
  src/
  ├── auth/
  │   ├── login.ts (340 lines)
  │   ├── middleware.ts (120 lines)
  │   └── types.ts (85 lines)
  ├── api/
  │   ├── routes.ts (560 lines)
  │   └── handlers.ts (420 lines)
  └── utils/
      └── format.ts (95 lines)

结构化压缩:
  src/ (7 files, ~2120 lines)
  模块: auth (login + middleware + types), api (routes + handlers), utils (format)
  入口: api/routes.ts → 注册所有路由
  认证: auth/middleware.ts → Bearer token 验证
  数据类型: auth/types.ts → User, AuthToken, Permission
```

**适用场景：**
- 项目结构：大型代码库的目录树
- 模块索引：每个模块的功能和关键文件
- 依赖关系图：模块间的依赖关系
- API 端点列表：所有可用的 API 端点

**优点：**

结构化压缩是三种策略中压缩率最高的，而且几乎无损。Agent 看到结构化索引后，知道"信息在哪"，需要时可以通过工具精准读取原始内容。

**结构化压缩的关键原则：**

1. **保留导航能力**：Agent 必须能从索引中找到它需要的信息
2. **标注关键入口**：标注最重要的文件和函数，让 Agent 优先关注
3. **提供上下文提示**：在索引中标注每个组件的职责，帮助 Agent 判断是否需要展开

## 什么时候不能压缩

某些信息压缩后就会失去决策价值——这些信息必须全文保留：

| 信息类型 | 不能压缩的原因 |
|----------|---------------|
| 安全规则（权限边界、密钥策略） | 漏掉一条规则可能导致安全事故 |
| 当前正在修改的代码 | Agent 需要逐行理解才能写出正确的修改 |
| 验收标准 | 每一条都是一个独立的 pass/fail 条件 |
| 错误消息（第一个失败） | 错误消息的精确措辞是调试的关键线索 |
| 用户的最新指令 | 用户说的话不能由模型"总结"——会丢失意图 |

### 为什么这些信息不能压缩？

**安全规则**：压缩可能导致遗漏关键约束。例如，"所有 API 调用必须使用 Bearer token"如果被压缩为"API 需要认证"，Agent 可能不知道具体怎么认证。

**当前代码**：Agent 需要理解代码的完整上下文才能写出正确的修改。压缩代码会破坏语法和逻辑。

**验收标准**：每一条标准都是独立的 pass/fail 条件。压缩可能合并或遗漏标准，导致 Agent 无法准确判断任务是否完成。

**错误消息**：错误消息的精确措辞包含调试的关键信息。"TypeError: Cannot read property 'name' of undefined"比"类型错误"有用得多。

**用户指令**：用户的原始意图可能被摘要曲解。"不要删除任何页面"如果被压缩为"谨慎操作"，Agent 可能做出不同的决策。

## 压缩时机

```
任务开始时:
  预注入 L1+L2 摘要 → 不压缩（还没有内容）

每次迭代后:
  检查窗口使用率
  ├── < 60% → 不压缩
  ├── 60-80% → 压缩 L5（操作证据），只保留最新一轮
  └── > 80% → 压缩 L4+L5 + L3 中的旧迭代
               → 如果还是不够，触发人工决策

关键原则: 先压缩低优先级层（L4→L5→L3），永远不压缩 L1
```

### 为什么 L1 永远不压缩？

L1 包含任务目标和验收标准——这是 Agent 的"北极星"。如果 L1 被压缩，Agent 可能偏离目标或遗漏关键约束。即使窗口空间极度紧张，L1 也应该保持完整。

### 压缩的优先级顺序

```
1. L5（操作证据）→ 最先压缩，因为只在当前迭代有用
2. L4（外部知识）→ 其次压缩，因为可以通过工具重新获取
3. L3（工作状态）→ 再次压缩，但要保留关键历史
4. L2（项目知识）→ 谨慎压缩，保留结构索引
5. L1（目标）→ 永不压缩
```

### L3 的特殊压缩策略

L3（工作状态层）不能简单地丢弃旧内容，因为它包含"已尝试方案"等关键历史。压缩策略是：

```
压缩前 L3（累积 20 轮迭代）：
  Iteration 1: 读文件 → 分析 → 修改 → 测试失败
  Iteration 2: 读文件 → 分析 → 修改 → 测试失败
  ...
  Iteration 20: 当前轮

压缩后 L3：
  [Summary: Iteration 1-18]
  目标：修复 auth 模块的 3 个类型错误
  尝试过：方案 A（添加类型断言）→ 失败（引入新错误）
          方案 B（重构接口定义）→ 失败（破坏其他模块）
          方案 C（引入泛型）→ 部分成功（2/3 错误已修复）
  最后状态：1 个错误待修复，文件 src/auth/middleware.ts:47

  [Iteration 19] → 全文保留
  [Iteration 20] → 全文保留（当前轮）
```

关键：压缩保留了"尝试过什么"和"当前状态"，Agent 不需要重复失败的尝试。

## 压缩的评估标准

好的压缩应该满足以下标准：

### 标准一：决策等价性

压缩后的信息应该让 Agent 做出和使用完整信息时相同的决策。

```
好的压缩：
  原文：100 行测试输出，99 通过，1 失败（Test 47）
  压缩：Tests: 99/100 passed, 1 failed (Test 47: expected 200 got 404)
  决策等价：Agent 知道需要修复 Test 47，且知道错误类型

坏的压缩：
  压缩：一些测试失败了
  决策不等价：Agent 不知道是哪些测试，也不知道错误类型
```

### 标准二：可追溯性

压缩后的信息应该包含足够的线索，让 Agent 能定位到原始内容。

```
好的压缩：
  src/auth/middleware.ts:47 — TypeError: Argument of type 'string' is not assignable to parameter of type 'number'

坏的压缩：
  auth 模块有类型错误
```

### 标准三：无歧义

压缩后的信息不应该有多种解读方式。

```
好的压缩：
  测试失败：Test 47，期望 200 实际 404

坏的压缩：
  测试有问题（"有问题"可以是失败、超时、跳过等多种情况）
```

## 示例：为长对话历史设计压缩方案

一个持续了 20 轮迭代的 Agent 对话。每轮包含 Agent 的思考和工具调用结果。

```
压缩前（~80K tokens）:
  [Iteration 1] 读文件 → 分析 → 修改 → 测试失败
  [Iteration 2] 读文件 → 分析 → 修改 → 测试失败
  ...
  [Iteration 19] 读文件 → 分析 → 修改 → 测试通过
  [Iteration 20] 当前轮

压缩后（~30K tokens）:
  [Summary: Iteration 1-18]
  目标：修复 auth 模块的 3 个类型错误
  尝试过：方案 A（添加类型断言）→ 失败（引入新错误）
          方案 B（重构接口定义）→ 失败（破坏其他模块）
          方案 C（引入泛型）→ 部分成功（2/3 错误已修复）
  最后状态：1 个错误待修复，文件 src/auth/middleware.ts:47

  [Iteration 19 - 全文保留] → 最近的上下文
  [Iteration 20 - 全文保留] → 当前轮
```

关键：压缩保留了"尝试过什么"和"当前状态"，Agent 不需要重复失败的尝试。

## 压缩的常见陷阱

### 陷阱一：过度压缩

过度压缩丢失了关键信息，导致 Agent 做出错误决策。

```
过度压缩：
  原文：POST /api/users 创建用户。参数：name (string, required),
        email (string, required), role (enum: admin|user, default: user)
  压缩：创建用户 API
  丢失：参数要求、类型、默认值
```

### 陷阱二：压缩时机错误

在 Agent 需要信息之前就压缩了，导致 Agent 需要重新获取。

```
错误时机：
  Agent 还在修复 Test 47，但 L5 中 Test 47 的错误信息已经被压缩
  Agent 需要重新运行测试来获取错误信息
```

### 陷阱三：压缩了不应压缩的层

压缩了 L1（目标）或 L2（项目约定），导致 Agent 偏离目标或违反项目规范。

### 陷阱四：压缩后没有更新索引

压缩了内容但没有更新结构化索引，导致 Agent 找不到压缩后的内容。

## 练习

为一个"运行了 15 轮迭代的任务"设计压缩方案：

1. 哪些轮次应该全文保留？
2. 早期轮次的哪些信息需要保留（已尝试方案？错误类型？）
3. 哪些信息可以安全丢弃？
4. 压缩后的摘要应该包含什么结构？

## 排错指南

| 症状 | 可能原因 | 修复 |
|------|----------|------|
| 压缩后 Agent 重复之前的错误 | 摘要没有保留"已尝试方案"列表 | 在 L3 中维护 "Tried & Failed" 列表 |
| 压缩导致关键上下文丢失 | 压缩了不应压缩的层（如 L1 验收标准） | 确认压缩只发生在 L4+L5+L3 旧迭代 |
| Agent 频繁重新读取已压缩的内容 | 摘要不够详细，Agent 无法判断是否需要展开 | 增加"可展开的信息源"索引 |
| 压缩后 Agent 做出错误决策 | 摘要丢失了关键细节 | 对关键约束使用全文保留策略 |
| 压缩过程本身消耗太多 Token | 使用了摘要式压缩但原文很短 | 对短内容（< 500 Token）直接保留 |
