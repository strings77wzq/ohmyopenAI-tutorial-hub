# 上下文工程

## 什么是上下文工程？

上下文工程（Context Engineering）是 Agent 系统设计中的核心学科，它回答一个根本问题：**在有限的上下文窗口里，Agent 应该看到什么、忽略什么、记住什么，以及如何证明这些选择没有破坏任务质量。**

这不是 Prompt Engineering 的延伸。Prompt Engineering 关注如何措辞让模型输出更好；上下文工程关注的是整个信息架构——从哪些信息应该存在，到它们以什么顺序、什么粒度、在什么时机进入 Agent 的视野。

## 为什么上下文如此重要？

LLM 有一个硬约束：**上下文窗口是有限的。** 即使最新的模型支持 200K 甚至更长的上下文，长期运行的 Agent 任务也会迅速填满窗口。更关键的是，有限窗口不是唯一的限制——注意力本身也有衰减效应。

### 信号与噪声

想象一个 Agent 正在调试一个认证错误。它需要：

- 错误堆栈（**高信号**——直接指向问题）
- 项目架构文档（**中信号**——帮助定位文件位置）
- 50 行无关的测试输出（**噪声**——浪费 Token 且分散注意力）
- 用户的原始指令（**高信号**——定义了成功标准）

如果这些信息以平铺方式全部注入窗口，Agent 可能会被噪声淹没。研究表明，LLM 对上下文中间部分的注意力显著低于开头和结尾——这被称为 **"Lost in the Middle"** 效应。换句话说，信息在窗口中的位置和它本身的内容一样重要。

### 信息层级

不是所有信息都同等重要。上下文工程的核心洞察是：**信息有天然的优先级层级。** 用户的任务目标比项目架构更重要，项目架构比历史日志更重要。如果窗口空间不足，必须有策略地丢弃低优先级信息，而不是让所有信息平等竞争注意力。

### 超越容量：上下文的质量

即使窗口足够大，信息的质量同样关键。过时的信息比没有信息更危险——Agent 可能基于已经失效的假设做决策。重复的信息会稀释关键信号的密度。矛盾的信息会让 Agent 产生困惑，在不同指令间摇摆。

## 上下文工程的核心挑战

### 1. 有限窗口与无限信息

一个典型的 Agent 任务可能涉及：
- 用户的完整指令和约束条件
- 项目的核心架构文档
- 需要修改的源代码文件
- 工具调用的输出（测试结果、构建日志、搜索结果）
- 之前的对话历史

把这些全部塞进窗口往往是不可能的，即使技术上可行，也不是最优解。

### 2. 信息的时效性

上下文中的信息会"过期"。上一次迭代的构建日志在下一次迭代后就不再是最新状态。如果 Agent 基于过时的日志做决策，可能会重复已经修复的问题，或者忽略新引入的错误。

### 3. 信息的选择性注入

不是所有相关信息都应该被注入。例如，Agent 在修复一个具体的函数时，只需要该函数的代码和它的直接调用者，不需要整个项目的 500 个文件。但如何精确选择"刚好够用"的信息，同时不遗漏关键上下文，是一个持续的挑战。

### 4. 上下文污染

无关信息不仅浪费 Token，还会主动干扰 Agent 的决策。当窗口中充斥着不相关的内容时，Agent 的注意力会被分散，可能导致：
- 遗忘关键约束条件
- 重复已经尝试过的失败方案
- 基于噪声而非信号做判断

## 上下文工程的设计原则

### 原则一：优先级驱动

越接近任务目标的信息，优先级越高。当 Token 预算紧张时，优先保留高层信息（目标、约束），丢弃低层信息（历史日志、中间结果）。

### 原则二：渐进式披露

不要一次性注入所有信息。先给摘要，Agent 需要细节时再展开。先给高层结构，低层细节按需加载。这减少了初始窗口的占用，同时保证 Agent 在需要时能获取完整信息。

### 原则三：只保留最新

历史信息的价值随时间递减。每次迭代后，应该用最新状态替换旧状态，而不是累积保留。Agent 不需要知道 10 次迭代前的构建日志，只需要知道当前状态和之前尝试过什么方案。

### 原则四：压缩优先于丢弃

在删除信息之前，先尝试压缩。一段 500 行的日志可以压缩为 3 行摘要，保留了决策价值但大幅节省了 Token。只有在压缩也无法保留关键信息时，才考虑丢弃。

### 原则五：安全性不可压缩

某些信息永远不应该被压缩或丢弃：安全规则、权限边界、用户的最新指令。这些信息的每一条都可能决定任务的成败或系统的安全。

## 本模块的学习路径

本模块围绕一个核心模型展开——**五层上下文模型**，它将 Agent 的上下文窗口按优先级和来源分为五个层级：

```
┌─────────────────────────────────────────────────┐
│  L1  目标层 — 不可妥协的锚点                      │
│      用户任务 + 验收标准 + 不可变约束              │
├─────────────────────────────────────────────────┤
│  L2  项目知识层 — 结构化参考                      │
│      架构文档 + 编码约定 + 技术栈 + 项目记忆       │
├─────────────────────────────────────────────────┤
│  L3  工作状态层 — 滚动更新的笔记本                │
│      当前假设 + 已完成步骤 + 失败输出              │
├─────────────────────────────────────────────────┤
│  L4  外部知识层 — 按需加载的参考库                │
│      API 文档 + 库源码 + 搜索结果 + 最佳实践      │
├─────────────────────────────────────────────────┤
│  L5  操作证据层 — 验证性信息                      │
│      测试结果 + 构建日志 + 截图 + 性能报告        │
└─────────────────────────────────────────────────┘
```

**核心原则：**
- **L1 目标层**：Agent 不能自行修改，必须经用户确认
- **L2 项目知识**：摘要优先，按需展开
- **L3 工作状态**：只保留最新，每次迭代替换而非累积
- **L4 外部知识**：懒加载，不预注入
- **L5 操作证据**：只要结论，不要完整输出

我们将依次学习：

1. **[上下文分层模型](./layering)** — 理解五层结构：目标、项目知识、工作状态、外部知识、操作证据
2. **[注入策略](./injection-strategy)** — 掌握三种注入模式：预注入、懒注入、触发注入，以及 Token 预算分配
3. **[压缩与摘要](./compression)** — 学会三种压缩技术：提取式、摘要式、结构化，以及压缩的时机和边界
4. **[实战案例](./practice)** — 为一个真实的 Agent 任务设计完整的上下文包，并模拟执行过程

每个概念都会配合具体的代码示例和场景分析。学完本模块后，你将能够：
- 为任何 Agent 任务设计合理的上下文架构
- 在 Token 预算紧张时做出正确的取舍决策
- 识别和修复常见的上下文问题（污染、过时、冗余）

## 快速自测

在深入学习之前，先思考以下问题：

1. 你的 Agent 在执行长任务时，是否出现过"忘记"关键约束的情况？
2. 当上下文窗口接近满载时，你的 Agent 是否开始做出不合理的决策？
3. 你是否观察到 Agent 重复读取同一个文件，或者重复尝试已经失败的方案？

如果以上任何一个答案是"是"，那么你的 Agent 很可能存在上下文工程问题。接下来的章节将帮助你系统性地诊断和解决这些问题。
